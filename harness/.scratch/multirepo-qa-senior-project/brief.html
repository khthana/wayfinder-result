Cross-Repo Entity Disambiguation

บทวิเคราะห์ข้อเสนอ Multi-Repo/Microservice Codebase Q&A Harness พร้อมโครงร่างที่ปรับใหม่ หลังพบว่า contribution ที่นักศึกษาตั้งใจจะเสนอถูกตีพิมพ์ไปแล้วเมื่อธันวาคม 2025 และช่องว่างสามข้อที่อ้างไว้ใน proposal ไม่เป็นความจริง

นักศึกษา ทำคนเดียว ระยะเวลา 2 ภาคเรียน · ~8 เดือน ทรัพยากร GPU server ภาควิชา จัดทำ 1 ก.ย. 2026
ส่วนที่ 1

เอกสารแนะแนวสำหรับอาจารย์

บรรทัดสรุป

สิ่งที่ต้องรู้ก่อนพบนักศึกษา

ข้อเสนอในรูปแบบปัจจุบันจะถูกกรรมการทุบได้ภายในห้านาที — ไม่ใช่เพราะไอเดียแย่ แต่เพราะการวางตำแหน่งผิด ข้ออ้างสามในสี่ประโยคที่ใช้สร้างความชอบธรรมให้โครงงานเป็นเท็จ และ contribution หลักที่อ้างว่าเป็นของใหม่ ถูกตีพิมพ์ไปแล้วพร้อมผลที่ชนะทั้ง Copilot และ Cursor

แต่นี่เป็นข่าวดี เพราะยังอยู่ในขั้นเสนอหัวข้อ ไม่ใช่เดือนที่หก ปัญหาที่นักศึกษาจับได้นั้นเป็นปัญหาจริง — Sourcegraph วัดเองว่าช่องว่างประสิทธิภาพของ agent บนงาน multi-repo กว้างกว่างาน single-repo — เพียงแต่ต้องเปลี่ยนสิ่งที่ประกาศว่าเป็นของใหม่

เอกสารนี้เสนอให้เปลี่ยนจาก routing policy ไปเป็น cross-repo entity disambiguation ซึ่งเป็นช่องว่างที่งานสองชิ้นระบุตรงกันโดยอิสระว่าเป็น failure mode อันดับหนึ่ง แต่ยังไม่มีใครแก้ ที่สำคัญกว่านั้นคือมันเป็น contribution ระดับ component ไม่ใช่ระดับ ระบบ — นักศึกษาจึงไม่ต้องเอาชนะ Cursor แบบตัวต่อตัว ซึ่งเป็นสิ่งที่คนทำคนเดียวไม่มีทางทำได้

คำตัดสินรายข้ออ้าง

ทุกประโยคใน proposal ที่ทำหน้าที่สร้างความชอบธรรม ถูกตรวจกับหลักฐานจริง:

  • ผิด Cursor/Copilot are single-repo Cursor รองรับ multi-root workspace ตั้งแต่ราวพฤษภาคม 2025 และมี per-root indexing กับ @Codebase ที่ค้นรวมกัน · Claude Code ทำ multi-repo ผ่าน --add-dir เหลือเพียง Copilot ที่ข้ออ้างยังพอฟังขึ้น เพราะ semantic index ของ VS Code มีปัญหาจริงใน multi-root workspace
  • ผิด No lightweight cross-repo solution currently exists flupkede/codesearch เป็น multi-repo semantic code search MCP server เขียนด้วย Rust มี repo groups และ cross-repo RRF fan-out ranking — คือ “routing layer” ที่นักศึกษาตั้งใจจะสร้างพอดี — รันออฟไลน์เต็มรูปแบบ ไม่ต้องใช้ GPU ไม่ต้องมี vector DB ภายนอก ยังมี Sourcebot ที่ติดตั้งด้วย docker compose up คำสั่งเดียว
  • ตายแล้ว The routing/pruning policy is the core contribution arXiv 2512.05908 (ธ.ค. 2025) ทำ two-phase repository routing แล้วตามด้วย in-repo localization บนระบบ 46 repository / 1.1M LOC ได้ Pass@10 = 0.82 ชนะ Copilot (0.61) และ Cursor (0.57) · นักศึกษาต้องอ้างอิงงานชิ้นนี้ มิฉะนั้นเป็นปัญหา academic integrity
  • ผิด real access is unavailable ไม่จริงสำหรับ open-source polyrepo organization — kubernetes, HashiCorp, Grafana, Netflix OSS เปิดหมด ที่เข้าไม่ถึงคือ corpus ระดับองค์กรแบบปิด ซึ่งโครงงานนี้ไม่จำเป็นต้องใช้
ข้อที่นักศึกษากังวลเกินจริง

corpus สังเคราะห์ใช้ได้ ไม่ต้องกังวล — Train Ticket ตีพิมพ์ใน IEEE TSE, TeaStore ใน IEEE MASCOTS 2018, Sock Shop ใน ECASE@ICSE 2017 และมี systematic mapping study (AST 2024) ยืนยันการใช้ทั้งชุมชน ความเสี่ยงที่นักศึกษาระบุไว้ในหัวข้อ Risk จึงไม่ใช่ความเสี่ยงจริง

ข้อกังขาที่อาจารย์ตั้งไว้ว่า “RAG น่าจะช้า”

ข้อกังขานี้ถูก แต่ชี้ผิดมิติ และการชี้ให้ถูกมิติเปลี่ยนการออกแบบโครงงานทั้งหมด:

มิติคำตัดสินหลักฐาน
Query latency ไม่ใช่ปัญหา dense retrieval อยู่ระดับมิลลิวินาที และ เร็วกว่า agentic search ซึ่งต้องเสีย LLM round-trip หลายรอบต่อการค้นหนึ่งครั้ง
Cold-start indexing ช้าจริง Cursor เปิดตัวเลข p99 ที่ 4.03 ชม. ก่อนทำ index reuse เหลือ 21 วินาที หลังทำ — แต่เป็น dedup ระดับแพลตฟอร์ม ที่นักศึกษาคนเดียวทำตามไม่ได้
Recall ปัญหาแท้จริง embedding สำเร็จรูปตกจาก NDCG@10 71.7 บน code search ธรรมดา เหลือ 20.3 เมื่อเปลี่ยนเป็นงาน issue-to-edit localization
ข้อควรระวังในการอ่านวรรณกรรมฝั่งอุตสาหกรรม

หลักฐานที่คนอ้างกันบ่อยที่สุดว่า “agentic grep ชนะ RAG” อ่อนกว่าที่เข้าใจกัน — คำพูดที่ถูกยกมาซ้ำๆ ตามด้วยประโยคว่า “This was just vibes, so internal vibes” ทันที ขณะที่การทดลอง A/B บน production ของ Cursor (พ.ย. 2025) วัดได้ว่า semantic search ให้ accuracy +12.5% เหนือ grep อย่างเดียว และ Cursor เองก็ไปสร้าง trigram index เพิ่ม ไม่ใช่เอา index ออก

สิ่งที่ควรบอกนักศึกษา: อย่าตั้งโจทย์เป็น “RAG vs agentic” เพราะ hybrid คือคำตอบเชิงประจักษ์ และการตั้งโจทย์แบบขั้วตรงข้ามจะทำให้ถูกกรรมการที่ตามวรรณกรรมจับได้

งานที่กินพื้นที่ไปแล้ว

สี่หัวข้อย่อยที่นักศึกษาอาจคิดว่ายังว่างอยู่ แต่ปิดไปแล้วทั้งหมด:

หัวข้อสถานะปิดโดย
Repository routingปิดarXiv 2512.05908
“structural index ช่วยกว่า grep ไหม”ปิดarXiv 2606.22417 — controlled ablation แบบมี p-value
Abstraction-level selectionปิดRAPTOR, A-RAG
Query-complexity routingปิดAdaptive-RAG, RAGRouter-Bench
Token-level compressionปิดLLMLingua-2, Provence
Chunking strategy tuningไม่คุ้มcAST ได้ +4.3 Recall@5; JetBrains พบ line-based เทียบเท่า syntax-aware

ประเด็นเรื่อง premise ที่ต้องแก้: proposal อ้าง Lost in the Middle เป็นฐาน ซึ่งยังจริงในปี 2026 แต่กลไกเปลี่ยนไปแล้ว — งานปัจจุบันชี้ว่า semantic similarity และ distractor สำคัญกว่าตำแหน่ง และมีงานที่เสนอว่าปรากฏการณ์นี้เป็น emergent property ของ training distribution คือ เทรนให้หายได้ ควรเปลี่ยนไปอ้างงานที่ไม่หมดอายุเมื่อโมเดลเก่งขึ้น บวกเหตุผลเรื่องต้นทุนและ latency แทน

ช่องว่างที่ยังเหลือจริง

ตรวจสอบแล้วว่ายืนอยู่ แต่ต้องกรอบให้แม่น เพราะมีของที่เข้ามาใกล้:

ช่องว่างความเหมาะกับคนเดียวข้อควรระวัง
Cross-repo name collision
entity disambiguation		 ดีที่สุด A-RAG และ DeepRepoQA ระบุตรงกันว่า entity confusion เป็น failure mode อันดับหนึ่ง แต่ไม่มีใครแก้
Multi-repo QA benchmark ระวัง ไม่มีฝั่ง peer-reviewed จริง แต่ CodeScaleBench ของ Sourcegraph มี 370 tasks โดยส่วน Org 220 tasks ต้องใช้ organization-level navigation — แข่งวางตำแหน่งกับบริษัทที่มีทรัพยากรมากกว่า
Index staleness vs routing accuracy ใช้เวลาสูง arXiv 2512.05908 ระบุเองว่ายังไม่ได้ทำ แต่ต้องรัน pipeline ข้ามช่วงเวลาหลายรอบ
Cost/accuracy Pareto ใน multi-repo เป็นส่วนเสริม เล็กเกินกว่าจะเป็น contribution เดี่ยว แต่ควรใส่เป็นผลรองของโครงงาน

ตรวจแล้ว ผมตรวจ MULocBench ซึ่งดูเผินๆ เหมือนจะปิดช่องว่างนี้ — ไม่ปิด เพราะเป็น multi-type (ครอบคลุมไฟล์ที่ไม่ใช่โค้ด เช่น config และ docs) ไม่ใช่ multi-repo เป็น 1,100 issues จาก 46 Python project ที่แยกกัน

คำถามที่ควรถามนักศึกษาในการพบครั้งถัดไป

เรียงตามลำดับที่ควรถาม — สามข้อแรกเป็นการทดสอบว่านักศึกษาอ่านงานที่มีอยู่มาจริงแค่ไหน ก่อนจะไปถึงการปรับหัวข้อ:

  1. ลองเปิด Cursor ให้ดูหน่อยว่ามันทำ multi-root workspace ไม่ได้จริงไหม ไม่ใช่การจับผิด แต่เป็นการสอนว่าข้ออ้างเรื่องช่องว่างต้องตรวจกับของจริงก่อนเขียนลงกระดาษเสมอ และเป็นบทเรียนที่ติดตัวไปตลอด
  2. อ่าน arXiv 2512.05908 แล้วบอกหน่อยว่างานของเราต่างจากเขาตรงไหน คำถามชี้ขาด ถ้าตอบไม่ได้แปลว่ายังไม่มีหัวข้อ ถ้าตอบได้แปลว่าเริ่มมองเห็นช่องว่างจริง
  3. ถ้ามี UserService อยู่ใน 5 repo แล้วคนถามว่า “UserService จัดการ session ยังไง” เครื่องมือควรทำอะไร คำถามที่พาไปสู่หัวข้อใหม่โดยไม่ต้องบอกคำตอบ ให้เขาค้นพบปัญหา entity collision เอง
  4. ถ้าทำแล้วผลออกมาว่าวิธีของเราไม่ช่วยเลย จะเขียนเล่มยังไง ทดสอบว่าเข้าใจเรื่อง negative result ไหม ถ้าไม่เข้าใจต้องสอน เพราะนี่คือกลไกที่ทำให้โครงงานนี้ไม่มีทางล้ม
  5. ถ้าเดือนที่สองพบว่าชื่อชนกันน้อยมาก จะทำอะไรต่อ ฝึกให้คิดเรื่องจุด go/no-go และแผนสำรองตั้งแต่ก่อนเริ่ม ไม่ใช่ตอนที่สายไปแล้ว

หัวข้อและข้ออ้าง

ชื่อโครงงานที่เสนอ

Cross-Repository Entity Disambiguation for LLM Code Question Answering

ในระบบ polyrepo และ microservice สัญลักษณ์ชื่อเดียวกัน — UserService, Order, Config, handleRequest — ปรากฏในหลาย repository โดยมีความหมายต่างกัน retrieval คืนมาทั้งหมด แล้ว agent เอามาปนกันจนตอบผิด โครงงานนี้วัดขนาดของปัญหาในระบบจริง เสนอวิธีแก้ระดับ component และวัดว่าช่วยได้จริงหรือไม่

สมมติฐานที่พิสูจน์ผิดได้

H1 — การทำ explicit cross-repo entity disambiguation เพิ่มความถูกต้องของคำตอบบนคำถามที่ entity ชนกัน เมื่อเทียบกับ hybrid retrieval baseline ที่ไม่จัดการการชน

ถ้าผลออกมาว่าไม่ช่วย โครงงานก็ยังสมบูรณ์ — เป็น negative result ที่ขัดกับสิ่งที่งานสองชิ้นคาดเดาไว้ จึงมีค่าพอเขียนเล่ม นี่คือเหตุผลหลักที่เลือกหัวข้อนี้: นักศึกษาไม่มีทางส่งงานไม่ได้

ทำไมข้อนี้รอด ในขณะที่ข้อเสนอเดิมไม่รอด

เป็น contribution ระดับ component ไม่ใช่ระดับ ระบบ — ไม่ต้องเอาชนะ Cursor หรือ Copilot ตัวต่อตัว ซึ่งคนทำคนเดียวไม่มีทางทำได้ แค่ต้องแสดงว่าเสียบชั้น disambiguation เข้าไปใน baseline ที่มีอยู่แล้วดีขึ้น

ขอบเขต

อยู่ในขอบเขตตัดออก และเหตุผล
วัด collision rate ด้วย tree-sitter เขียน static analyzer เอง — ไม่มีพื้น IR ใช้เวลาเกินคุ้ม
สร้างชุดประเมิน ~200 คำถาม สร้าง code graph database — LARGER แสดงว่าทำได้โดยไม่ต้องมี graph DB
ชั้น disambiguation เสียบบน agent ที่มีอยู่ สร้าง agent เต็มระบบเอง — ความเสี่ยงข้อใหญ่ที่สุด อาจารย์ต้องคอยดึง
เปรียบเทียบกับ baseline สามตัว เทรน embedding model เอง — เกินขอบเขต ป.ตรี
วิเคราะห์สถิติแบบมี CI จูน chunking strategy — หลักฐานบอกว่าได้ผลน้อยมาก

Corpus สองชั้น

กับดักที่ต้องเช็คก่อนเลือก

“microservice demo” ส่วนใหญ่อยู่ใน repo เดียว — Train Ticket และ Google Online Boutique เป็น monorepo ที่มีหลาย service จึงใช้กับโจทย์ cross-repo ไม่ได้ ประเด็นนี้ถูกมองข้ามง่ายมาก และถ้าพลาดจะเสียเวลาไปทั้งเดือน

ชั้นที่ 1 · ควบคุมได้ ใช้ตอนพัฒนา

Sock Shop เป็นตัวเลือกหลัก เพราะเป็น polyrepo แท้ — แต่ละ service แยก repository จริง (front-end, catalogue, carts, orders, payment, shipping, user, queue-master)

ชั้นที่ 2 · ของจริง ใช้ตอนวัดผล

GitHub organization ที่เป็น polyrepo แท้และมี type ชื่อซ้ำข้าม repo สูง: kubernetes (kubernetes, api, apimachinery, client-go, kubectl), HashiCorp, Grafana, Netflix OSS

ผลเชิงประจักษ์ชิ้นแรก · ทำก่อนอย่างอื่น

ใช้ tree-sitter ดึงชื่อ top-level symbol ต่อ repo แล้วหาชื่อที่ปรากฏใน ≥2 repo เพื่อตอบประโยคนี้:

“จากการสำรวจ N polyrepo organization พบว่า X% ของชื่อสัญลักษณ์ระดับบนสุดชนกันข้าม repository ตั้งแต่ 2 แห่งขึ้นไป”

ประโยคเดียวนี้เป็นผลลัพธ์ที่ตีพิมพ์ได้ในตัวเอง และเป็นจุด go/no-go แรก — ถ้าการชนเกิดน้อย ต้องเปลี่ยนหัวข้อตั้งแต่เดือนที่ 2 ไม่ใช่เดือนที่ 6

นักศึกษาเคยเรียนสถิติเบื้องต้นแต่ไม่มีพื้น IR — จุดแข็งนี้หาได้ยากใน senior project และควรใช้ให้เต็ม เพราะ GPU server ทำให้รันซ้ำได้แทบฟรี

  • รัน ≥3 seeds รายงาน confidence interval ไม่ใช่เลขเดี่ยว
  • paired test ระหว่าง baseline กับวิธีที่เสนอ บนคำถามชุดเดียวกัน
  • Cohen’s κ ระหว่าง LLM-as-judge กับ label ที่ตรวจเอง — StackRepoQA ตั้งเกณฑ์ไว้ที่ 0.78–0.87

ถ้า κ ต่ำ ต้องเลิกใช้ LLM-as-judge เป็น metric หลัก ต้องเช็คก่อนใช้ ไม่ใช่หลังจากรันการทดลองทั้งหมดไปแล้ว

Control ที่ต้องมี

ยืมจาก Agent Retrieval Bench: counterfactual wrong-repository controls และ no-gold examples สำหรับวัด abstention — เพิ่มงานน้อยแต่ทำให้ผลน่าเชื่อถือขึ้นมาก พร้อม base-commit freezing และ query sanitization กัน leakage

Baseline · ของจริงทั้งหมด ไม่ต้องสร้างเอง

#Baselineบทบาท
1ripgrep + LLMbaseline โง่แต่แข็ง — หลักฐานยืนยันว่า agentic grep แข็งจริง
2flupkede/codesearch MCPhybrid RRF multi-repo ที่มีอยู่แล้ว คือคู่แข่งตัวจริง
3Claude Code + --add-dirตัวแทน agent เชิงพาณิชย์
4Sourcebotถ้าเวลาเหลือเท่านั้น

การใช้ GPU server

  • GPU → embedding model โลคัลและ LLM-as-judge — ปริมาณเรียกสูง ต้นทุนต่อครั้งต้องเป็นศูนย์
  • API frontier model → ตัว agent เท่านั้น เรียกน้อยครั้งกว่ามาก คุมงบได้
  • ห้ามใช้ local LLM เป็นตัว agent — โมเดลเปิดยังอ่อนกับงาน agentic tool-calling จะทำให้ผลการทดลองวัดความอ่อนของโมเดล ไม่ได้วัดวิธีการ

แผน 8 เดือน

ภาคเรียนที่ 1

  1. เดือน 1

    อ่านวรรณกรรม + ปูพื้น IR

    BM25, recall@k, MRR, nDCG — กันเวลาไว้เต็มเดือนเพราะไม่มีพื้นฐานมาก่อน

    annotated bibliography + baseline ripgrep+LLM ที่รันได้
  2. เดือน 2

    เลือก corpus + วัด collision rate

    ตรวจก่อนว่าแต่ละ demo เป็น polyrepo จริงไหม แล้ววัดอัตราการชนของชื่อ · สัมภาษณ์ VoC 1 สัปดาห์

    ผลเชิงประจักษ์ชิ้นแรก
GATE 1

collision rate ต้องไม่ต่ำจนไร้นัยสำคัญ — ถ้าต่ำ เปลี่ยนไปทำ contribution แบบ benchmark ทันที ยังเหลือเวลาอีก 6 เดือน

  1. เดือน 3

    สร้างชุดประเมิน

    ~200 คำถามที่พุ่งเป้า entity ที่ชน โดย ~100 ข้อตรวจด้วยมือ · เสริมด้วยคำถามธรรมชาติจาก issue/PR history

    dataset v1
  2. เดือน 4

    รัน baseline ทั้งสามตัว

    วัด baseline บน dataset พร้อมตรวจ Cohen’s κ ของ LLM-as-judge ก่อนใช้จริง

    สอบหัวข้อ + ตัวเลข baseline
GATE 2

baseline ต้องตกจริงบนคำถามที่ entity ชน — ถ้า baseline ทำได้ดีอยู่แล้ว แปลว่าไม่มี headroom เปลี่ยนไปทำ staleness study

ภาคเรียนที่ 2

  1. เดือน 5

    ออกแบบและสร้างชั้น disambiguation

    เสียบบน agent ที่มีอยู่ ไม่สร้างเอง

    เครื่องมือที่รันได้
  2. เดือน 6

    วัดผล + ablation + วิเคราะห์สถิติ

    3 seeds ขึ้นไป รายงาน CI และ paired test

    ตารางผลหลัก
GATE 3

ถ้าวิธีที่เสนอไม่ชนะ baseline ไม่ต้องเปลี่ยนหัวข้อ — รายงานเป็น negative result พร้อมวิเคราะห์สาเหตุ ยังเป็นโครงงานที่สมบูรณ์

  1. เดือน 7

    วิเคราะห์ failure + corpus ชั้นสอง

    รันบน organization จริงเพื่อยืนยันว่าผลไม่ได้จำกัดอยู่แค่ระบบตัวอย่าง

    ผลบนของจริง
  2. เดือน 8

    เขียนเล่มและเตรียมสอบ

    เขียนข้อจำกัดของงานให้ตรงไปตรงมา รวมถึงข้อจำกัดของ VoC

    เล่มสมบูรณ์
ขอบเขตขั้นต่ำที่ยังจบได้

ถ้าทุกอย่างช้ากว่าแผน collision measurement study + evaluation set + baseline comparison เพียงสามอย่างนี้ก็เป็นโครงงานที่สมบูรณ์แล้ว เพราะเป็นงานวัดผลที่ยังไม่มีใครทำ ส่วนชั้น disambiguation เป็นส่วนต่อยอด

ความเสี่ยงและแผนสำรอง

ความเสี่ยงตรวจพบเมื่อแผนสำรอง
ชื่อชนกันน้อยเกินไปเดือน 2เปลี่ยนเป็น benchmark contribution
baseline เก่งอยู่แล้ว ไม่มี headroomเดือน 4เปลี่ยนเป็น staleness study
LLM-as-judge ไม่น่าเชื่อถือ (κ ต่ำ)เดือน 4ใช้ retrieval metric เป็นหลักแทน
ไหลไปสร้าง agent เต็มระบบตลอดเวลาเสี่ยงที่สุด — นักศึกษาที่อยากสร้างของเจ๋งมักตกหลุมนี้ อาจารย์ต้องคอยดึงกลับ

ข้อจำกัดที่ต้องเขียนลงเล่มตรงๆ

นักศึกษาปีสี่ที่ยังไม่เคยทำงานไม่ใช่ตัวแทนของ developer ที่ทำงานกับ polyrepo ระดับองค์กร การสัมภาษณ์ VoC จึงใช้เป็น motivating evidence ได้ แต่ใช้เป็นหลักฐานสนับสนุนผลไม่ได้ การเขียนข้อจำกัดนี้เองแสดงวุฒิภาวะเชิงวิจัย และมักได้คะแนนจากกรรมการ
