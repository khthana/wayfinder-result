# วิธีอ่านเอกสารชุดนี้

**เอกสารนี้เป็นร่างสำหรับถกเถียง ไม่ใช่ข้อกำหนดตายตัวที่ส่งมาให้ทำตาม**

อาจารย์ระบุไว้ตรง ๆ ว่าจะเอา spec นี้ไปให้ทีมนักศึกษาออกความเห็นและแก้ไข เอกสารจึงเขียนต่างจาก spec ทั่วไปสามอย่าง:

1. **ทุกการตัดสินมีเหตุผลและทางเลือกที่ไม่เอากำกับ** — เพื่อให้เถียงได้อย่างมีข้อมูล แทนที่จะเถียงจากความรู้สึกหรือยอมรับไปเฉย ๆ
2. **แยกชัดว่าอะไรต่อรองไม่ได้ อะไรเปลี่ยนได้** — ดูตาราง §1.5
3. **ของที่ยังไม่ถูกทดสอบติดป้ายไว้** — โดยเฉพาะหน้าจอฝั่งนักศึกษาที่ยังไม่เคยผ่านสายตาผู้ใช้จริงสักคน

> **ข้อสังเกตที่บันทึกไว้ตามตรง:** ทีมโครงงานรีวิว spec นี้ในฐานะ**คนสร้าง** ไม่ใช่ในฐานะ**ผู้ใช้** ความเสี่ยงที่ว่ายังไม่มีนักศึกษาผู้เรียนคนไหนเคยอ่านหน้าส่งงานเลย **ไม่ได้ถูกปิดด้วยการรีวิวรอบนี้** อาจารย์ตัดสินแล้วว่าข้ามไปก่อน (7 ส.ค. 69)

# 1. บทนำ

## 1.1 ที่มาของปัญหา

วิชา UX/UI Design ของภาควิชา มีนักศึกษาราว 48 คนต่อการเปิดสอนหนึ่งครั้ง และมี **ชิ้นงานที่ต้องตรวจราว 20 ชิ้น × ทั้งห้อง ต่อหนึ่งภาคการศึกษา** ตัวเลขนี้ไม่ได้ประมาณเอา แต่สกัดมาจากเอกสารตรวจงานฉบับที่ใช้กับผู้ช่วยสอนจริง

ปัญหาที่ตามมามีสองชั้น และชั้นที่สองสำคัญกว่าชั้นแรก:

**ชั้นที่หนึ่ง — ปริมาณงานตรวจ** อาจารย์ตรวจเองทั้งหมดไม่ไหว จึงต้องใช้ผู้ช่วยสอน ซึ่งพาปัญหาความสม่ำเสมอของการให้คะแนนตามมา

**ชั้นที่สอง — ข้อจำกัดการตรวจกำหนดหน้าตาของรายวิชา** ปัจจุบันงาน Figma เป็นสัดส่วนน้อยของภาคการศึกษา **ไม่ใช่เพราะ Figma ไม่สำคัญ แต่เพราะตรวจ Figma ด้วยมือมันลำบาก** เมื่อมีระบบช่วยตรวจ บทบาทของ Figma ในรายวิชาจะ**มากขึ้น** ไม่ใช่น้อยลง

> ระบบนี้จึงไม่ใช่แค่ "ทำของเดิมให้เร็วขึ้น" แต่เป็นการ**ปลดข้อจำกัดที่กำลังกำหนดหน้าตาของรายวิชาอยู่** ถ้าทีมเขียนบทนำของรายงานโดยเล่าแค่เรื่อง "ลดเวลาตรวจ" จะเสียประเด็นที่แข็งที่สุดของโครงงานไป

**ชั้นที่สาม — ความรับผิดชอบต่อการประกันคุณภาพ** หลักสูตรใช้กรอบ **TABEE** ซึ่งข้อ 1.7 บังคับให้ **สืบย้อนได้ว่าใครตัดสินอะไรด้วยเหตุผลใด** และ Course Portfolio ต้องเก็บ**ชิ้นงานจริง ไม่ใช่แค่คะแนน** ย้อนหลังอย่างน้อย 2 ปีการศึกษา (วงรอบรับรอง 6 ปี) การเอา AI เข้ามาให้คะแนนโดยไม่มีร่องรอยว่าใครตัดสิน จะทำให้หลักฐานสำหรับ TABEE ขาดตรงจุดที่สำคัญที่สุด

## 1.2 เป้าหมายของระบบ

1. ให้ AI **เสนอ**คะแนนตาม rubric พร้อมเหตุผลและหลักฐานที่ชี้กลับไปที่ตัวงานได้ โดยที่**อาจารย์เป็นผู้ตัดสินเสมอ**
2. เป็น**สมุดคะแนนของทั้งรายวิชา** ไม่ใช่เฉพาะส่วนที่ AI ตรวจ
3. คำนวณ **ผลสัมฤทธิ์ตาม CLO** จากคะแนนที่มีอยู่จริง
4. เก็บ**ร่องรอยการตัดสินใจครบทุกชั้น** ในรูปที่ยกไปเป็นหลักฐาน TABEE ได้
5. ผลิต**ตัวเลขความสอดคล้องระหว่าง AI กับอาจารย์** ที่เชื่อถือได้พอจะเป็นผลการทดลองของรายงานโครงงาน

## 1.3 ขอบเขต

**อยู่ในขอบเขต**

- ชิ้นงานที่ตรวจคือ **Figma และ PDF เท่านั้น** ไม่มีเว็บที่ deploy แล้ว ไม่มีโค้ด (อาจารย์ยืนยันซ้ำ 6 ส.ค. 69)
- ระบบ **standalone** ทำทุกอย่างเอง **ไม่ต่อกับ LMS เดิมและไม่ต่อกับระบบทะเบียน**
- deploy บน infrastructure ของคณะ
- รองรับบทบาท อาจารย์ / ผู้ช่วยสอน / นักศึกษา / ผู้ดูแลระบบ

**อยู่นอกขอบเขต**

| ไม่ทำ | เหตุผล |
|---|---|
| เชื่อมต่อระบบทะเบียน KMITL | ไม่มีสิทธิ์เข้าถึง และไม่จำเป็นต่อการพิสูจน์แนวคิด — นำเข้ารายชื่อด้วย Excel แทน |
| รวม CLO ขึ้นเป็น PLO | เป็นงานระดับหลักสูตร ไม่ใช่ระดับรายวิชา |
| ตรวจสอบความซื่อสัตย์ทางวิชาการ (คัดลอกงาน) | ยังตอบไม่ได้ว่าเป็นฟีเจอร์หรือเป็นนโยบาย ต้องคุยกับภาควิชาก่อน |
| ประเมินเพื่อน (peer evaluation) | เพิ่มความซับซ้อนของโมเดลคะแนนมาก โดยยังไม่มีหลักฐานว่าจำเป็น |
| การแจ้งเตือน (อีเมล/push) | ยังไม่มีหลักฐานว่าจำเป็น — นักศึกษาเข้าระบบตามเดดไลน์อยู่แล้ว |
| ระบบสิทธิ์ที่ตั้งค่าได้อิสระ | ใช้บทบาทตายตัวสี่แบบแทน ซึ่งพอกับความต้องการจริงและลดพื้นที่ผิดพลาดมาก |

## 1.5 อะไรต่อรองไม่ได้ อะไรเปลี่ยนได้

นี่คือตารางที่ทีมควรอ่านก่อนเถียงเรื่องใด ๆ ในเอกสารนี้

### ต่อรองไม่ได้

| ข้อจำกัด | เพราะอะไร |
|---|---|
| **สถาปัตยกรรมสองเครื่อง** (VM ⟷ GPU box) | เป็นรูปของ infrastructure ที่คณะให้มา ไม่ใช่ตัวเลือกออกแบบ |

| **นักศึกษาไม่เห็นคะแนนที่ AI ให้** | ตัดสินโดยอาจารย์ · ดู §7.4 |
| **AI ไม่ตรวจจนกว่าอาจารย์จะกดสั่ง** | ถ้าไม่มีข้อนี้ AI กลายเป็นเครื่องลองคะแนนของนักศึกษา |
| **ระบบเสนอได้ แต่แก้ rubric เองไม่ได้** | ต้องตอบให้ได้ว่าไม้บรรทัดที่ตัดสินนักศึกษาเปลี่ยนเพราะใคร |
| **RubricVersion ที่ตรวจไปแล้วแก้ไม่ได้ตลอดไป** | ถ้าแก้ได้ คะแนนเก่าทั้งหมดกลายเป็นคะแนนที่ไม่รู้ว่าวัดด้วยอะไร |
| **ข้อมูลที่ใช้วัดระบบ ห้ามใช้ปรับปรุงระบบ** | ถ้าละเมิด ตัวเลขทั้งเล่มใช้ไม่ได้ · ดู เอกสารฉบับที่ 3 |

### เปลี่ยนได้ — และอยากให้ทีมเถียง

- ทางเลือกของ framework และไลบรารีทุกตัว (ยกเว้นข้อบังคับว่าต้องเป็น TypeScript ทั้งระบบ)
- หน้าตาและการจัดวางของทุกหน้าจอ
- ลำดับของงานใน roadmap ภายใต้หมุดวันที่ที่ตายตัว
- โครงสร้างตารางในฐานข้อมูล **ตราบใดที่ยังตอบคำถามการสืบย้อนได้ครบ**
- จำนวนและชื่อของหัวข้อประเมินในตัวอย่าง rubric
- วิธีแบ่งงานในทีม

# 2. Domain model และอภิธานศัพท์

## 2.1 หลักการห้าข้อที่โครงสร้างทั้งหมดตั้งอยู่บน

### 2.1.1 แยก "รายวิชา" ออกจาก "การเปิดสอน"

**รายวิชา (Course)** คือแม่แบบในหลักสูตร: รหัส ชื่อ คำอธิบาย หน่วยกิต — **ไม่มีนักศึกษา ไม่มีคะแนน**

**การเปิดสอน (Course Offering)** คือรายวิชาหนึ่งที่สอนในภาคการศึกษาหนึ่ง เป็นเจ้าของ **CLO / สัปดาห์ / ชิ้นงาน / Rubric / รายชื่อ / คะแนน ทั้งหมด**

**ทางเลือกที่ไม่เอา:** เก็บทุกอย่างไว้ที่ "วิชา" ก้อนเดียวแล้วใส่ฟิลด์ภาคการศึกษา

**เหตุผลที่ไม่เอา:** วิชานี้เปิดสอนทุกภาค ถ้าไม่แยก การแก้ CLO ของเทอมนี้จะไปเปลี่ยนความหมายของคะแนนเทอมที่แล้ว และฟีเจอร์ "คัดลอกไปเทอมใหม่" (โจทย์ข้อ 14) จะเขียนไม่ได้เลย

### 2.1.2 สัปดาห์เป็น entity จริง

สัปดาห์มีลำดับ หัวข้อ ช่วงวันที่ **ชิ้นงานผูกกับสัปดาห์ได้แต่ไม่บังคับ** เพราะงานบางชิ้นคร่อมหลายสัปดาห์ และงานบางชิ้นไม่ผูกกับสัปดาห์ไหนเลย

### 2.1.3 ส่งซ้ำเก็บทุกเวอร์ชัน

การส่งใหม่สร้าง**ระเบียนใหม่** ไม่ทับของเดิม คะแนนชี้ไปที่**เวอร์ชันที่ถูกใช้ตรวจจริง**

**เหตุผล:** ถ้าทับ จะตอบไม่ได้ว่าคะแนนที่ให้ไปนั้นให้กับงานหน้าตาแบบไหน ซึ่งเป็นคำถามแรกที่จะถูกถามเวลามีข้อโต้แย้ง

### 2.1.4 การตรวจ = หนึ่งก้อนต่อผู้ตรวจหนึ่งราย

AI ตรวจ = ก้อนหนึ่ง · อาจารย์ตรวจ = อีกก้อนหนึ่ง · **ไม่เขียนทับกัน**

งานหนึ่งชิ้นจึงมีการตรวจได้หลายก้อน (AI, อาจารย์, ผู้ช่วยสอน, อาจารย์คนที่สองในโหมดทดสอบ rubric) และมีเครื่องหมาย `is_authoritative` ชี้ว่าก้อนไหนคือคะแนนที่มีผลจริง

### 2.1.5 หน่วยหลักของโดเมนคือ "กิจกรรมการประเมิน" ไม่ใช่ "ชิ้นงาน"

**การสอบคือกิจกรรมการประเมินที่ไม่มีไฟล์ให้เก็บ** โครงข้อมูลจึงเป็น:

```
กิจกรรมการประเมิน
   → (มี / ไม่มี) การส่งไฟล์
      → ถ้ามีไฟล์ จึงมี rubric และการตรวจ
```

**กิจกรรมที่ไม่มีไฟล์ก็ยังต้องผูก CLO และยังต้องมีคะแนน** ถ้าไม่ทำแบบนี้ ตัวเลข CLO จะสะท้อนแค่ครึ่งวิชา และการส่งออกคะแนนจะส่งออกได้แค่ครึ่งเดียว

**ราคาที่จ่าย:** อาจารย์ต้องใช้ระบบนี้เป็นสมุดคะแนนหลัก ไม่ใช่ใช้เฉพาะส่วน AI (อาจารย์ตัดสิน 6 ส.ค. 69)

### โครงเรื่องรายวิชา

|---|---|
| **รายวิชา (Course)** | แม่แบบในหลักสูตร: รหัส ชื่อ คำอธิบาย หน่วยกิต ไม่มีนักศึกษา ไม่มีคะแนน |
| **การเปิดสอน (Course Offering)** | รายวิชาหนึ่ง สอนในภาคการศึกษาหนึ่ง เป็นเจ้าของ CLO / สัปดาห์ / ชิ้นงาน / Rubric / รายชื่อ / คะแนน ทั้งหมด |

| **สัปดาห์ (Week)** | หน่วยเวลาของการเปิดสอน มีลำดับ หัวข้อ ช่วงวันที่ |

### งานและการส่ง

| คำ | นิยาม |
|---|---|
| **กิจกรรมการประเมิน (Assessment Activity)** | หน่วยหลักของโดเมน — ทุกอย่างที่ให้คะแนนได้ รวมถึงการสอบที่ไม่มีไฟล์ส่ง |
| **ชิ้นงาน (Assignment)** | กิจกรรมการประเมินที่**มีไฟล์ให้ส่ง** มีคำสั่ง กำหนดส่ง รูปแบบการส่ง (เดี่ยว/กลุ่ม) และ Rubric อย่างน้อยหนึ่งชุด |
| **การส่ง (Submission)** | เหตุการณ์ที่นักศึกษาหรือกลุ่มส่งงานหนึ่งครั้ง มีเวลาส่ง ผู้ส่ง และสถานะส่งช้า/ตรงเวลา · ส่งใหม่ = ระเบียนใหม่ |
| **ไฟล์แนบ (Artifact)** | ลิงก์ Figma, ไฟล์อัปโหลด, ข้อความ — หนึ่งการส่งมีได้หลายไฟล์แนบ |
| **สแนปช็อต (Snapshot)** | สำเนาภาพ/ข้อมูลของไฟล์แนบ **ณ เวลาที่กดส่ง** เก็บไว้เพื่อให้ตรวจสอบย้อนหลังได้แม้ต้นฉบับถูกแก้ |
| **กลุ่ม (Group)** | กลุ่มผู้ส่งของ **ชิ้นงานหนึ่งชิ้น** ไม่ใช่ของรายวิชา — ชิ้นงานคนละชิ้นจับกลุ่มคนละแบบได้ |
| **สถานะส่งช้า (Late)** | เป็น**สถานะ**ของการส่ง การหักคะแนนเป็นชั้นคำนวณแยกต่างหาก ไม่ใช่เกณฑ์ใน rubric |

### เกณฑ์และคะแนน

| คำ | นิยาม |
|---|---|
| **Rubric** | ชุดเกณฑ์การให้คะแนน**หนึ่งมิติ**ของชิ้นงานหนึ่ง · ชิ้นงานหนึ่งมีได้หลาย rubric (เช่น ด้านงานออกแบบ + ด้านการนำเสนอ) แต่ละตัวมีคะแนนเต็มของตัวเอง — **ไม่ใช่**การให้ผู้ตรวจต่างคนใช้คนละชุด |
| **RubricVersion** | เนื้อหาจริงของ rubric ณ ช่วงเวลาหนึ่ง · **เวอร์ชันที่ใช้ตรวจไปแล้วแก้ไม่ได้ตลอดไป** |
| **แม่แบบ rubric (Template)** | rubric ที่เก็บในคลังระดับ**รายวิชา** เพื่อหยิบข้ามเทอม · **หยิบ = ก๊อป** แก้ในชิ้นงานไม่กระทบแม่แบบ และแก้แม่แบบไม่ไหลกลับ |
| **หัวข้อประเมิน (Criterion)** | หนึ่งแง่มุมที่ถูกให้คะแนน มีน้ำหนักและระดับคุณภาพ **และเป็นจุดที่เชื่อมกับ CLO** |
| **ระดับคุณภาพ (Level)** | คำบรรยายว่าคะแนนแต่ละระดับหน้าตาเป็นอย่างไร — **คำบรรยายนี้คือสิ่งที่ LLM ใช้ตัดสิน** จึงบังคับเขียนครบทุกช่อง |
| **การตรวจ (Assessment)** | ผู้ตรวจหนึ่งราย + การส่งหนึ่งครั้ง + Rubric หนึ่งชุด = หนึ่งก้อน |
| **ผู้ตรวจ (Grader)** | AI หรือคน — ถ้าเป็น AI ต้องบันทึกรุ่นโมเดลและเวอร์ชัน prompt |
| **คะแนนรายหัวข้อ (CriterionScore)** | **หน่วยที่เล็กที่สุดที่ระบบเก็บ** ทุกตัวเลขที่เหลือคำนวณขึ้นมาจากตรงนี้ |
| **คำตัดสิน (Authoritative)** | เครื่องหมายบนการตรวจที่ระบุว่าก้อนนี้คือคะแนนที่มีผลจริง |
| **การปรับคะแนนรายบุคคล (IndividualAdjustment)** | ส่วนต่างที่อาจารย์ปรับให้สมาชิกกลุ่มคนหนึ่ง พร้อมเหตุผลบังคับ · **วางทับ ไม่เขียนทับ** |
| **คะแนนสุทธิ** | คะแนนกลุ่ม + ผลรวมการปรับรายบุคคล − ค่าปรับส่งสาย · **คำนวณเสมอ ไม่เก็บเป็นค่านิ่ง** |

### ผลลัพธ์การเรียนรู้

| คำ | นิยาม |
|---|---|
| **CLO** | ผลลัพธ์การเรียนรู้ของรายวิชา · **เป็นของการเปิดสอน** เทอมใหม่คัดลอกมาแก้ได้โดยไม่กระทบของเดิม |
| **การเชื่อม CLO (CLOLink)** | ความสัมพันธ์ระหว่าง**หัวข้อประเมิน**กับ CLO พร้อมน้ำหนัก — เชื่อมที่ระดับหัวข้อประเมิน ไม่ใช่ระดับชิ้นงาน · เป็นแบบ many-to-many |
| **ระดับการบรรลุ (Attainment)** | คำนวณสองระดับ: รายคน และทั้งชั้น |

### คน

| คำ | นิยาม |
|---|---|
| **ผู้ใช้ (User)** | บัญชีหนึ่งต่อคนหนึ่งคน |
| **บทบาท (Role)** | อาจารย์ / ผู้ช่วยสอน / นักศึกษา / ผู้ดูแลระบบ — **บทบาทผูกกับการเปิดสอน ไม่ใช่กับบัญชี** คนเดียวจึงเป็นอาจารย์ในวิชาหนึ่งและนักศึกษาในอีกวิชาได้ |

## 3.3 เส้นทางวิกฤต

```
ตั้งค่ารายวิชา → นำเข้ารายชื่อ → สร้างกิจกรรมการประเมิน + rubric
   → นักศึกษาส่งงาน (แช่แข็งหลักฐานตอนกดส่ง)
   → อาจารย์กด "สั่งตรวจทั้งชุด" (= enqueue + ล็อกการส่ง)
   → AI ตรวจ → อาจารย์ยืนยัน/แก้ → นักศึกษาเห็นคะแนน
   → คะแนนไหลเข้า CLO attainment
```

**ทุกอย่างที่ไม่อยู่บนเส้นนี้คือส่วนขยาย** รวมถึงของที่ออกแบบละเอียดไปแล้วอย่างหน้าจัดการผู้ช่วยสอน และหน้าคัดลอกไปเทอมใหม่

## 3.4 ทำไม CLO attainment ต้องลากช่องกรอกคะแนนเข้ามาด้วย

CLO attainment คิดจาก**ทุกกิจกรรมการประเมิน รวมถึงการสอบ** ถ้าคะแนนสอบไม่เข้าระบบ ตัวเลข CLO ที่ได้คือตัวเลขของครึ่งวิชา และไม่ใช่ตัวเลขที่รายงานประกันคุณภาพใช้ได้จริง

| เอาเข้า MVP | ไม่เอาเข้า MVP |
|---|---|
| กิจกรรมการประเมินที่**ไม่มีไฟล์ให้ส่ง** (สอบ/นำเสนอ) สร้างได้ | สัดส่วนคะแนนรวมทั้งวิชา |
| **ตารางกรอกคะแนนด้วยมือ** หนึ่งช่องต่อคน | การเสนอจุดตัดเกรด |
| ผูกกิจกรรมนั้นกับ CLO ได้ | ดาวน์โหลดไฟล์ส่งทะเบียน |
| คำนวณ CLO attainment จากทุกกิจกรรม | หน้าสรุปเกรดของนักศึกษา |

**ตัดช่องกรอกคะแนนออกแล้ว CLO attainment ที่เหลือคือของประดับ**

# 4. ข้อกำหนดเชิงคุณภาพ

## 4.1 เวลาตอบสนอง

| การกระทำ | เป้าหมาย | เหตุผล |
|---|---|---|
| เปิดหน้าจอทั่วไป | < 1 วินาที | เป็นการใช้งานปกติ |
| กดส่งงาน (บันทึกการส่ง) | < 2 วินาที | **ต้องไม่รอการดึง Figma** — ดู §7.2 |
| ดึงและแช่แข็ง Figma | ไม่มีเป้าหมาย ทำเป็นงานเบื้องหลัง | เป็นการเรียก API ภายนอกที่ควบคุมไม่ได้ |
| AI ตรวจงานหนึ่งชิ้น | ~9 วินาทีต่อหัวข้อประเมิน (ประมาณการ) | เป็นงานในคิว นักศึกษาไม่ได้รอ |
| ตรวจทั้งชั้น 13 กลุ่ม × 7 เกณฑ์ | ~15 นาที | อาจารย์กดสั่งแล้วไปทำอย่างอื่น |

## 4.2 การยืนยันตัวตน

เลือกได้เพราะตรวจพบว่า **สจล. ใช้ Google Workspace อยู่แล้ว** (MX ของ `kmitl.ac.th` ชี้ไป `aspmx.l.google.com` และ SPF include `_spf.google.com`) จึงไม่ต้องขอเชื่อมระบบ SSO ตัวใหม่กับฝ่าย IT

**นโยบายรหัสผ่าน** — ไม่มี เพราะไม่มีรหัสผ่าน

### 4.2.1 สองขั้นของการเข้าถึง

**การมีบัญชี กับ การเห็นรายวิชา เป็นสองประตูคนละบานที่มีเจ้าของคนละคน**

| ขั้น | ใครทำ | ทำอะไร | ผลลัพธ์ |
|---|---|---|---|
| 1 | **ผู้ดูแลระบบ** | นำเข้าตารางที่มี `รหัสนักศึกษา` + `ชื่อ-นามสกุล` | บัญชีนั้น**ล็อกอินได้** แต่ยังไม่เห็นวิชาใดเลย |
| 2 | **อาจารย์** | enroll นักศึกษาเข้า section ที่ตนสอน | นักศึกษา**เห็นวิชานั้น** และส่งงานได้ |

**ไฟล์นำเข้าไม่ต้องมีคอลัมน์อีเมล** เพราะอีเมลนักศึกษาของ สจล. มีรูปแบบคงที่คือ `<รหัสนักศึกษา>@kmitl.ac.th` ระบบสร้างอีเมลจากรหัสได้เอง แล้วใช้จับคู่กับสิ่งที่ Google ส่งกลับมา — *อาจารย์ผู้สอนใช้รูปแบบอีเมลคนละแบบ (`ชื่อ.นามสกุลย่อ@`) จึงต้องนำเข้าด้วยอีเมลตรง ๆ*

**กรณีล็อกอินสำเร็จแต่ไม่มีบัญชี → ปฏิเสธ** ผู้ดูแลระบบคุมประตูจริง โดยมีสามอย่างที่บังคับควบคู่กัน

1. ข้อความบนจอต้อง**บอกว่าให้ติดต่อใครและติดต่ออย่างไร** ไม่ใช่ "เกิดข้อผิดพลาด"
2. **บันทึกความพยายามที่ถูกปฏิเสธไว้** — รายการนี้คือรายชื่อนักศึกษาที่ตกหล่นจากการนำเข้า จึงเป็นฟีเจอร์ ไม่ใช่แค่ log ความปลอดภัย
3. หน้าผู้ดูแลระบบมีปุ่ม **"สร้างบัญชีจากรายการที่ถูกปฏิเสธ"** กดครั้งเดียวจบ

> **ความเสี่ยงที่ยังเหลือ** — ถ้าวันส่งงานผู้ดูแลระบบไม่ว่าง นักศึกษาที่ตกหล่นจะส่งงานไม่ได้ ผลคือคะแนนศูนย์ ไม่ใช่แค่ความไม่สะดวก **ต้องเขียนทางออกนอกระบบไว้ในประมวลรายวิชา** (ส่งทางอีเมลแล้วอาจารย์นำเข้าให้ทีหลัง)

## 4.3 บทบาทและสิทธิ์

**บทบาทสี่แบบตายตัว ไม่ใช่ระบบสิทธิ์ที่ตั้งค่าได้** — และ**บทบาทผูกกับการเปิดสอน ไม่ผูกกับคน** คนหนึ่งคนมีบัญชีเดียวเพราะมีอีเมลสถาบันเดียว แล้วในแต่ละ section ถือบทบาทอะไรก็ว่าไปตามนั้น ส่วนสิทธิ์ผู้ดูแลระบบเป็น**ธงแยกต่างหาก**ที่ไม่ผูกกับวิชาใด

รองรับกรณีจริงที่เกิดแน่: ผู้ช่วยสอนที่เป็นนักศึกษาปริญญาโท · อาจารย์ที่ไปลงเรียนวิชาอื่น · **อาจารย์ที่สวมบทบาทผู้ดูแลระบบเอง ซึ่งเป็นสิ่งที่จะเกิดในเทอมทดลอง**

**หนึ่ง section มีอาจารย์ได้หลายคน สิทธิ์เท่ากันทุกคน** ไม่มีแนวคิด "อาจารย์หลัก" เพราะการสอนร่วมเป็นเรื่องปกติ และการบังคับให้มีคนเดียวจะจบลงที่การใช้บัญชีร่วมกัน ซึ่งทำลาย audit log ทั้งระบบ

**มีปุ่มสลับบทบาทชัดเจน** พร้อมแถบบอกสถานะค้างไว้ตลอดว่าตอนนี้อยู่ในบทบาทใด สลับได้เฉพาะบทบาทที่ตัวเองถือจริง — ปุ่มนี้ไม่ใช่การเพิ่มสิทธิ์ เป็นการเลือกมุมมอง ข้อดีสองข้อ: **audit log อ่านแล้วเถียงไม่ได้** เพราะผู้ใช้เจตนาเข้าโหมดก่อนลงมือ และ**เมนูแต่ละโหมดสั้นลงมาก**

### 4.3.2 แถวที่สำคัญที่สุดในตาราง

**"ผู้ดูแลระบบดูไฟล์งานนักศึกษาไม่ได้"** — ข้อนี้บังคับที่ระดับบุคคลไม่ได้ เพราะอาจารย์สวมบทบาทผู้ดูแลระบบเอง จึงต้องบังคับที่ระดับหน้าจอแทน

> **หน้าจอฝั่งผู้ดูแลระบบไม่มีเส้นทางไปถึงไฟล์งานหรือคะแนนของนักศึกษาเลย** ถ้าคนคนเดียวกันอยากดูงาน ต้องสลับไปบทบาทอาจารย์แล้วเข้าทางวิชาที่ตนสอน ซึ่งเป็นสิทธิ์ที่มีอยู่แล้วโดยชอบ ไม่ได้มาจากการเป็นผู้ดูแลระบบ และ audit log บันทึกว่าเข้ามาในบทบาทใด

ประโยคนี้พูดความจริงและตรวจสอบได้ ต่างจากการเขียนว่า "ผู้ดูแลระบบไม่ควรเห็น" ซึ่งบังคับอะไรไม่ได้เลย

## 4.4 PDPA และการเก็บข้อมูล

### 4.4.1 ฐานทางกฎหมาย — ไม่ใช่ความยินยอม

**นักศึกษาปฏิเสธการถูกตรวจงานไม่ได้** ถ้าปฏิเสธแล้วไม่ได้คะแนน ความยินยอมนั้นก็ไม่ได้ให้โดยอิสระ จึงไม่ใช่ความยินยอมที่ใช้ได้ตาม PDPA ตั้งแต่ต้น การประเมินผลการเรียนเป็นภารกิจของสถาบันอุดมศึกษาอยู่แล้ว **ฐานที่ใช้จึงเป็นการปฏิบัติหน้าที่ของหน่วยงานรัฐ ไม่ใช่ความยินยอม**

จึงแยกเป็นสองก้อนที่มีธรรมชาติต่างกัน

| ก้อน | รูปแบบ | ปฏิเสธได้ไหม |
|---|---|---|
| **การตรวจงานและเก็บคะแนน** | ประกาศให้ทราบ | ไม่ได้ แต่ต้องได้รู้ |
| **การนำงานไปใช้ในชุดเทียบและงานวิจัย** | ขอความยินยอมจริง | **ได้ และถอนได้ทุกเมื่อ โดยไม่กระทบคะแนน** |

> **ติดป้าย** — ผู้เขียนไม่ใช่นักกฎหมาย การเลือกฐานตามมาตรา 24 และข้อความประกาศทั้งหมดเป็นร่างเพื่อถกกับทีม **ควรให้ผู้รับผิดชอบ PDPA ของ สจล. ยืนยันก่อนใช้จริง**

### 4.4.2 ช่องทางแจ้ง

| ช่องทาง | หน้าที่ |
|---|---|
| **Orientation รายวิชา** | สื่อสารจริง อธิบายได้ ถามตอบได้ |
| **หน้าจอตอนล็อกอินครั้งแรก** | **เก็บหลักฐาน** ว่าใครรับทราบ เมื่อไร ข้อความเวอร์ชันไหน |
| ประมวลรายวิชา | ข้อความเดียวกัน สำหรับคนที่ย้อนกลับมาอ่าน |

**หน้าจอไม่ได้ทำหน้าที่สื่อสาร** เพราะคนอ่านข้อความบนหน้าล็อกอินน้อยมาก — ยอมรับข้อนี้ตรง ๆ แล้วให้มันทำสิ่งที่มันทำได้ดีคือเก็บหลักฐานรายคนพร้อมเวลาและเวอร์ชัน

**กรอบคำพูดที่ต้องใช้ทุกที่:** *"อาจารย์เป็นผู้ให้คะแนนทุกชิ้น โดยมีเครื่องมือช่วยอ่านงานและร่างเหตุผลให้ก่อน"* — ไม่ใช่การเลี่ยงคำ แต่ตรงกับ `AI ตรวจ → อาจารย์ยืนยัน/แก้ → นักศึกษาเห็นคะแนน` ที่ออกแบบไว้ ประโยคที่ผิดและจะกระตุ้นการต่อต้านคือ *"AI ให้คะแนนคุณ"*

### 4.4.3 ร่างข้อความ — ประกาศเรื่องข้อมูลส่วนบุคคล

> ยกไปใช้ได้ทั้งบนหน้าจอ ในสไลด์ orientation และในประมวลรายวิชา · ช่องในวงเล็บเหลี่ยมต้องเติมก่อนใช้จริง · **ยังไม่ผ่านการตรวจทางกฎหมาย**

---

**ประกาศเรื่องข้อมูลส่วนบุคคล — ระบบช่วยตรวจงาน [ชื่อวิชา]**

**อาจารย์เป็นผู้ให้คะแนนทุกชิ้น** วิชานี้ใช้ระบบที่มีเครื่องมือช่วยอ่านงานและร่างเหตุผลของคะแนนเสนอให้อาจารย์ก่อน อาจารย์เป็นผู้ยืนยันหรือแก้ทุกคะแนนก่อนประกาศ **คะแนนที่นักศึกษาเห็นคือคะแนนที่อาจารย์ตัดสินแล้วเสมอ**

**ข้อมูลที่เก็บ** ชื่อ-นามสกุล รหัสนักศึกษา อีเมลของสถาบัน ไฟล์งานที่ส่ง คะแนน เหตุผลของคะแนน และบันทึกการแก้คะแนน

**เก็บไปทำอะไร** ประเมินผลการเรียนตามเกณฑ์ที่ประกาศไว้ในประมวลรายวิชา และจัดทำหลักฐานประกอบการประกันคุณภาพหลักสูตร

**ประมวลผลที่ไหน** ไฟล์งานถูกประมวลผลบนเครื่องคอมพิวเตอร์ภายในคณะเท่านั้น **ไม่ถูกส่งออกไปยังผู้ให้บริการภายนอก** และก่อนส่งเข้าเครื่องมือช่วยอ่าน ระบบจะถอดชื่อ รหัสนักศึกษา อีเมล และชื่อไฟล์เดิมออกทั้งหมด เครื่องมือจะเห็นงานเป็นรหัสที่ไม่ระบุตัวตน

**ข้อจำกัดที่ต้องแจ้งให้ทราบ** หากในตัวงานมีชื่อผู้จัดทำปรากฏอยู่ เช่น บนหน้าปกหรือมุมของหน้าจอออกแบบ ระบบไม่สามารถถอดออกได้ ระบบถอดได้เฉพาะข้อมูลที่ระบบเก็บไว้เท่านั้น

**เก็บนานเท่าไร** ไฟล์งานและคะแนนเก็บไว้ **5 ปีการศึกษา** นับจากวันปิดรายวิชา หลังพ้นกำหนดระบบจะลบไฟล์งาน และเก็บไว้เฉพาะคะแนนกับผลการบรรลุผลลัพธ์การเรียนรู้ในรูปแบบที่ไม่ระบุตัวบุคคล

**สิทธิ์ของนักศึกษา**

- ขอดูข้อมูลของตนเองที่ระบบเก็บไว้ได้

### 4.4.5 กฎถอดตัวตนก่อนเข้าชั้น LLM

**ถอดทุกกรณี ไม่มีข้อยกเว้น ไม่มีสวิตช์ปิด** — ชื่อ-นามสกุล · รหัสนักศึกษา · อีเมล · ชื่อไฟล์เดิม · ชื่อกลุ่มที่ตั้งเอง · metadata เจ้าของไฟล์ใน Figma และ PDF (`Author`, `Creator`, `last_modified_by`) · EXIF ของรูป

**แทนด้วยรหัสทึบที่สุ่มขึ้น** เช่น `sub_8f3a1c` — **ห้าม derive จากรหัสนักศึกษาแม้จะผ่าน hash** เพราะ hash ที่คงที่ทำให้เชื่อมโยงงานของคนเดียวกันข้ามครั้งได้ ซึ่งเป็นการระบุตัวตนโดยพฤตินัย

**บังคับที่ตัวสร้าง prompt ไม่ใช่ที่หน้าจอ** และต้องมี**การทดสอบอัตโนมัติที่ยืนยันว่า prompt ที่ออกไปไม่มีสตริงเหล่านี้ปนอยู่** เพราะเป็นกฎที่พังเงียบ ๆ ได้ง่ายมากเมื่อมีคนเพิ่มฟีเจอร์แล้วเผลอส่ง object เต็ม ๆ เข้าไป

เหตุผลมีสองชั้น และ**ชั้นที่สองสำคัญกว่า**: ชั้นแรกคือลดพื้นที่เสี่ยงตาม PDPA ชั้นที่สองคือ**ตัดอคติจากตัวตน** — โมเดลที่มองไม่เห็นชื่อ ลำเอียงตามเพศ เชื้อชาติ หรือชื่อเสียงของนักศึกษาไม่ได้ ซึ่งเป็นสิ่งที่การตรวจด้วยมือทำไม่ได้ และเป็นข้ออ้างที่แข็งกว่ามากเวลาต้องตอบว่าทำไมถึงเชื่อผลของระบบ

> **ข้อจำกัดที่ห้ามกลบ** — ถ้าชื่อผู้จัดทำอยู่ในพิกเซลของงานเอง (หน้าปก slide มุมล่างของ frame ลายเซ็นใน persona) ระบบถอดออกไม่ได้ นโยบายจึงพูดได้แค่ว่า **"ไม่ส่งข้อมูลระบุตัวตนที่ระบบถืออยู่"** ไม่ใช่ "โมเดลไม่มีทางรู้ว่าใครทำ"

### 4.4.6 งานนักศึกษาไม่ออกนอกคณะ

**ไฟล์งานของนักศึกษาในรายวิชา ไม่ถูกส่งออกนอกเครือข่ายของคณะเลย ไม่มีเงื่อนไข** — ทำได้เพราะการตรวจจริงและการทดลองซ้ำทั้งหมดรันบนโมเดลเปิดที่เครื่อง GPU ในคณะอยู่แล้ว (§3) ส่วน API แบบเสียเงินเป็นเพียงจุดเทียบระดับบนในบทวิจัย

**จุดเทียบทำด้วยชุดตัวอย่างแยกต่างหาก**ที่ขออนุญาตเป็นรายชิ้น — งานของเทอมก่อนที่เจ้าของยินยอม หรืองานที่ทีมทำขึ้นเอง

ทางเลือก "ขอความยินยอมรายคนแล้วส่งเฉพาะคนที่ยอม" ถูกปฏิเสธด้วยสามเหตุผล: **ประโยคที่ไม่มีเงื่อนไขมีค่ามหาศาล**ในหน้าประกาศและตอนตอบกรรมการ · มัน**สร้างนักศึกษาสองชั้นในวิชาเดียวกัน** เพราะคนที่ไม่ยินยอมจะถูกตรวจด้วยโมเดลคนละตัวกับเพื่อน · และมัน**ทำลายการเปรียบเทียบเอง**ด้วย selection bias

> **ราคาที่ยอมจ่าย ต้องเขียนเป็นข้อจำกัดในบทวิจัย** — ชุดเทียบจะเล็กและอาจไม่สะท้อนงานจริงของเทอมนั้น
> **ยังไม่ได้ทำ** — ตรวจสอบว่าผู้ให้บริการ API ที่ใช้ทำจุดเทียบ นำข้อมูลไปฝึกโมเดลหรือไม่ ต้องอ้างนโยบายฉบับจริงพร้อมวันที่

# 5. Data model

## 5.1 หลักการ

**หน่วยที่เล็กที่สุดที่ระบบเก็บคือ `CriterionScore`** = การตรวจหนึ่งครั้ง × หัวข้อประเมินหนึ่งข้อ

ทุกตัวเลขที่เหลือในระบบ — คะแนนชิ้นงาน คะแนนสุทธิ CLO attainment เกรด — **คำนวณขึ้นมาจากตรงนี้ ไม่เก็บเป็นค่านิ่ง**

**ทางเลือกที่ไม่เอา:** เก็บคะแนนรวมของชิ้นงานเป็นตัวเลขเดียว

**เหตุผลที่ไม่เอา:** ถ้าเก็บแบบนั้น จะตอบคำถามของ TABEE 1.7 ไม่ได้เลยว่าคะแนนนี้มาจากไหน และจะคำนวณ CLO attainment ไม่ได้เพราะ CLO ผูกที่ระดับหัวข้อประเมิน

# 6. สถาปัตยกรรมและ tech stack

## 6.1 TypeScript ทั้งระบบ

**ตัดสิน:** ระบบทั้งหมดเขียนด้วย TypeScript · Python ใช้ได้เฉพาะ**สคริปต์วิจัย**ที่กินข้อมูลจากไฟล์ JSONL ที่ export ไว้ **ห้ามแตะฐานข้อมูลตรง**

**ทางเลือกที่ไม่เอา:** เว็บเป็น TypeScript + ชั้นตรวจเป็น Python (ซึ่งเป็นรูปที่คนทำงาน ML คุ้นที่สุด)

**เหตุผลที่ไม่เอา:** ทีมมี 2–3 คนและมีเวลา 1 ปี การมีสองภาษาแปลว่ามีสอง toolchain สอง deployment สองชุด type ที่ต้องซิงก์กันเอง ต้นทุนนั้นสูงกว่าประโยชน์ที่ได้ เพราะงานที่ต้องใช้ Python จริง ๆ (ไลบรารีสถิติ) เป็นงานวิเคราะห์ ไม่ใช่งานที่รันในระบบ

**ผลข้างเคียงที่เป็นข้อดี:** สคริปต์วิจัยกินข้อมูลจาก JSONL ที่ export และ**ติดเวอร์ชันไว้** แปลว่าผลการวิเคราะห์ทำซ้ำได้จริง ต่างจากการ query ฐานข้อมูลสดซึ่งข้อมูลเปลี่ยนไปแล้ว

## 6.2 สองเครื่อง

```
┌─────────────────────────────┐        ┌──────────────────────┐
│  VM (4–8 core / 16 GB)      │        │  GPU box             │
│                             │        │                      │
│  Next.js (หน้าเว็บ + API)   │  HTTP  │  vLLM                │
│  PostgreSQL                 │ ─────▶ │  endpoint แบบ        │
│  คิว = ตารางใน Postgres     │ ภายใน  │  OpenAI-compatible   │
│  worker (TypeScript)        │        │  RTX 5090 32 GB      │
│  ดิสก์แยก 500 GB            │        │                      │
└─────────────────────────────┘        └──────────────────────┘
```

**เหตุผลที่คิวเป็นตารางใน Postgres ไม่ใช่ Redis/RabbitMQ:** ปริมาณงานของระบบนี้คือ **~100 งานต่อการกดสั่งตรวจหนึ่งครั้ง สัปดาห์ละไม่กี่ครั้ง** การเพิ่มบริการอีกตัวเข้ามาดูแลไม่คุ้ม และ Postgres ทำได้ดีพอที่ปริมาณนี้ · **ถ้าทีมอยากเถียงข้อนี้ นี่เป็นข้อที่เถียงได้**

**เหตุผลที่ GPU box รัน vLLM อย่างเดียว:** ให้ขอบเขตความรับผิดชอบชัด — เครื่องนั้นเป็นบริการอนุมานล้วน ไม่มี state ไม่มีฐานข้อมูล พังแล้วเปิดใหม่ได้โดยไม่กระทบข้อมูล

```
┌─ ชั้นที่ 1: ตัวอ่านไฟล์ (Figma API / PDF) ─────────────┐
```

**ชั้นกฎคือตัวประกันของโครงงาน** — มันไม่พึ่งความแม่นของ LLM เลย ถ้าชั้น LLM ให้คะแนนไม่แม่นพอ ระบบที่เหลือ (ชั้นกฎ + สมุดคะแนน + CLO attainment + การสืบย้อน) **ยังเป็นระบบที่ใช้งานได้จริงและมีคุณค่าต่อรายวิชา** ทีมควรรู้ข้อนี้ตั้งแต่วันแรก

## 6.4 โมเดล

- ต้องเป็น **vision-language model ไม่ใช่ LLM ข้อความล้วน** เพราะงาน UX/UI ที่ต้องตัดสินเป็นภาพ
- 32 GB ต่อการ์ดรัน VLM ระดับ **27–32B แบบ 4-bit** ได้ — **ต้อง spike ยืนยันก่อนล็อกสถาปัตยกรรม**
- **ความเสี่ยง: RTX 5090 เป็นสถาปัตยกรรม Blackwell ซึ่งใหม่** CUDA / PyTorch / ไลบรารี serving ต้องเวอร์ชันใหม่พอ **ห้ามสมมติว่ารันได้**
- **ค่า LLM API อาจารย์ออกเอง เงื่อนไข "ไม่มาก ไม่ประจำ"** จึงเป็น**ข้อจำกัดออกแบบ**: งานที่ทำซ้ำทุกสัปดาห์ (ตรวจจริง) และงานที่รันซ้ำเยอะ (ทดลอง baseline) **ต้องอยู่บนโมเดลเปิดที่ 5090** ส่วน API เก็บไว้เป็น**จุดอ้างอิงระดับบนสุด**ซึ่งรันไม่บ่อย
- ระบบต้องมี **ตัวนับต้นทุนต่อ call + เพดานงบที่หยุดเรียก API เองเมื่อชน**

# 7. กฎทางธุรกิจและกรณีขอบ

## 7.1 การให้คะแนน

### ลำดับการคำนวณ

```
ขั้น 0  ประตูก่อนถึง AI   ไม่ส่ง = 0 · ส่งช้าเกิน 3 วัน = 0  → จบ ไม่เรียก AI เลย
ขั้น 1  คะแนนตาม rubric   (คะแนนกลุ่ม)
ขั้น 2  + การปรับรายบุคคล  (บังคับเหตุผล)
ขั้น 3  − ค่าปรับส่งช้า    10% ของคะแนนเต็มต่อวัน นับจากเวลาของครั้งที่ถูกใช้ตรวจ
ขั้น 4  พื้น              ถ้าผลรวม ≤ 0 → 1 คะแนน
```

> **หมายเหตุตามตรง:** สามชั้นที่บวกลบกัน (ขั้น 1–3) สลับลำดับกันได้ผลเท่ากัน **สิ่งเดียวที่ต้องล็อกจริง ๆ คือพื้นที่อยู่ล่างสุด** ไม่งั้นคนที่อยู่ที่พื้นแล้วได้คะแนนพิเศษจากดุลพินิจ จะจบสูงกว่าคนที่ส่งตรงเวลาและทำงานเท่ากัน

**หน้าจอต้องแสดงครบทั้งสี่บรรทัด ไม่ใช่แสดงแต่ผลลัพธ์**

### ไม่มีช่องกรอก "คะแนนสุดท้าย" ที่ไหนในระบบ

ดุลพินิจของอาจารย์แสดงออกได้**สองที่เท่านั้น**:
1. เปลี่ยนระดับที่ AI เสนอ ภายในหัวข้อประเมินหนึ่ง ๆ
2. **รายการปรับคะแนน** (เครื่องหมาย + จำนวน + เหตุผลบังคับ)

ทั้งสองแบบเป็นการ**วางทับ ไม่ใช่เขียนทับ**

**เหตุผล:** ถ้ามีช่องคะแนนสุดท้าย ทุกชั้นที่ออกแบบไว้จะถูกข้ามด้วยการพิมพ์ตัวเลขทับ และคำถาม "คะแนนนี้มาจากไหน" จะตอบไม่ได้**พอดีในกรณีที่สำคัญที่สุด — คือตอนที่อาจารย์ไม่เห็นด้วยกับระบบ**

### เกณฑ์ชนิด `human_only`

แสดงบนหน้าจอว่า *"ข้อนี้ระบบไม่ให้คะแนน"* · **ยังนับเข้าคะแนนเต็ม** · **แต่ตัดออกจากการคำนวณ agreement**

### จุดตัดเกรด

ระบบ**เสนอ**จุดตัดได้ อาจารย์ต้องยืนยัน · **ระบบตัดเกรดเองไม่ได้** · `GradeSnapshot` แช่แข็ง**ตอนยืนยัน ไม่ใช่ตอนคำนวณ**

## 7.2 การส่งงาน

| กรณี | ระบบทำอะไร |
|---|---|
| ส่งใหม่หลังเลยกำหนด | **ทำได้เสมอ** แลกกับคะแนน — ค่าปรับคิดจากเวลาของ**ครั้งที่ถูกใช้ตรวจ** |
| อาจารย์กด "สั่งตรวจทั้งชุด" | **ปิดรับการส่งของทั้งกิจกรรม** ในทรานแซกชันเดียวกับการ enqueue |
| ส่งใหม่แล้วคะแนนที่มีอยู่จะกลายเป็น 0 | **ระบบปฏิเสธ ไม่ใช่แค่เตือน** |
| ดึง Figma ไม่สำเร็จ | ขึ้นว่า **"ส่งสำเร็จแล้ว"** ก่อนเสมอ แล้วค่อยบอกสิ่งที่ต้องไปทำ |
| ส่งช้าเกิน 3 วัน | คะแนน 0 · **ไม่เรียก AI เลย** |
| ไม่ส่ง | คะแนน 0 |

**เหตุผลที่ปิดรับตอนกดสั่งตรวจ:** ค่าปรับส่งสายปกป้อง**ความยุติธรรมระหว่างนักศึกษา** แต่ไม่ปกป้อง**เวลาของอาจารย์** ถ้าไม่ปิด งานจะไหลเข้ามาระหว่างที่ตรวจอยู่ และงานที่ตรวจไปแล้วจะไม่ตรงกับหลักฐานล่าสุด

**ต้องมีทางเปิดใหม่รายคน** สำหรับกรณีมีเหตุผลจริง (ป่วย เอกสารรับรอง)

## 7.3 การตรวจ

- **AI ไม่ตรวจอะไรเลยจนกว่าจะครบสองเงื่อนไข: หมดเวลาส่ง + อาจารย์กดสั่ง**
  → กันการใช้ AI เป็นเครื่องลองคะแนน และทำให้ทั้งชั้นถูกตรวจด้วยเงื่อนไขเดียวกันจนเทียบกันได้
- **8 สถานะ ข้ามไม่ได้** คะแนน AI ไม่มีทางถึงมือนักศึกษาโดยตรง
- **ยืนยันยกชั้นได้ แต่ระบบบังคับเปิดดู "งานกลุ่มเสี่ยง" ก่อน** 6 เงื่อนไข: ตรวจไม่ได้ / มีเกณฑ์ `human_only` / ใกล้เส้นเกรด / อยู่ในกลุ่ม blind / คะแนนสุดขั้ว / ผิดปกติเทียบกับตัวเอง — **ปรับตัวเลขเงื่อนไขได้ แต่ปิดไม่ได้**
- **AI ตรวจไม่ได้ ห้ามให้ 0** → เข้าคิวรออาจารย์ · และเกณฑ์ข้ออื่นที่ตรวจสำเร็จต้องยังอยู่
- **ไม่เก็บค่าความมั่นใจที่ LLM รายงานเอง** — แสดงผลรันซ้ำ 3 ครั้งแทน เพราะค่าความมั่นใจที่โมเดลบอกเองไม่สัมพันธ์กับความถูกต้องจริง
- **ประกาศคะแนนทีละชิ้นงาน ทั้งชั้นพร้อมกัน**
- **AI เข้าใจเกณฑ์ผิดทั้งชั้น** → แก้คำบรรยาย → RubricVersion ใหม่ → **ตรวจใหม่เฉพาะเกณฑ์นั้น** เกณฑ์อื่นยกผลเดิมมาพร้อมธง

## 7.4 นักศึกษาเห็นอะไร

| เห็น | ไม่เห็น |
|---|---|
| คะแนนสุดท้ายรายหัวข้อประเมิน | **คะแนนที่ AI ให้** |
| เหตุผลของคะแนน | คะแนนของเพื่อนที่ไม่ได้อยู่กลุ่มเดียวกัน |
| ป้ายว่าผ่านตาผู้สอนแล้วหรือยัง | ค่า agreement ของระบบ |
| rubric เต็มทุกเกณฑ์ทุกระดับ **ตั้งแต่ก่อนส่ง** | ตัวเลข CLO ของชั้น |
| คะแนนกลุ่มที่ตนอยู่ร่วมกัน | คะแนนสุทธิของเพื่อนร่วมกลุ่ม |
| กราฟ CLO ของตนเอง | |
| **ชื่อผู้ตรวจของงานชิ้นนั้น** | |

**"นักศึกษาไม่เห็นคะแนน AI" คือการปิดจากสายตา ไม่ใช่การไม่บันทึก** — ข้อมูลยังอยู่ครบในฐานข้อมูลเสมอ

**ไม่มีปุ่มทักท้วงในระบบ** จึงต้องเขียนเวลาและสถานที่จริงที่นักศึกษาไปคุยกับอาจารย์ได้ไว้แทน

## 7.5 งานกลุ่ม

- **นักศึกษาสร้างกลุ่มเองตอนกดส่ง** อาจารย์แก้ได้ · สมาชิกคนอื่นเห็นทันทีว่าถูกเพิ่มโดยใคร
- คะแนนสองชั้น: **คะแนนกลุ่ม + การปรับรายบุคคลที่บังคับเหตุผล**
- เพื่อนเห็น**คะแนนกลุ่มร่วมกัน** แต่เห็น**คะแนนสุทธิเฉพาะของตัวเอง**
- **ไม่ทำ peer evaluation ใน MVP**

## 7.6 สองชั้นของคำอธิบาย

| ชั้น | ใครเห็น | เปลี่ยนแล้วเกิดอะไร |
|---|---|---|
| **rubric ทางการ** | นักศึกษาเห็นตั้งแต่ได้รับโจทย์ | เปลี่ยน = RubricVersion ใหม่ |
| **คำอธิบายชั้น AI (`JudgePromptVersion`)** | **ไม่ประกาศอัตโนมัติ แต่นักศึกษาขอดูได้เสมอ** | เปลี่ยนได้โดยไม่ขึ้นเวอร์ชัน rubric |

**เส้นแบ่งตัดสินด้วยคำถามเดียว:** *"ถ้านักศึกษาอ่านข้อความนี้ตอนทำงาน เขาจะทำงานต่างไปไหม"* — ถ้าต่าง แปลว่ามันคือ rubric ต้องขึ้นเวอร์ชันใหม่

**ผลพลอยได้ที่สำคัญ:** เพราะอาจถูกขอดูได้ตลอด **คำอธิบายชั้น AI จึงต้องเขียนเป็นภาษาที่คนอ่านรู้เรื่อง ห้ามเป็น prompt hack** ซึ่งกันการจูนให้เดาถูกโดยไม่เข้าใจไปในตัว
