# 0. วิธีอ่านและสถานะของงานออกแบบ

## 0.1 มีอะไรให้ดูบ้าง

ต้นแบบเป็น HTML ที่เปิดในเบราว์เซอร์ได้เลย ไม่ต้องติดตั้งอะไร อยู่ที่ `prototypes/`

| โฟลเดอร์ | เนื้อหา | วิธีเปิด |
|---|---|---|
| `prototypes/instructor/` | หน้าจอฝั่งอาจารย์ 11 หน้า | เปิด `index.html` |
| `prototypes/grading/` | หน้าจอตรวจงาน 3 แบบ | `index.html?variant=A` / `B` / `C` |
| `prototypes/student/` | หน้าจอฝั่งนักศึกษา 6 หน้า | เปิด `index.html` |
| `prototypes/calibration/` | ระบบทดสอบ rubric 6 หน้า | `index.html?v=setup` / `summary` / `criterion` / `proposal` / `history` / `terms` · หรือกดลูกศรซ้าย-ขวา |

ทั้งสี่ชุดใช้ระบบสี ตัวอักษร และระยะห่างชุดเดียวกัน และรองรับทั้งธีมสว่างและมืด

## 0.2 ระดับความน่าเชื่อถือของแต่ละส่วน

**ข้อนี้สำคัญกว่าที่เห็น** — ต้นแบบไม่ได้มีน้ำหนักหลักฐานเท่ากันทุกหน้า

| ส่วน | ผ่านตาใครมาแล้ว | ระดับความมั่นใจ |
|---|---|---|
| หน้าจอตรวจงาน 3 แบบ | อาจารย์ผู้สอนเลือกแล้วว่าเอาแบบ A เป็นหลัก | **สูง** — ผู้ใช้จริงตัดสินเอง |
| แดชบอร์ดความสอดคล้อง | ออกแบบจากคำถามที่อาจารย์ถามจริง | **กลาง** — ยังไม่มีข้อมูลจริงไหลผ่าน |
| หน้าจอตั้งค่าฝั่งอาจารย์ | อาจารย์เห็นและให้ความเห็นบางหน้า | **กลาง** |
| **หน้าจอฝั่งนักศึกษาทั้งหมด** | **ยังไม่มีนักศึกษาผู้เรียนคนไหนเคยเห็น** | **⚠ ต่ำ** |

> **⚠ คำเตือนที่ต้องอยู่ในรายงาน:** หน้าจอฝั่งนักศึกษาทั้ง 6 หน้าออกแบบจากการอนุมานว่าผู้เรียนต้องการอะไร ไม่ได้ออกแบบจากการสังเกตผู้เรียนจริง ทีมโครงงานรีวิวในฐานะ**คนสร้าง** ไม่ใช่ในฐานะ**ผู้ใช้** — การที่ทีมบอกว่า "เข้าใจง่ายดี" **ไม่ใช่หลักฐาน** อาจารย์ตัดสินแล้วว่าเดินหน้าไปก่อน แต่ข้อนี้ต้องเขียนไว้ในข้อจำกัดของงาน ไม่ใช่เงียบ

## 0.3 หลักการออกแบบห้าข้อ

1. **ทุกตัวเลขบอกที่มาของตัวเองได้** ไม่มีคะแนนไหนโผล่มาโดยไม่มีทางกดดูว่ามาจากไหน
2. **AI เสนอ คนตัดสิน และหน้าจอต้องทำให้รู้สึกแบบนั้น** — คะแนนที่ AI ให้แสดงเป็น *ข้อเสนอ* ที่ยังไม่ถูกยืนยัน ไม่ใช่ตัวเลขสำเร็จรูปที่รอกดผ่าน
3. **ไม่มีช่องกรอกคะแนนสุดท้ายที่ไหนเลย** ดุลพินิจต้องผ่านโครงสร้างที่บันทึกเหตุผลได้
4. **ความเร็วมาจากการไม่ต้องตัดสินใจซ้ำ ไม่ใช่จากการซ่อนข้อมูล**
5. **ภาษาไทยเป็นภาษาหลักบนหน้าจอ** ศัพท์อังกฤษใช้เฉพาะที่แปลแล้วเสียความหมาย (rubric, CLO, Figma)

# 1. เส้นทางผู้ใช้

## 1.1 อาจารย์ — รอบการทำงานหนึ่งชิ้นงาน

```
[ก่อนเปิดภาค]
ตั้งค่าการเปิดสอน → นำเข้ารายชื่อจาก Excel → กำหนด CLO
   → สร้างกิจกรรมการประเมิน → สร้าง rubric (หรือหยิบจากคลัง)

[ระหว่างภาค — วนซ้ำต่อชิ้นงาน]
เปิดคิวงานรอตรวจ → เห็นว่าครบกำหนดแล้ว
   → กด "สั่งตรวจทั้งชุด"  ←── จุดเดียวที่ AI เริ่มทำงาน
   → (ระบบปิดรับส่งงานของกิจกรรมนี้ทันที ในทรานแซกชันเดียวกัน)
   → รอ ~15 นาที ไปทำอย่างอื่น
   → กลับมา: "ตรวจเสร็จ 13 กลุ่ม · เสี่ยง 4 กลุ่ม"
   → เปิดห้องตรวจ (แบบ A) ทีละกลุ่ม
       ├ กลุ่มเสี่ยง — บังคับเปิดดู
       └ กลุ่มปกติ — ดูผ่าน ๆ แล้วยืนยัน
   → กด "ยืนยันที่เหลือทั้งหมด"  ←── ทำได้ต่อเมื่อเปิดดูกลุ่มเสี่ยงครบแล้ว
   → กด "ประกาศคะแนน"           ←── ทั้งชั้นพร้อมกัน

[ปลายภาค]
สมุดคะแนนรวม → กรอกคะแนนสอบด้วยมือ → ดู CLO attainment
   → เสนอจุดตัดเกรด → อาจารย์ยืนยัน → แช่แข็ง GradeSnapshot
   → คัดลอกสามคอลัมน์ไปวางใน Excel ของทะเบียน
```

## 1.2 นักศึกษา — รอบการทำงานหนึ่งชิ้นงาน

```
เข้าระบบ → หน้าแรก "ของที่ต้องส่ง" เรียงตามความใกล้เดดไลน์
   → เปิดชิ้นงาน → อ่านโจทย์ + อ่าน rubric เต็ม (ก่อนทำ ไม่ใช่หลังตรวจ)
   → (ถ้าเป็นงานกลุ่ม) สร้างกลุ่ม / เข้ากลุ่ม
   → วางลิงก์ Figma + แนบ PDF → กดส่ง
   → หน้ายืนยันหลังส่ง: "ส่งสำเร็จแล้ว" + สิ่งที่ต้องไปทำ (ถ้ามี)
   → รอ … (ไม่รู้ว่ามี AI อยู่ในระบบ)
   → อาจารย์ประกาศ → เห็นคะแนนรายหัวข้อ + เหตุผล + ชื่อผู้ตรวจ
   → ไม่พอใจ → ไปคุยกับอาจารย์ตามเวลาที่ระบุบนหน้าจอ (ไม่มีปุ่มทักท้วงในระบบ)
```

## 1.3 จุดที่สองเส้นทางแตะกัน

มีจุดเดียว: **การประกาศคะแนน** ทุกอย่างระหว่างการกดส่งกับการประกาศเป็นกล่องดำสำหรับนักศึกษาโดยเจตนา — ดู §5.3

# 2. หน้าจอฝั่งอาจารย์

## 2.1 รายวิชาทั้งหมด · ตั้งค่ารายวิชา `MVP`

หน้าแรกหลังเข้าระบบ แสดงการเปิดสอนที่ตนสอนเรียงตามภาคการศึกษาใหม่ไปเก่า แต่ละใบมีตัวเลขที่บอกสถานะจริง: จำนวนงานที่รอตรวจ จำนวนที่ประกาศแล้ว

**การตัดสินที่ควรถกกัน:** เราแยก "รายวิชา" กับ "การเปิดสอน" ในฐานข้อมูล แต่บนหน้าจอนี้แสดงเป็นใบเดียวที่เขียนว่า "UX/UI Design — ภาค 1/2569" **ทางเลือกที่ไม่เอาคือให้ผู้ใช้เข้ารายวิชาก่อนแล้วค่อยเลือกภาค** ซึ่งตรงกับฐานข้อมูลมากกว่า แต่เพิ่มการคลิกหนึ่งครั้งทุกครั้งโดยไม่ได้อะไรกลับมา เพราะอาจารย์คิดเป็น "วิชาที่สอนเทอมนี้" ไม่ได้คิดเป็น "แม่แบบในหลักสูตร"

## 2.2 นักศึกษา — นำเข้าจาก Excel `MVP`

ลากไฟล์ลงมา → ระบบแสดง**ตารางพรีวิวก่อนยืนยัน** พร้อมสามกลุ่มที่แยกสีกัน: จะเพิ่มใหม่ / มีอยู่แล้ว / **หายไปจากไฟล์แต่มีอยู่ในระบบ**

**กฎที่ฝังอยู่ในหน้าจอนี้: ระบบไม่ถอนใครออกให้เอง** กลุ่มที่สามแสดงเป็นคำเตือนพร้อมข้อความว่า "ถ้าคนเหล่านี้ถอนรายวิชาแล้ว กรุณาเปลี่ยนสถานะทีละคน"

**เหตุผล:** บางคนถอนแล้วจริง แต่บางคนแค่หายไปจากไฟล์ที่อาจารย์ export มาผิดช่วง และ**บางคนมีคะแนนไปแล้ว** การถอนอัตโนมัติจึงเป็นการทำลายข้อมูลจากไฟล์ที่ระบบไม่มีทางรู้ว่าถูกต้องหรือเปล่า

## 2.3 CLO `MVP`

รายการ CLO พร้อมช่องเขียนคำบรรยาย และ**คอลัมน์ขวาที่แสดงว่า CLO ข้อนี้ถูกวัดด้วยหัวข้อประเมินกี่ข้อ รวมน้ำหนักเท่าไร**

คอลัมน์ขวานี้คือหัวใจของหน้า — มันจับ**ข้อผิดพลาดที่พบบ่อยที่สุดในการทำ outcome-based** คือ CLO ที่เขียนไว้สวยแต่ไม่มีอะไรวัดมันเลย ระบบขึ้นเตือนสีส้มทันทีที่ CLO ข้อไหนมีน้ำหนักรวมเป็นศูนย์

## 2.4 ตั้งค่ากิจกรรมการประเมิน `MVP`

สวิตช์ตัวแรกของหน้าคือ **"กิจกรรมนี้มีไฟล์ให้ส่งไหม"** ปิดสวิตช์แล้วหน้าจอเปลี่ยนเป็นแบบสอบ: ไม่มีช่องกำหนดส่ง ไม่มี rubric เหลือแค่ชื่อ คะแนนเต็ม การผูก CLO และ**ตารางกรอกคะแนนด้วยมือ**

**นี่คือสวิตช์ที่ทำให้ CLO attainment เป็นตัวเลขของทั้งวิชา ไม่ใช่ของครึ่งวิชา** ถ้าตัดออก หน้าที่ 2.8 จะกลายเป็นของประดับ

## 2.5 สร้าง rubric — สองโหมด `MVP`

| โหมด | ใช้เมื่อไร |
|---|---|
| **โหมดตาราง** | แก้ rubric ที่มีอยู่ · เห็นทุกช่องพร้อมกัน · ตรวจความเหลื่อมของคำบรรยายระหว่างระดับได้ |
| **โหมดทีละข้อ** | สร้างใหม่จากศูนย์ · โฟกัสทีละหัวข้อประเมิน · ลดโอกาสเขียนคำบรรยายลวก ๆ |

**ทั้งสองโหมดบังคับเหมือนกันข้อเดียว: คำบรรยายระดับคุณภาพต้องเขียนครบทุกช่อง** เพราะ**คำบรรยายนี้คือสิ่งที่ LLM ใช้ตัดสินจริง ๆ** ช่องว่างหนึ่งช่องแปลว่า AI ตัดสินระดับนั้นด้วยความว่างเปล่า

แต่ละหัวข้อประเมินมีป้ายชนิดกำกับ:

- 🔧 **`rule`** — ชั้นกฎให้คะแนนได้เอง (contrast, ความสม่ำเสมอของ spacing, การใช้ component)
- 🤖 **`llm`** — ต้องตีความ ใช้ชั้น LLM
- 👤 **`human_only`** — ระบบไม่ให้คะแนน · **ยังนับเข้าคะแนนเต็ม แต่ตัดออกจากการคำนวณ agreement**

**ทางเลือกที่ไม่เอา: ให้ระบบเดาชนิดเอง** ไม่เอาเพราะการเดาผิดจะทำให้ AI ไปให้คะแนนข้อที่ควรเป็นดุลพินิจของอาจารย์ล้วน โดยไม่มีใครรู้ตัว

## 2.6 คิวงานรอตรวจทั้งเทอม `MVP`

มุมมองเดียวที่ตอบว่า *"ตอนนี้ต้องทำอะไรบ้าง"* — เรียงตามความเร่งด่วน ไม่ใช่ตามสัปดาห์

แต่ละแถวมีปุ่มเดียวที่เด่นชัด: **"สั่งตรวจทั้งชุด"** ซึ่งขึ้น dialog เตือนว่า *"กดแล้วจะปิดรับการส่งงานของกิจกรรมนี้ทันที นักศึกษาที่ยังไม่ส่งจะส่งไม่ได้อีก"*

**ทำไมคำเตือนนี้ต้องแรง:** เพราะเป็นการกระทำที่ย้อนกลับได้ยากและกระทบนักศึกษาโดยตรง การเปิดใหม่ทำได้เป็นรายคนเท่านั้น (สำหรับกรณีป่วยหรือมีเหตุผลจริง)

## 2.7 หน้าจอตรวจงาน — สามแบบ `MVP: A เท่านั้น`

ทำสามแบบเพื่อให้อาจารย์เลือกจากของจริง ไม่ใช่จากคำบรรยาย **อาจารย์เลือกแบบ A**

### แบบ A — ห้องตรวจ `เลือกแล้ว`

```
┌───────────────────────────────┬──────────────────────────────┐
│                               │  หัวข้อประเมิน 1 / 7          │
│   งานของนักศึกษา              │  ลำดับชั้นการมองเห็น          │
│   (Figma / PDF)               │  ┌────────────────────────┐  │
│   เต็มพื้นที่ ซูมได้          │  │ AI เสนอ: ระดับ 3       │  │
│                               │  │ "หัวข้อหลักกับรอง       │  │
│   ● หมุดหลักฐานที่ AI ชี้     │  │  ต่างกันน้อยเกินไป..."  │  │
│                               │  │ 🔗 หลักฐาน: Frame 4    │  │
│                               │  └────────────────────────┘  │
│                               │  [1] [2] [◉3] [4]  ← เปลี่ยน │
│                               │  เหตุผลที่แก้: [_________]   │
└───────────────────────────────┴──────────────────────────────┘
```

**เหตุผลที่เลือก:** เป็นแบบเดียวที่ **"จบได้ในตัวเอง"** — เปิดกลุ่มหนึ่ง ตรวจครบ ปิด แล้วไปกลุ่มถัดไป โดยไม่ต้องจำอะไรข้ามหน้าจอ อาจารย์ให้เหตุผลว่างานตรวจจริงมักถูกขัดจังหวะ และแบบนี้กลับมาทำต่อได้โดยไม่ต้องตั้งหลักใหม่

**การกดที่หลักฐานต้องกระโดดไปที่ frame นั้นในงานจริง** — ไม่ใช่แค่แสดงชื่อ frame เป็นข้อความ

> **⚠ ความเสี่ยงที่ยังไม่ปิด:** ฟีเจอร์นี้ขึ้นกับว่า Figma API คืนพิกัดที่ปักหมุดได้จริงหรือเปล่า **ถ้าคืนไม่ได้ คุณค่าหลักของหน้านี้หายไปทั้งหน้า** ต้อง spike ยืนยันก่อนลงมือสร้างจริง — ดู เอกสารฉบับที่ 4 §2

### แบบ B — สายพาน `ไม่เอาใน MVP`

ตรวจทีละหัวข้อประเมินข้ามทุกกลุ่ม (ดูข้อ 1 ของทั้ง 13 กลุ่มติดกัน แล้วค่อยขยับไปข้อ 2)

**ข้อดีที่แท้จริง:** ให้คะแนนสม่ำเสมอกว่ามาก เพราะสมองอยู่ในบริบทเดียวตลอด และเห็นความต่างระหว่างกลุ่มได้ทันที

**เหตุผลที่ไม่เอาใน MVP:** ต้องตรวจครบทั้งชั้นถึงจะได้คะแนนของกลุ่มแรกครบหนึ่งกลุ่ม — ถูกขัดจังหวะแล้วค้างกลางทางเสมอ

### แบบ C — แผงควบคุม `ไม่เอาใน MVP`

ตารางทั้งชั้น × ทุกหัวข้อประเมินในจอเดียว เหมาะกับการกวาดตาหาความผิดปกติ ไม่เหมาะกับการตรวจจริง

### ปลายทางที่ตั้งใจไว้

```
C (กวาดตาหาจุดผิดปกติ) → B (ตรวจข้อที่น่าสงสัยข้ามทุกกลุ่ม)
   → A (ลงลึกกลุ่มที่มีปัญหา) → C (ยืนยันภาพรวมอีกรอบ)
```

**MVP ทำ A อย่างเดียว** แล้วค่อยเติม C และ B ทีหลัง — เรียงตามความง่ายในการสร้าง ไม่ใช่ตามลำดับการใช้งาน

## 2.8 สมุดคะแนนรวม `MVP`

ตารางนักศึกษา × กิจกรรมการประเมินทั้งหมด (รวมสอบ) พร้อมแถบ CLO attainment ที่คำนวณสด

**ปุ่มคัดลอกสามคอลัมน์อยู่ตรงนี้** และมันคือฟีเจอร์ส่งออกตัวจริงของ MVP — **ไม่มีโหมดคัดลอกเฉพาะคะแนน**

**เหตุผลที่ไม่มี:** ถ้ามีปุ่มคัดลอกคะแนนอย่างเดียว วันหนึ่งจะมีคนวางเหลื่อมไปหนึ่งแถว แล้วคะแนนทั้งห้องจะไปอยู่ผิดคนโดยไม่มีอะไรเตือนเลย **ความผิดพลาดแบบเงียบที่ตรวจไม่พบคือความผิดพลาดที่แย่ที่สุด** การบังคับพารหัสและชื่อไปด้วยทำให้คนวางเห็นทันทีว่าชื่อไม่ตรงแถว

ตารางเรียงตาม**รหัสนักศึกษาจากน้อยไปมาก**เสมอ · ไม่มี merge cell · ไม่มีแถวว่าง · ไม่มีหัวตารางหลายชั้น

**ทิศทางเป็นทางเดียว: ระบบ → Excel** หน้าจอเขียนไว้ตรง ๆ ว่าถ้าแก้ใน Excel ต้องกลับมาแก้ในระบบด้วย ไม่งั้นจะมีสองความจริง

# 3. ระบบทดสอบ rubric และแดชบอร์ดความสอดคล้อง

หน้าจอกลุ่มนี้ไม่มีผลต่อคะแนนของนักศึกษาเลย แต่**เป็นที่ที่ผลการทดลองของรายงานโครงงานเกิดขึ้น**

## 3.1 แถบบนที่อยู่ทุกหน้า

```
🔒 ชุดทดสอบยังไม่เคยเปิด · เปิดได้ครั้งเดียว 31 มี.ค. 70
```

ไม่ใช่ของประดับ — เป็นการทำให้กฎที่สำคัญที่สุดของงานวิจัยมองเห็นได้ตลอดเวลา แทนที่จะอยู่แค่ในหัวของคนเขียนรายงาน

## 3.2 หน้าสรุปผลรอบทดสอบ `MVP`

### ตัวเลขพาดหัวจับคู่เสมอ

```
   ตรงกันพอดี            ตรงกันหรือห่างไม่เกิน 1 ระดับ
   62%                   94%
   เพดานมนุษย์ 71%       เพดานมนุษย์ 96%
```

**ทุกตัวเลขความสอดคล้องต้องมีเพดานมนุษย์อยู่ข้าง ๆ เสมอ ไม่ใช่อยู่ในเชิงอรรถ**

**เหตุผล:** 62% ลอย ๆ ไม่มีความหมาย มันแปลว่าอะไรก็ได้ตั้งแต่ "แย่มาก" ถึง "เกือบเท่าที่เป็นไปได้" ขึ้นกับว่าคนสองคนตรงกันเองแค่ไหน **เพดานมนุษย์คือตัวหารของทั้งวิทยานิพนธ์** — และ 62 จาก 71 เป็นเรื่องที่ต่างจาก 62 จาก 100 โดยสิ้นเชิง

### แผนภาพหลักคือ confusion matrix 4×4

```
              AI ให้
            1    2    3    4
        1  [10]  5    3    0
อาจารย์ 2   6  [33] 12    3
  ให้   3   2   15  [58] 13
        4   1    2   12  [21]
```

**ทางเลือกที่ไม่เอาสองแบบ:**

| ไม่เอา | เพราะ |
|---|---|
| แผนภาพกระจาย (scatter) | มีแค่ 4 ระดับ จุดทับกันหมดจนอ่านไม่ออก |
| แท่งคู่ (AI vs อาจารย์) | บอกว่าแต่ละฝ่ายให้คะแนนกระจายยังไง **แต่ไม่บอกว่าใครตรงกับใครในชิ้นเดียวกัน** ซึ่งเป็นคำถามทั้งหมดของเรื่องนี้ |

confusion matrix ตอบสามคำถามในภาพเดียว: ตรงกันแค่ไหน (แนวทแยง) · ผิดไปทางไหน (บนขวา = AI ให้สูงกว่า) · ผิดห่างแค่ไหน (ระยะจากแนวทแยง)

**กดช่องไหนก็ได้ → เห็นรายการงานในช่องนั้น** ทำให้ตัวเลขกลายเป็นงานจริงได้ทันที

### ประโยคที่แดชบอร์ดต้องพูดเอง

หน้าจอเขียนไว้ตรง ๆ ว่า:

> *"ในภาพรวม AI ให้สูงกว่า 36 ครั้ง ต่ำกว่า 38 ครั้ง — ดูเหมือนสมดุล **แต่ตัวเลขนี้กำลังปกปิดปัญหา** มีสามเกณฑ์ที่เอนไปคนละทางแรง ๆ แล้วหักล้างกันพอดีในผลรวม กรุณาดูรายเกณฑ์"*

**นี่คือการตัดสินใจออกแบบที่สำคัญที่สุดของหน้านี้** — ระบบไม่ควรหวังว่าจะมีคนสังเกตเห็นเอง เพราะตัวเลขรวมที่ดูดีคือสิ่งที่คนอยากเชื่อและจะหยุดอ่านตรงนั้น

## 3.3 หน้าเจาะรายเกณฑ์ `MVP`

แต่ละหัวข้อประเมินมีสองจุดบนเส้นเดียวกัน: **ค่าที่ AI ทำได้** และ **เพดานมนุษย์ของเกณฑ์นั้น** เรียงตาม**ความยาวของเส้น**

> **ความยาวของเส้นคือระยะที่ยังปรับปรุงได้จริง** ไม่ใช่ระยะจาก 100%

ตัวอย่างที่ต้นแบบใช้: C5 (การออกแบบ flow) QWK 0.31 เพดาน 0.61 — เส้นยาว 0.30 · C7 (ความสมบูรณ์ของการส่งมอบ) QWK 0.64 เพดาน 0.88 — เส้นยาว 0.24 **ทั้งที่ตัวเลขดิบของ C7 ดูดีกว่ามาก**

### คำเตือนสถิติที่หน้าจอต้องแสดงเอง

> *"n = 28 ต่อเกณฑ์ → ช่วงความเชื่อมั่นราว ±0.18 · **C1 (0.71) กับ C7 (0.64) แยกจากกันไม่ได้ทางสถิติ** การไล่แก้เกณฑ์จากล่างขึ้นบนตามอันดับคือการไล่ตามสัญญาณรบกวน"*

**ถ้าไม่แสดงข้อนี้ หน้าจอนี้จะกลายเป็นเครื่องผลิตงานที่ไร้ผล** — คนจะเห็นอันดับแล้วเชื่ออันดับ

### ทิศของความคลาดเคลื่อนเป็นตัวบอกว่าจะแก้ยังไง

| รูปแบบที่เห็น | แปลว่า | วิธีแก้ที่ได้ผล |
|---|---|---|
| เอนไปทางเดียวชัด (เช่น AI ให้สูงกว่าเกือบทุกครั้ง) | AI กับอาจารย์เข้าใจ "ระดับ 3" ไม่ตรงกัน | **แก้คำบรรยายระดับ** — ได้ผลจริง |
| กระจายสองทาง | ไม่ได้เข้าใจต่างกัน แต่**ตัดสินไม่คงเส้นคงวา** | แก้คำบรรยายไม่ช่วย ต้องเพิ่มตัวอย่างอ้างอิง หรือย้ายไปให้ชั้นกฎทำ |

**ผลที่ตามมาต่อฐานข้อมูล: ต้องเก็บ mean signed error ไม่ใช่เก็บแค่ MAE** เพราะ MAE ทิ้งเครื่องหมาย ซึ่งเป็นข้อมูลชิ้นเดียวที่บอกว่าจะแก้ยังไง

### แยก "ปัญหาของ rubric" ออกจาก "ปัญหาของการอ่านไฟล์"

ในรายการงานที่ไม่ตรงกันมากที่สุด 11 ชิ้น มี **3 ชิ้นที่ AI อ่านไฟล์ไม่ได้เลย** ระบบต้องติดป้ายแยกให้ เพราะสามชิ้นนั้น**ไม่มีการแก้คำบรรยายใดในโลกที่ช่วยได้** และแก้ถูกกว่ามาก (ไปดูว่าทำไม export ออกมาแล้วอ่านไม่ได้) ควรแก้ก่อน

## 3.4 หน้าเสนอการปรับปรุง rubric `ไม่เอาใน MVP`

ระบบเสนอการแก้คำบรรยายได้ **แต่แก้เองไม่ได้** อาจารย์ต้องกดรับ และระบบบันทึกทั้งที่รับและที่ไม่รับพร้อมเหตุผล

### สองอย่างที่หน้านี้บังคับแสดง

**1. ผลข้างเคียง** — *"รับข้อเสนอนี้: C5 ดีขึ้น +0.09 · **C4 แย่ลง −0.03**"* เพราะหัวข้อประเมินไม่ได้อิสระต่อกัน การรัดคำบรรยายของข้อหนึ่งมักดันงานก้ำกึ่งไปตกที่อีกข้อ

**2. ราคาที่ซ่อนอยู่** — *"รับข้อเสนอนี้ = สร้าง RubricVersion ใหม่ = ต้องตรวจ bridge set 18 ชิ้น ≈ 2.5 ชั่วโมงของอาจารย์"*

**เหตุผลที่ต้องแสดงราคา:** ถ้าไม่แสดง อาจารย์จะกดรับข้อเสนอเล็ก ๆ หลายครั้ง แล้วพบทีหลังว่าเทียบผลข้ามเวอร์ชันไม่ได้เลย

### การจำลองผลรันบนชุดไหน

**ชุด validation 24 ชิ้นที่กันไว้จาก dev — ไม่ใช่ชุด test**

> **นี่เป็นการแก้ข้อผิดพลาดในโจทย์ตั้งต้นของ ticket 22 เอง** โจทย์เขียนว่าให้จำลองบนชุด test ซึ่งละเมิดกฎ "ข้อมูลที่ใช้วัด ห้ามใช้ปรับปรุง" โดยตรง — ถ้าจำลองบนชุด test แล้วรับเฉพาะข้อเสนอที่ทำให้ดีขึ้น แปลว่าชุด test ถูกใช้ปรับจูนไปแล้ว และตัวเลขสุดท้ายของวิทยานิพนธ์จะเป็นตัวเลขที่สูงเกินจริงโดยไม่มีทางรู้ว่าเกินเท่าไร

## 3.5 หน้าประวัติการปรับ `MVP: เก็บข้อมูล · หน้าจอทีหลัง`

กราฟ QWK ตามเวลา มีหมุดทุกครั้งที่เปลี่ยน RubricVersion

**เส้นกลายเป็นเส้นประเมื่อไม่มี bridge set** — สื่อสารด้วยรูปว่าช่วงนั้นเทียบกันไม่ได้ แทนที่จะลากเส้นทึบต่อกันแล้วให้คนเข้าใจผิดว่าดีขึ้น

## 3.6 หน้าเทียบข้ามภาค `ไม่เอาใน MVP`

จะมีข้อมูลจริงต่อเมื่อมีสองภาคการศึกษา — ซึ่งเป็นไปได้เพราะวิชาเปิดสอนทุกภาค และเพราะมีการซ้อมใหญ่ปลายภาค 1/2569

# 4. หน้าจอฝั่งนักศึกษา

> **⚠ ทั้งหมวดนี้ยังไม่ผ่านสายตาผู้เรียนจริงสักคน** อ่านโดยถือว่าเป็นข้อเสนอ ไม่ใช่ข้อสรุป

## 4.1 หน้าแรก "ของที่ต้องส่ง" `MVP`

เรียงตามความใกล้เดดไลน์ ไม่ใช่ตามสัปดาห์ — ตอบคำถามที่นักศึกษาเข้ามาถามจริง ๆ คือ *"ตอนนี้ต้องทำอะไรก่อน"*

แต่ละใบบอกสถานะเป็นภาษาคน: "ยังไม่ส่ง · เหลือ 2 วัน" · "ส่งแล้ว · รอผล" · "ประกาศแล้ว · 24/30"

## 4.2 หน้าส่งงาน `MVP`

สามส่วน: อ่านโจทย์ · **อ่าน rubric เต็ม** · แนบงาน

**rubric ต้องเห็นครบทุกเกณฑ์ทุกระดับตั้งแต่ก่อนทำงาน ไม่ใช่หลังถูกตรวจ**

**เหตุผล:** ถ้า rubric คือสิ่งที่ตัดสินคะแนน การซ่อนไว้จนตรวจเสร็จคือการให้สอบโดยไม่บอกว่าสอบอะไร และมันขัดกับสิ่งที่วิชานี้สอนเองด้วย

**ทางเลือกที่ไม่เอา: แสดง rubric แบบย่อ** ไม่เอาเพราะคำบรรยายระดับคุณภาพคือสิ่งที่มีประโยชน์ที่สุด — ย่อแล้วเหลือแค่ชื่อเกณฑ์ ซึ่งบอกอะไรไม่ได้เลย

## 4.3 หน้าจัดกลุ่ม `MVP`

**นักศึกษาสร้างกลุ่มเองตอนกดส่ง ไม่มีระบบเชิญและตอบรับ** อาจารย์แก้ได้ และสมาชิกที่ถูกเพิ่มเห็นทันทีว่าใครเพิ่ม

**เหตุผลที่ไม่ทำระบบเชิญ:** ระบบเชิญ/ตอบรับมีสถานะเพิ่มมาสามแบบ (รอตอบ ปฏิเสธ หมดอายุ) ทุกสถานะต้องมีหน้าจอและกฎว่าจะเกิดอะไรถ้าเดดไลน์มาถึงตอนยังไม่ตอบ — **ต้นทุนสูงมากเทียบกับปัญหาที่แก้** ซึ่งคือ "ถูกใส่ชื่อในกลุ่มโดยไม่รู้ตัว" ที่แก้ได้ด้วยการแสดงให้เห็นว่าใครเพิ่ม

## 4.4 หน้าหลังกดส่ง `MVP`

**ข้อความแรกที่เห็นคือ "ส่งสำเร็จแล้ว" เสมอ** ต่อให้ระบบดึง Figma ไม่สำเร็จ

ถ้าดึงไม่ได้ ข้างล่างขึ้นกล่องแยกว่า *"ระบบยังเข้าถึงไฟล์ Figma ของคุณไม่ได้ — กรุณาเปิดสิทธิ์การดูให้ทุกคนที่มีลิงก์"* พร้อมปุ่มลองใหม่

**เหตุผลที่สำคัญมาก:** ความล้มเหลวในการดึงไฟล์เป็นปัญหาทางเทคนิคของระบบ **ไม่ใช่ความล้มเหลวในการส่งงาน** ถ้าหน้าจอขึ้นแดงว่า "ส่งไม่สำเร็จ" ตอนใกล้เดดไลน์ นักศึกษาจะกดส่งซ้ำหลายรอบ และสิ่งที่ควรเป็น bug ของเราจะกลายเป็นความเสียหายเรื่องคะแนนของเขา

## 4.5 หน้าผลการตรวจ `MVP`

| แสดง | ไม่แสดง |
|---|---|
| คะแนนรายหัวข้อประเมิน + เหตุผล | **คะแนนที่ AI ให้** |
| ระดับที่ได้ เทียบกับคำบรรยายทุกระดับ | ค่า agreement ของระบบ |
| **ชื่อผู้ตรวจของงานชิ้นนี้** | คะแนนของคนอื่น |
| ป้าย "ผ่านการตรวจสอบโดยผู้สอนแล้ว" | ตัวเลข CLO ของทั้งชั้น |

| การหักคะแนนส่งช้าแยกบรรทัด | |
| กราฟ CLO ของตนเอง | |

**บรรทัดที่ต้องมีท้ายหน้า:** *"ถ้าเห็นว่าคะแนนไม่ตรงกับงาน คุยกับอาจารย์ได้ที่ [เวลาและสถานที่จริง]"*

**ไม่มีปุ่มทักท้วงในระบบ** — เพราะปุ่มทักท้วงที่ไม่มีคนดูแลจริงแย่กว่าไม่มีปุ่ม มันสร้างความคาดหวังว่ามีกระบวนการ ทั้งที่ไม่มี

## 4.6 การหักคะแนนต้องแสดงครบทุกบรรทัด

```
คะแนนตาม rubric (กลุ่ม)        24 / 30
การปรับรายบุคคล                +2      "รับผิดชอบส่วน user research"
หักส่งช้า (1 วัน × 10%)         −3
─────────────────────────────────────
คะแนนสุทธิ                      23 / 30
```

**ไม่แสดงแค่ผลลัพธ์** เพราะเลข 23 ตัวเดียวตอบคำถาม "ทำไม" ไม่ได้ และคำถามนั้นคือคำถามเดียวที่นักศึกษาถามจริง

**พื้นอยู่ล่างสุดเสมอ** — ถ้าผลรวมออกมา ≤ 0 ให้ 1 คะแนน · ลำดับข้อนี้ล็อกไว้ ไม่งั้นคนที่อยู่ที่พื้นแล้วได้คะแนนพิเศษจากดุลพินิจจะจบสูงกว่าคนที่ส่งตรงเวลาและทำงานเท่ากัน

# 5. การตัดสินใจออกแบบที่ควรถกกันมากที่สุด

## 5.1 ไม่มีช่องกรอกคะแนนสุดท้ายที่ไหนเลย

ทุกหน้าจอที่เกี่ยวกับคะแนนถูกออกแบบให้**ไม่มีทาง**พิมพ์ตัวเลขสุดท้ายทับได้ ดุลพินิจแสดงออกได้สองทาง: เปลี่ยนระดับในหัวข้อประเมิน หรือเพิ่มรายการปรับคะแนนพร้อมเหตุผล

**นี่เป็นข้อจำกัดที่ผู้ใช้จะบ่นแน่นอน** เพราะบางครั้งอาจารย์รู้ว่าคะแนนควรเป็นเท่าไรและอยากพิมพ์ลงไปเลย

**เหตุผลที่ยังยืนยัน:** ถ้ามีช่องนั้น ทุกชั้นที่ออกแบบมาจะถูกข้ามด้วยการพิมพ์เลขทับ และคำถาม "คะแนนนี้มาจากไหน" จะตอบไม่ได้**พอดีในกรณีที่สำคัญที่สุด คือตอนที่อาจารย์ไม่เห็นด้วยกับระบบ** ซึ่งเป็นกรณีที่ TABEE 1.7 ต้องการคำตอบมากที่สุด

## 5.2 ยืนยันยกชั้นได้ แต่บังคับเปิดดูของเสี่ยงก่อน

ปุ่ม "ยืนยันที่เหลือทั้งหมด" **มีอยู่จริงและใช้ได้** แต่ระบบจะไม่ให้กดจนกว่าจะเปิดดูงานที่เข้าเงื่อนไขเสี่ยงครบทั้ง 6 ข้อ

**ทางเลือกที่ไม่เอาสองแบบ**

| ไม่เอา | เพราะ |
|---|---|
| บังคับเปิดดูทุกงาน | อาจารย์จะเลิกใช้ระบบ ประโยชน์ด้านเวลาหายไปทั้งหมด |
| ยืนยันยกชั้นได้เลย | คะแนน AI จะถึงมือนักศึกษาโดยไม่มีใครดู ซึ่งขัดกับข้อ "คนตัดสิน" ที่เป็นข้อต่อรองไม่ได้ |

**ปรับตัวเลขของเงื่อนไขเสี่ยงได้ แต่ปิดกลไกไม่ได้**

## 5.3 นักศึกษาไม่รู้ว่ามี AI อยู่ในระบบ

หน้าจอฝั่งนักศึกษาไม่พูดถึง AI เลย มีแค่ "ผู้ตรวจ: อ.ธนา" และป้าย "ผ่านการตรวจสอบโดยผู้สอนแล้ว"

**ข้อดี:** ตรงกับความจริง — คะแนนที่ประกาศคืออาจารย์ตัดสิน · ไม่เปิดช่องให้โต้แย้งกับ AI แทนที่จะโต้แย้งกับคะแนน · ไม่มีใครพยายามเขียนงานเอาใจ AI

**ข้อเสียที่ต้องพูดตรง ๆ:** เป็นการไม่บอกสิ่งที่นักศึกษาอาจอยากรู้ และถ้ารู้ทีหลังจากช่องทางอื่น ความไว้วางใจจะเสียหายมากกว่าการบอกตั้งแต่ต้น

**เส้นที่วางไว้ตอนนี้: "ปิดจากสายตา แต่ไม่ปิดถ้าถูกถาม"** — ไม่โฆษณาบนหน้าจอ แต่ถ้านักศึกษาถาม อาจารย์ตอบตามจริงและให้ดูได้ทั้ง rubric และคำอธิบายชั้น AI **นี่เป็นข้อที่ควรถกกับอาจารย์อีกครั้งก่อนใช้จริง ไม่ใช่ข้อที่ปิดแล้ว**

## 5.4 คำอธิบายชั้น AI ต้องเขียนเป็นภาษาคน

`JudgePromptVersion` เปลี่ยนได้โดยไม่ขึ้นเวอร์ชัน rubric แต่**นักศึกษาขอดูได้เสมอ**

**ผลข้างเคียงที่ตั้งใจ:** เพราะอาจถูกขอดูตลอด **มันจึงต้องเขียนเป็นภาษาที่คนอ่านรู้เรื่อง ห้ามเป็น prompt hack** — ซึ่งกันการจูน prompt ให้เดาถูกโดยไม่ได้เข้าใจอะไรไปในตัว

**เส้นแบ่งว่าอะไรควรเป็น rubric อะไรควรเป็นคำอธิบายชั้น AI ตัดสินด้วยคำถามเดียว:** *"ถ้านักศึกษาอ่านข้อความนี้ตอนทำงาน เขาจะทำงานต่างออกไปไหม"* ถ้าต่าง มันคือ rubric ต้องขึ้นเวอร์ชันใหม่
