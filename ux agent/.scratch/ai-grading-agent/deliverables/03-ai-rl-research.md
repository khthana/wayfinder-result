# 0. บทสรุปสำหรับผู้บริหาร

เอกสารนี้ตอบสามคำถาม

1. **AI ตัดสินอะไรได้ ตัดสินอะไรไม่ได้** และควรจัดสถาปัตยกรรมอย่างไรให้ส่วนที่ตัดสินไม่ได้ไม่ทำให้ทั้งระบบพัง
2. **จะรู้ได้อย่างไรว่าระบบดีพอ** — ตัววัด ขนาดตัวอย่างที่ต้องมี และตัวหารที่ทำให้ตัวเลขมีความหมาย
3. **RL ในโครงงานนี้คืออะไรได้จริงบ้าง** — และจะออกแบบการทดลองอย่างไรให้**ล้มไม่ได้โดยโครงสร้าง**

## ข้อสรุปที่สำคัญที่สุดห้าข้อ

| # | ข้อสรุป | ผลต่อการออกแบบ |
|---|---|---|
| 1 | **เพดานของ AI ≈ ระดับที่มนุษย์สองคนตรงกัน** งานออกแบบแบบ open-ended มี exact agreement ระหว่างมนุษย์เพียง **55–75%** | ต้องวัดเพดานมนุษย์**ก่อน**วัด AI · ตัวเลขนี้คือ**ตัวหารของทั้งวิทยานิพนธ์** |

# 1. AI ตัดสินอะไรได้

## 1.1 สามชั้นของการตรวจ

```
ชั้นที่ 1  ตัวอ่านไฟล์      Figma API / PDF → โครงสร้าง + ภาพ
ชั้นที่ 2  ชั้นกฎ           โค้ดล้วน · LLM ห้ามแตะ
ชั้นที่ 3  ชั้น LLM         vision-language model · ตีความ
```

**ชั้นกฎไม่ได้มีไว้แค่ให้คะแนน** มันยัง**ป้อน metrics ให้ชั้น LLM ใช้เป็นหลักฐาน** เช่น ชั้นกฎบอกว่า "พบขนาดฟอนต์ 11 ขนาดใน 6 หน้าจอ" แล้วชั้น LLM ใช้ข้อเท็จจริงนั้นประกอบการตัดสินเรื่องความสม่ำเสมอ แทนที่จะต้องนับเอง (ซึ่งทำได้ไม่แม่น)

| ชั้น | เกณฑ์ที่รับผิดชอบ | ตัวอย่าง |
|---|---|---|
| ชั้นกฎ | `kind = rule` | อัตราส่วน contrast · จำนวนขนาดฟอนต์ · ความสม่ำเสมอของ spacing · สัดส่วนการใช้ component/style · ความครบของสิ่งที่สั่งให้ส่ง |
| ชั้น LLM | `kind = llm` | ลำดับชั้นการมองเห็น · โครงสร้างข้อมูลและการนำทาง · ความเหมาะสมของ flow กับโจทย์ผู้ใช้ · คุณภาพ micro-copy |
| ไม่มีใครทำ | `kind = human_only` | ความคิดสร้างสรรค์ · ความเหมาะสมเชิงวัฒนธรรม · การตอบโจทย์ที่ต้องรู้บริบทของผู้เรียนคนนั้น |

## 1.2 ทำไมชั้นกฎเป็นตัวประกันของโครงงาน

ชั้นกฎ**ไม่พึ่งความแม่นของ LLM เลย** ถ้าชั้น LLM ให้คะแนนได้ไม่ดีพอที่จะใช้จริง ส่วนที่เหลือของระบบ — ชั้นกฎ สมุดคะแนน CLO attainment การสืบย้อน การส่งออก — **ยังเป็นระบบที่ใช้งานได้จริงและมีคุณค่าต่อรายวิชา**

**นี่คือเหตุผลเชิงโครงสร้างที่ทำให้โครงงานนี้ไม่มีทางไม่มีผลงานส่ง** และทีมควรรู้ตั้งแต่วันแรก เพราะมันเปลี่ยนวิธีจัดลำดับงาน

## 1.3 ข้อบังคับสี่ข้อของชั้น LLM

1. **หนึ่ง call ต่อหนึ่งหัวข้อประเมิน** ไม่ใช่ call เดียวแล้วให้คืนคะแนนทุกข้อ
   **เหตุผล:** ให้แต่ละการตัดสินอิสระจากกัน · แยกได้ว่าข้อไหนพัง · ตรวจใหม่เฉพาะข้อที่แก้ rubric ได้
   **ราคาที่จ่าย:** จำนวน call เพิ่มเป็นเท่าของจำนวนเกณฑ์ — ยอมรับได้ที่ปริมาณงานระดับนี้
2. **บังคับคืนสามอย่างเสมอ: ระดับ + เหตุผล + หลักฐานที่ชี้ตำแหน่งได้** คำตัดสินที่ชี้หลักฐานไม่ได้ถือว่าไม่สมบูรณ์
3. **ห้ามเก็บค่าความมั่นใจที่โมเดลรายงานเอง** — ค่าที่ LLM บอกว่ามั่นใจ 90% ไม่สัมพันธ์กับความถูกต้องจริง **ใช้ผลรันซ้ำ 3 ครั้งแทน** ถ้าสามครั้งให้คนละระดับ นั่นคือความไม่แน่นอนที่วัดได้จริง
4. **ต้องเป็น vision-language model** งาน UX/UI ตัดสินจากภาพ การส่งเฉพาะโครงสร้าง JSON ของ Figma ไปให้ LLM ข้อความล้วนคือการตัดข้อมูลที่สำคัญที่สุดออก

## 1.4 ความเสี่ยงทางเทคนิคสองข้อที่ต้อง spike ก่อนล็อกสถาปัตยกรรม

| # | คำถาม | ถ้าคำตอบเป็น "ไม่" |
|---|---|---|
| S1 | **Figma API คืนพิกัดที่ปักหมุดบนภาพได้จริงไหม** | ฟีเจอร์ "กดที่หลักฐานแล้วกระโดดไปที่ frame" ตายทั้งฟีเจอร์ → คุณค่าหลักของหน้าจอตรวจหายไป → ต้องออกแบบวิธีชี้หลักฐานใหม่ทั้งหมด |
| S2 | **vLLM รัน VLM ระดับ 27–32B แบบ 4-bit บน RTX 5090 (Blackwell) ได้จริงไหม** | ต้องลดขนาดโมเดล หรือย้ายไปใช้ API ซึ่งชนกับข้อจำกัดงบประมาณ |

# 2. จะรู้ได้อย่างไรว่าระบบดีพอ

## 2.1 กฎข้อเดียวที่ละเมิดไม่ได้

> **ข้อมูลที่ใช้วัดระบบ ห้ามใช้ปรับปรุงระบบ**

ละเมิดข้อนี้แล้ว **ตัวเลขทุกตัวในวิทยานิพนธ์ใช้ไม่ได้** และไม่มีทางรู้ว่าสูงเกินจริงเท่าไร

**การละเมิดเกิดขึ้นโดยไม่ตั้งใจได้ง่ายมาก** เช่น รันการจำลองผลของข้อเสนอแก้ rubric บนชุด test แล้วรับเฉพาะข้อที่ทำให้ดีขึ้น — นั่นคือการปรับจูนบนชุด test เรียบร้อยแล้ว แม้จะไม่ได้ตั้งใจ

**กลไกป้องกันที่ต้องมีในระบบ ไม่ใช่แค่ในวินัยของคน**

- **`DatasetMembership` เป็นตารางสมาชิกที่ตรึงไว้ ไม่ใช่การสุ่มตอน query** — ถ้าสุ่มตอน query คำว่า "เปิดครั้งเดียว" ไม่มีความหมาย
- **`SystemMeta.last_test_access`** และแถบ 🔒 บนทุกหน้าของแดชบอร์ด
- ระบบ**ปฏิเสธและบันทึก**ทุกครั้งที่มีการพยายามอ่านชุด test

## 2.2 การแบ่งข้อมูลสามชุด

| ชุด | ขนาด | ใช้ทำอะไร |
|---|---|---|
| **dev** | ส่วนใหญ่ | ปรับ prompt · เลือก anchor · ทดลองทุกอย่าง · เปิดดูได้ไม่จำกัด |
| **validation** | ~24 ชิ้น กันไว้จาก dev | จำลองผลของข้อเสนอแก้ rubric ก่อนตัดสินใจรับ |
| **test** | 30–40 ชิ้น แช่แข็ง | **เปิดครั้งเดียว 31 มี.ค. 2570** |

## 2.3 ตัววัดที่ใช้ และตัวที่ไม่ใช้

| ตัววัด | ใช้ไหม | เหตุผล |
|---|---|---|
| **Exact / adjacent agreement** | ✅ ตัวหลักในการรายงาน | CI แคบกว่า QWK ที่ N เดียวกัน · สื่อสารกับอาจารย์ได้ตรงที่สุด |
| **QWK** | ✅ แต่ต้องมาพร้อม CI เสมอ | ปรับ chance แล้ว และให้น้ำหนักความห่างแบบกำลังสอง ซึ่งตรงกับความจริงว่าผิดไป 3 ระดับแย่กว่าผิดไป 1 ระดับมากกว่าสามเท่า |
| **Mean signed error (bias)** | ✅ **บังคับเก็บ** | **บอกทิศ ซึ่งเป็นข้อมูลชิ้นเดียวที่บอกว่าจะแก้ยังไง** |
| **MAE** | ⚠ ใช้ประกอบ | **ทิ้งเครื่องหมาย** ซึ่งเป็นข้อมูลที่นำไปทำอะไรต่อได้ · ใช้ MAE อย่างเดียวคือการเห็นว่ามีปัญหาแต่ไม่รู้ว่าปัญหาไปทางไหน |
| **ICC(2,1)** | ✅ สำหรับเพดานมนุษย์ | เทียบกับวรรณกรรม portfolio assessment ได้ |
| **ค่าความมั่นใจที่ LLM รายงาน** | ❌ | ไม่สัมพันธ์กับความถูกต้องจริง |

**หน่วยวิเคราะห์คือ (งาน × เกณฑ์) ไม่ใช่งาน** — งาน 40 ชิ้น × 7 เกณฑ์ = 280 การตัดสิน ทำให้วัด bias รายเกณฑ์ได้

> **แต่ต้องยอมรับว่าคะแนนภายในงานเดียวกันสัมพันธ์กัน → effective N < 280** ทุก CI ต้องคำนวณด้วย **cluster bootstrap ที่ resample ที่ระดับงาน/นักศึกษา** ไม่ใช่ระดับเซลล์ **มิฉะนั้น CI จะแคบเกินจริงและข้อสรุปทั้งหมดจะแข็งเกินความเป็นจริง**

## 2.4 ตาราง "มี N เท่านี้ อ้างอะไรได้"

**ตารางนี้ควรอยู่ในบทที่ 3 ของเล่ม** เพราะมันคือคำสัญญาที่ประกาศล่วงหน้าว่าจะไม่อ้างเกินข้อมูล

| N (ชิ้นงานที่อาจารย์ตรวจจริง) | วัดได้จริง | ปรับได้จริง | **ห้ามอ้าง** |
|---|---|---|---|
| **10–30** | ทิศของ bias รายเกณฑ์แบบหยาบ · รายการความผิดพลาดเชิงคุณภาพ · ความกำกวมของถ้อยคำ rubric | แก้ถ้อยคำที่ AI ตีความผิดชัด ๆ · เลือก anchor · แก้ระดับที่ AI ไม่เคยใช้เลย | **QWK ทุกชนิด** (CI ±0.25) · การเทียบ prompt สองแบบด้วยตัวเลข |
| **30–60** | bias รายเกณฑ์ถ้า ≥ 0.25 ระดับ · exact/adjacent ±13pp · MAE ±0.16 | การชดเชย bias เชิงเส้นรายเกณฑ์ · ปรับ threshold การส่งต่อให้คนทวน | QWK เป็นตัวเลขเดี่ยว · เลือก prompt ที่ดีที่สุดจาก 5 ตัวด้วย QWK |
| **60–120** | QWK พร้อม CI กว้าง ~0.23–0.27 → พูดได้แค่เป็น "ช่วง" · bias ที่เล็กถึง 0.20 ระดับ | prompt optimization แบบมีระเบียบ · isotonic/linear calibration | ว่าผ่านเกณฑ์ 0.70 · ว่า prompt ใหม่ดีกว่าเก่าเมื่อ ΔQWK < 0.10 |
| **150–300** | QWK CI ~0.16–0.19 · ตรวจจับ ΔQWK ≥ 0.15 แบบ paired ได้ที่ power ~0.9 | ทุกอย่างข้างต้น + เลือกระหว่างสถาปัตยกรรมการตรวจที่ต่างกันจริง | ว่า ΔQWK 0.05 มีความหมาย |

**สิ่งที่ตารางนี้บอกทันที:** ที่ n = 28 ต่อเกณฑ์ (ตัวเลขของต้นแบบ) **การเรียงอันดับ 7 เกณฑ์แล้วไล่แก้จากล่างขึ้นบนคือการไล่ตามสัญญาณรบกวน** เพราะ CI ราว ±0.18 ทำให้เกณฑ์ที่ QWK 0.71 กับ 0.64 แยกจากกันไม่ได้

## 2.5 เพดานมนุษย์ — ตัวหารของทั้งวิทยานิพนธ์

### วรรณกรรมบอกอะไร

Jonsson & Svingby (2007) review งานวิจัย 75 ชิ้นเรื่อง rubric ใน performance assessment:

- งาน **open-ended ที่ประเมินสมรรถนะซับซ้อน** (งานออกแบบ UX คือกรณีนี้เป๊ะ) มี **exact rater consensus เพียง 55–75%** แม้ใช้ rubric
- เกณฑ์ที่ถือว่าเชื่อถือได้: **exact ≥ 70% · adjacent ≥ 90%**
- **anchor / benchmark example ช่วยเพิ่ม agreement ได้มากที่สุด** มากกว่าการอบรมผู้ตรวจ
- rubric เฉพาะเจาะจงกับโจทย์ให้ผลดีกว่า generic rubric
- **สเกลที่มีระดับน้อยกว่าให้ consensus สูงกว่า**

Portfolio assessment ในหลักสูตรแพทย์ (Ewha Womans University): ICC ของผู้ตรวจทุกคน **0.382** · หลังคัดผู้ตรวจที่แย่ออกขึ้นเป็น **0.442** · สหสัมพันธ์รายคนกับ gold standard กระจายตั้งแต่ **0.42 ถึง 0.89**

แต่เมื่อผู้ตรวจได้รับการอบรมและมีเกณฑ์ที่ระบุชัด ICC ขึ้นถึง **≥ 0.81** ได้
→ **ปัญหาไม่ได้อยู่ที่มนุษย์ แต่อยู่ที่ว่า rubric ชัดพอและมี anchor หรือเปล่า**

### แปลว่าอะไรกับโครงงานนี้

1. ถ้าอาจารย์สองคนตรงกัน exact เพียง ~65% **การไล่ให้ AI ทำได้ 90% คือการ fit สัญญาณรบกวน ไม่ใช่ความแม่นยำ**
2. **ต้องวัด human–human ก่อนวัด AI** — ให้อาจารย์ (หรืออาจารย์ + ผู้ช่วยสอน) ตรวจงานชุดเดียวกัน 20–30 ชิ้น
3. ถ้าหาผู้ตรวจคนที่สองไม่ได้ ใช้ **intra-rater reliability** แทน: อาจารย์คนเดิมตรวจงานชุดเดิมซ้ำ**หลังผ่านไป 2–3 สัปดาห์ โดยสุ่มลำดับใหม่** — เป็นเพดานที่อ้างได้จริงและทำได้ด้วยคนคนเดียว
4. **เป้าหมายที่ป้องกันตัวได้ในห้องสอบ**

> **"AI–teacher agreement ไม่ต่ำกว่า teacher–teacher (หรือ teacher–self) agreement เกิน 0.10 QWK"**
> ไม่ใช่ "QWK ≥ 0.70" ลอย ๆ

ข้อ 4 คือความแตกต่างระหว่างวิทยานิพนธ์ที่ตอบคำถามกรรมการได้กับที่ตอบไม่ได้ **"QWK 0.68" ตอบไม่ได้ว่าดีหรือแย่** แต่ "0.68 [0.58, 0.79] เทียบกับเพดานมนุษย์ 0.71 [0.60, 0.81]" ตอบได้ทันที

### เกณฑ์ความสำเร็จที่ประกาศล่วงหน้า

> **ขอบล่างของ 95% CI ของ QWK ≥ 0.60 · |bias| ทุกเกณฑ์ < 0.25 ระดับ · adjacent agreement ≥ 90%**

ตั้งเป้าที่ **CI ไม่ใช่ที่ point estimate** — บรรลุได้จริงที่ N ~150 และป้องกันตัวได้ในการสอบ

## 2.6 ห้าวิธีที่ทำให้ N น้อยมีพลังมากขึ้น

1. **หน่วยวิเคราะห์เป็น (งาน × เกณฑ์)** พร้อม cluster bootstrap
2. **วัดผลต่างแบบ paired เสมอ** — เทียบ prompt เก่า/ใหม่บนงานชุดเดียวกัน แล้ว bootstrap ที่ผลต่าง ตัดความแปรปรวนจาก "งานชุดนี้ยากหรือง่าย" ออกไป
3. **ตั้งเป้าที่ CI**
4. **รายงานเทียบเพดานมนุษย์เสมอ**
5. **ใช้ metric ที่ไม่ปรับ chance เป็นตัวหลัก** (exact/adjacent, MAE) เพราะ CI แคบกว่า

## 2.7 เมื่อ rubric เปลี่ยนเวอร์ชัน

**RubricVersion ใหม่ = ไม้บรรทัดใหม่** คะแนนจากคนละเวอร์ชันเทียบกันตรง ๆ ไม่ได้

**ทางแก้: bridge set 15–25 ชิ้นที่ตรวจด้วยทั้งสองเวอร์ชัน** ถ้าไม่มี bridge set กราฟแนวโน้มต้องแสดงเป็น**เส้นประ** เพื่อสื่อสารด้วยรูปว่าช่วงนั้นเทียบกันไม่ได้ แทนที่จะลากเส้นทึบต่อกันแล้วให้คนเข้าใจผิด

**ราคาของ bridge set หนึ่งชุด ≈ 2.5 ชั่วโมงของอาจารย์** — ต้องแสดงราคานี้บนหน้าจอตอนกดรับข้อเสนอ ไม่ใช่ให้รู้ทีหลัง

## 2.8 ลำดับการใช้เวลาตรวจของอาจารย์

เวลาของอาจารย์คือทรัพยากรที่หายากที่สุดในโครงงานนี้ ลำดับที่ให้ผลตอบแทนสูงสุด:

1. **ตรวจซ้ำเพื่อวัดเพดานมนุษย์ (20–30 ชิ้น)** — ถูกที่สุด ให้ผลตอบแทนทางวิชาการสูงสุด **และต้องทำก่อนสิ่งอื่นทั้งหมด**
2. **ตรวจแบบ blind เพื่อสร้าง gold set** — เป็นเชื้อเพลิงของทุกอย่างที่เหลือ
3. **เลือก anchor example** — ผลตอบแทนต่อชิ้นสูงมาก
4. ตรวจเพิ่มเพื่อขยายเส้นโค้งการเรียนรู้

# 3. การได้มาซึ่งข้อมูล — และเหตุผลที่หมุดที่แข็งที่สุดคือวันเปิดภาค

# 4. RL — สิ่งที่โจทย์เรียกว่า RL คืออะไรได้จริง

## 4.1 พูดตรง ๆ ก่อน: สิ่งที่คนเรียกว่า RL ส่วนใหญ่ในบริบทนี้ไม่ใช่ RL

| สาย | ทำอะไร | แตะ weight ไหม | **เรียกว่า RL ได้ไหม** |
|---|---|---|---|
| **สาย P — prompt optimization** | ใช้ GEPA/OPRO ค้นถ้อยคำของคำอธิบาย + เลือกชุด anchor อัตโนมัติ โดยมี agreement บน dev เป็น objective | ไม่ | **ไม่ใช่** — วรรณกรรมเรียก self-refine / reflective prompt search |
| **สาย D — preference learning** | DPO/ORPO บนโมเดลเปิดด้วย LoRA จากคู่ (คำตัดสินที่อาจารย์ยอมรับ vs ที่อาจารย์แก้) | ใช่ (LoRA) | **กึ่ง** — พัฒนามาจาก RLHF แต่**ไม่มี reward model และไม่มี rollout** |
| **สาย B — contextual bandit** | เลือก "กลยุทธ์การตรวจ" ต่อชิ้นงาน แล้วเรียนรู้จากผลย้อนกลับ | ไม่ | **ใช่ — RL ตัวจริงตัวเดียวในโครงงาน** |

> **การเขียนผิดตรงนี้คือจุดที่กรรมการจับได้ง่ายที่สุด** ในเล่มต้องเขียนว่าสาย D เป็น **preference optimization** และอธิบายว่าต่างจาก RLHF เต็มรูปตรงที่ไม่มี reward model และไม่มีการ sample จากนโยบายระหว่างเทรน

**สาย B ราคาถูกที่สุด** (ไม่ต้อง GPU ไม่ต้องเทรน ใช้ ~30 observation ต่อ arm) และเป็นตัวเดียวที่ทำให้เล่มพูดคำว่า RL ได้โดยไม่ผิดนิยาม จึงวางเป็น**ฐานที่ต้องมี**

## 4.2 คำถามวิจัย — หนึ่งประโยค

> **ที่ระดับข้อมูลของรายวิชาเดียว (นักศึกษา 40–60 คน 2 ภาคการศึกษา) การปรับ prompt อัตโนมัติ กับการเรียนรู้จากความชอบของอาจารย์ ทำให้ agreement ระหว่าง AI กับอาจารย์เพิ่มขึ้นเป็นเส้นโค้งอย่างไรเมื่อจำนวนชิ้นงานที่อาจารย์ตรวจเพิ่มขึ้น และต้องใช้กี่ชิ้นจึงจะแยกสองวิธีออกจากกันได้อย่างมีนัยสำคัญ**

**คำถามย่อยสามข้อ**

- **RQ1 (เส้นโค้ง):** agreement เพิ่มเท่าไรต่อชิ้นงานที่อาจารย์ตรวจ และเริ่มแบนที่ N เท่าไร
- **RQ2 (เปรียบเทียบ):** ที่ N เท่ากัน สายไหนดีกว่า และจุดสลับอันดับ (ถ้ามี) อยู่ที่ N เท่าไร
- **RQ3 (นัยเชิงปฏิบัติ):** ถ้าอาจารย์มีเวลาตรวจได้ X ชิ้นต่อเทอม ควรลงแรงไปทางไหน

## 4.3 ทำไมกรอบนี้ล้มไม่ได้โดยโครงสร้าง

**เส้นโค้งการเรียนรู้เป็นผลการทดลองไม่ว่าจะชันหรือแบน**

- **ชัน** = เรียนรู้ได้จริง พร้อมตัวเลขว่าต้องใช้ข้อมูลเท่าไร
- **แบน** = ข้อมูลระดับนี้ไม่พอ **พร้อมหลักฐานเชิงปริมาณและการประมาณว่าต้องมีเท่าไรจึงจะพอ** ซึ่งเป็นคำตอบที่มีค่าต่อทุกคนที่คิดจะทำระบบแบบเดียวกันในวิชาเดียว

เทียบกับการตั้งคำถามว่า *"RL ทำให้ดีขึ้นไหม"* ซึ่งถ้าผลออกมาว่าไม่ ก็เหลือแค่ "ไม่พบความแตกต่าง" — **อ่อนกว่ามากในห้องสอบ**

## 4.4 สมมติฐานที่ประกาศล่วงหน้า

เขียนลงเล่ม**ก่อน**เริ่มเก็บข้อมูล เพื่อไม่ให้เป็นการอธิบายผลย้อนหลัง

| # | สมมติฐาน | ฐานที่มา |
|---|---|---|
| **H1** | ทั้งสองสายให้เส้นโค้งที่**ชันมากช่วง N = 0–60 แล้วแบนเร็ว** | ที่ N หลักสิบ bias รายเกณฑ์คือสิ่งที่แก้ได้คุ้มที่สุดและแก้ได้เร็ว |
| **H2** | **สายปรับ prompt ชนะที่ทุกค่า N ในช่วงที่โครงงานนี้เอื้อมถึง** | GEPA ชนะ GRPO เฉลี่ย 6% / สูงสุด 20% ด้วย rollout น้อยกว่า 35 เท่า |
| **H3** | ผลต่างระหว่างสองสาย **มี CI คร่อมศูนย์ตลอด** ที่ N ≤ 200 | paired ΔQWK ต้องการ N ~150–300 จึงตรวจจับผลต่าง 0.15 ได้ที่ power 0.9 และผลต่างที่คาดในที่นี้เล็กกว่านั้น |
| **H4** | ตัวที่ขยับ agreement ได้มากที่สุดต่อหน่วยแรง **ไม่ใช่ทั้งสองสาย แต่คือ anchor example + การชดเชย offset รายเกณฑ์** | วรรณกรรม rubric calibration |

> **ถ้า H3 เป็นจริงตามคาด นั่นคือผลของโครงงาน ไม่ใช่ความล้มเหลวของโครงงาน** — และนี่คือเหตุผลทั้งหมดที่ต้องเขียน H3 ไว้ล่วงหน้า

## 4.5 วิธีสร้างเส้นโค้งการเรียนรู้

**แกน x = จำนวนชิ้นงานที่อาจารย์ตรวจแบบ blind** ไม่ใช่จำนวนแถวคะแนน — เพราะนี่คือ**ต้นทุนจริงที่อาจารย์จ่าย** และเป็นคำตอบที่เอาไปใช้ได้จริง

**จุดบนแกน x:** N ∈ {20, 40, 60, 80, 100} ในภาค 1 → ต่อถึง {150, 200, 250} เมื่อรวมภาค 2

**ขั้นตอน**

1. **สุ่มชุดย่อยแบบซ้อนกัน (nested)** — ชุด N=20 ต้องเป็นสับเซ็ตของ N=40 เสมอ เพื่อให้เส้นโค้งสะท้อน "ข้อมูลเพิ่มขึ้น" ไม่ใช่ "บังเอิญได้ชุดที่ง่ายกว่า"
2. **สุ่มซ้ำ 3 ชุดต่อหนึ่งค่า N** แล้วรายงานค่าเฉลี่ย ± ช่วง — **ถ้าไม่ทำซ้ำ เส้นโค้งจะขึ้น ๆ ลง ๆ จากเสียงรบกวนล้วน ๆ และตีความไม่ได้เลย**
3. **สุ่มที่ระดับนักศึกษา/กลุ่ม (GroupKFold)** ไม่ใช่ระดับแถว
4. **ทุกจุดวัดผลบน test set ชุดเดียวกันที่แช่แข็งไว้** · ระหว่างทางใช้ dev เท่านั้น
5. **รวม 3 seed × 4 ค่า N × 2 สาย = 24 รอบ** — ถ้าเห็นว่าเยอะเกิน **ให้ตัดค่า N ทิ้ง ไม่ใช่ตัดจำนวน seed**
6. CI ด้วย **cluster bootstrap ที่ระดับนักศึกษา** · การเทียบ P กับ D ต้อง **paired บนงานชุดเดียวกัน** แล้ว bootstrap ที่ผลต่าง

> **กับดักที่ต้องเขียนกันไว้ในเล่ม:** ถ้าเส้นโค้งขึ้นแล้วลงแล้วขึ้น **อย่ารีบตีความว่า "โมเดลเรียนรู้แล้วลืม"** — ที่ N ระดับนี้ ความแกว่งขนาดนั้นอธิบายได้ด้วยเสียงรบกวนอย่างเดียว การทำ 3 seed ต่อจุดมีไว้เพื่อให้เห็นข้อนี้ด้วยตาตัวเอง ไม่ใช่เพื่อความสวยของกราฟ

**หมายเหตุเรื่อง baseline:** สาย D ต้องเทียบกับ **สาย P ที่ optimize แล้ว** ไม่ใช่เทียบกับ prompt ดิบ — ไม่งั้นเครดิตของการปรับ prompt จะถูกนับเป็นผลงานของ preference learning

## 4.6 การสร้างคู่ preference — จุดที่ทำผิดกันบ่อยที่สุด

**วิธีที่ดูตรงไปตรงมาแต่ผิด:** เอาคำตัดสินของอาจารย์เป็นตัวชนะ และคำตัดสินของ AI เป็นตัวแพ้

**ทำไมผิด:** ข้อความของอาจารย์อยู่**นอกการกระจายของโมเดล** DPO จะไล่ตาม**สไตล์การเขียน**แทนที่จะไล่ตาม**การตัดสิน**

**วิธีที่ถูก (best-of-n distillation)**

1. ให้โมเดล**สร้างคำตัดสินเอง k = 4 แบบ** ต่อหนึ่ง (ชิ้นงาน × เกณฑ์)
2. **ตัวชนะ** = ตัวที่ระดับตรงกับอาจารย์ที่สุด · **ตัวแพ้** = ตัวที่ห่างที่สุด
3. ถ้า k ตัวให้ระดับเดียวกันหมด **ทิ้งคู่นั้น** — ไม่มีสัญญาณให้เรียน
4. **ใช้เฉพาะคู่จากงานที่ตรวจแบบ blind เท่านั้น**

## 4.7 นิยาม state / action / reward ของสาย B

| องค์ประกอบ | นิยามในโครงงานนี้ |
|---|---|
| **context (state)** | ประเภทชิ้นงาน · เกณฑ์ที่กำลังตรวจ · `rubric_version_id` · สัญญาณจากชั้นกฎ (จำนวนเฟรม จำนวน component ผลตรวจ contrast) · ความซับซ้อนของไฟล์ |
| **action (arm)** | กลยุทธ์การตรวจ 5 ตัว: (1) zero-shot · (2) few-shot 3 anchor · (3) best-of-3 แล้ว majority · (4) ให้บรรยายก่อนให้คะแนน · (5) โมเดลเล็กแทนโมเดลใหญ่ |
| **reward** | `1 − |ระดับที่ AI ให้ − ระดับที่อาจารย์ให้| / (จำนวนระดับ − 1)` ∈ [0,1] · **มาช้า** (รู้ผลตอนอาจารย์ตรวจเสร็จ) · **วัดได้เฉพาะบนชิ้นที่ blind** |
| **policy** | Thompson sampling หรือ LinUCB |
| **ที่ยากกว่าตำรา** | **reward ไม่นิ่ง** — เมื่อ rubric หรือ `JudgePromptVersion` เปลี่ยน ค่าที่เรียนมาก็เก่าทันที ต้องใช้ bandit แบบ **sliding window หรือ discount** และใส่ `rubric_version` เป็นส่วนหนึ่งของ context |

**ต้นทุนของแต่ละ arm ต่างกัน** (best-of-3 แพงกว่า zero-shot 3 เท่า) จึงควรใช้ **reward สุทธิ = ความแม่น − λ × ต้นทุน** และรายงานทั้งแบบคิดและไม่คิดต้นทุน — ทำให้ผลการทดลองมีคำตอบเชิงปฏิบัติที่ใช้ได้ทันที

## 4.8 Reward hacking สี่แบบและวิธีตรวจจับ

| # | รูปแบบ | ทำไมเกิด | วิธีตรวจจับ |

## 4.9 ทรัพยากรและเวลาเครื่อง

**การมี GPU ของภาคเปลี่ยนแผนในทางที่ดีขึ้นชัดเจน** — เดิมวางไว้บน Kaggle (T4 16GB จำกัด 30 ชม./สัปดาห์) และ**แก้ปัญหา PDPA ไปในตัว** เพราะงานนักศึกษาไม่ต้องออกนอกคณะ

**แต่ต้องระวังสองข้อ**

1. **GPU ไม่ได้แก้ค่า API ของโมเดล frontier** — baseline และการตรวจจริงประจำวันยังเรียก API ภายนอก **งานที่ทำซ้ำทุกสัปดาห์และงานที่รันซ้ำเยอะต้องอยู่บนโมเดลเปิด** ส่วน API เก็บไว้เป็น**จุดอ้างอิงระดับบนสุดที่รันไม่บ่อย**
2. **ต้องมีตัวนับต้นทุนต่อ call และเพดานงบที่หยุดเรียก API เองเมื่อชน**

| VRAM ต่อการ์ด | ทำอะไรได้ |
|---|---|
| 16 GB | QLoRA 7–8B ได้ · 13B ไม่ไหว |
| 24 GB | QLoRA 13B สบาย · LoRA 7–8B ไม่ quantize ได้ — **จุดที่คุ้มที่สุด** |
| 32 GB (RTX 5090) | VLM 27–32B แบบ 4-bit สำหรับ inference — **ต้อง spike ยืนยัน** |
| 40–80 GB | 30B+ · full fine-tune 7B |

**ประมาณการเวลาเครื่อง:** QLoRA 7–8B ≈ 1–3 ชม./รอบ × 24 รอบ ≈ **25–70 ชั่วโมง** กระจายตลอดภาค 2 ได้

## 4.10 การเชื่อมกับระบบจริง

**แยกออกจากระบบ ไม่ต่อเข้า MVP** — สาย P และ D อยู่ในรูป**สคริปต์วิจัยที่อ่านข้อมูลแบบอ่านอย่างเดียว ไม่มีสิทธิ์เขียนกลับ**

| ผลของ | นำกลับเข้าระบบได้ไหม |
|---|---|
| **สาย P** | **ได้และควรนำกลับ** — ออกมาเป็น `JudgePromptVersion` ใหม่ที่ต้องผ่านประตูอนุมัติเหมือนข้อเสนออื่น **ไม่มีสิทธิ์พิเศษ** |
| **สาย D (LoRA adapter)** | **ไม่นำกลับใน MVP** — จะเปลี่ยนสถาปัตยกรรมจาก "เรียก API" เป็น "โฮสต์โมเดลเอง" ซึ่งเป็นการตัดสินใจระดับสถาปัตยกรรม ไม่ใช่ผลพลอยได้ของการทดลอง |
| **สาย B (bandit)** | **ได้ในเทอมถัดไป** — เป็นตารางเลือกกลยุทธ์ต่อ context ซึ่งฝังเป็นค่าคงที่ได้โดยไม่ต้องมี bandit ทำงานจริงในระบบ |

**เหตุผลของการแยก:** ถ้าการทดลองต่ออยู่กับระบบที่นักศึกษาใช้จริง **เวลาการทดลองพัง คะแนนของนักศึกษาก็พังด้วย** และจะไม่มีใครกล้าทดลองอะไรอีกเลยตลอดโครงงาน

# 5. ปฏิทินและจุดตัดสินใจหยุด

สอบจบปลายภาค 2/2569 (ราว เม.ย.–พ.ค. 2570) · **วันที่ด้านล่างคือวันตัดสินใจจริง ไม่ใช่วันประมาณ**

| วันที่ | ประตู | ถ้าไม่ผ่าน |
|---|---|---|
| **31 ต.ค. 2569** | **P0 เสร็จ** — ระบบบันทึกครบ · blind ตั้งแต่ชิ้นงานแรก · ตรวจซ้ำรอบ 0 เสร็จ **มีเพดานมนุษย์เป็นตัวเลขแล้ว** | **หยุดสาย RL ทั้งหมดทันที** ทุ่มเวลาที่เหลือให้ระบบหลัก — ไม่มีเพดานมนุษย์ = ไม่มีตัวหาร = ทุกตัวเลขหลังจากนี้ตีความไม่ได้ |
| **31 ธ.ค. 2569** *(จบภาค 1)* | คู่คะแนน blind ≥ **300 คู่** จากนักศึกษา ≥ **35 คลัสเตอร์** · สาย P รันครบอย่างน้อย 2 จุดบนเส้นโค้ง | **ตัดสาย D ทิ้ง** เดินต่อด้วยสาย P + bandit รายงานเป็นข้อจำกัดด้านข้อมูล |
| **28 ก.พ. 2570** | **จุดตัดสินใจหลัก** — สาย D ต้องรันจบ end-to-end บนข้อมูลจริงอย่างน้อย 1 รอบ (ไม่ต้องชนะ แค่ต้องรันจบและมีตัวเลข) | **หยุดสาย D เขียนเป็นผลเชิงลบตาม §6** — **ห้ามต่อเวลา** |
| **31 มี.ค. 2570** | **แช่แข็งการทดลอง** — ไม่รันอะไรใหม่อีก **เปิด test set ครั้งเดียว** คำนวณผลทั้งหมด | ไม่มีทางเลือกอื่น วันนี้ตายตัว |
| **เม.ย.–พ.ค. 2570** | เขียนเล่ม + สอบ | |

## กฎเหล็กสองข้อ

1. **ห้ามเลื่อนวันที่ 28 ก.พ. ไม่ว่าผลจะ "ใกล้จะได้แล้ว" แค่ไหน** — นี่คือกับดักที่กลืนโครงงานบ่อยที่สุด และ **"ใกล้จะได้แล้ว" เป็นความรู้สึกที่เกิดได้ตลอดเวลาโดยไม่สัมพันธ์กับความจริง**
2. **31 มี.ค. คือวันเปิด test set ครั้งเดียว** ถ้าเปิดแล้วผลไม่ถูกใจ **ห้ามกลับไปแก้แล้วเปิดใหม่** ถ้าทำ ตัวเลขในเล่มจะไม่ใช่ผลการทดลองอีกต่อไป และต้องเขียนกำกับว่าเปิดกี่ครั้ง

# 6. ย่อหน้าทางถอย — เขียนไว้ให้ใช้ได้ทันที

> ใช้แทนหัวข้อ "ผลการทดลองส่วน RL" ได้เลยถ้าถึง 28 ก.พ. 2570 แล้วสาย D ไปไม่ถึงไหน — แก้แค่ตัวเลขในช่องว่าง

> **ผลการทดลองด้านการเรียนรู้จากความชอบของผู้สอน**
>
> การทดลองนี้ตั้งคำถามว่า ที่ระดับข้อมูลของรายวิชาเดียว การเรียนรู้จากความชอบของผู้สอนให้ผลต่างจากการปรับ prompt อัตโนมัติหรือไม่ และต้องใช้ชิ้นงานที่ผู้สอนตรวจกี่ชิ้นจึงจะแยกสองวิธีออกจากกันได้
>
> ผลปรากฏว่า **ที่จำนวนข้อมูลสูงสุดที่เก็บได้จริงในสองภาคการศึกษา (\_\_\_ คู่คะแนน จากนักศึกษา \_\_\_ คน) ช่วงความเชื่อมั่น 95% ของผลต่างระหว่างสองวิธียังคร่อมศูนย์ (Δ QWK = \_\_\_ [\_\_\_, \_\_\_])** กล่าวคือข้อมูลระดับนี้ไม่เพียงพอที่จะสรุปว่าวิธีใดดีกว่า ผลนี้ตรงกับสมมติฐาน H3 ที่ประกาศไว้ล่วงหน้าก่อนเริ่มเก็บข้อมูล และสอดคล้องกับการทบทวนวรรณกรรมที่พบว่างานที่ใช้ preference learning กับการให้คะแนนอัตโนมัติสำเร็จนั้นใช้ข้อมูลระดับหมื่นชิ้น ซึ่งห่างจากข้อมูลของรายวิชาเดียวสองอันดับของขนาด
>
> จากเส้นโค้งการเรียนรู้ที่วัดได้ **ประมาณการว่าต้องมีคู่คะแนนอิสระประมาณ \_\_\_ คู่ จากนักศึกษาไม่น้อยกว่า \_\_\_ คน จึงจะตรวจจับผลต่างขนาด 0.15 QWK ได้ที่ power 0.8** ซึ่งเทียบเท่ากับการเก็บข้อมูลต่อเนื่อง \_\_\_ ภาคการศึกษา หรือการขยายไปยังรายวิชาอื่นในหลักสูตรพร้อมกัน \_\_\_ รายวิชา
>
> ผลเชิงลบนี้มีนัยเชิงปฏิบัติที่ชัดเจน: **สำหรับผู้สอนที่ต้องการนำ AI มาช่วยตรวจงานในรายวิชาเดียว การลงแรงไปที่การออกแบบตัวอย่างอ้างอิงและการชดเชยความเอนเอียงเชิงตัวเลขรายเกณฑ์ ให้ผลตอบแทนต่อหน่วยแรงสูงกว่าการฝึกโมเดลอย่างมีนัยสำคัญ** ระบบที่พัฒนาขึ้นจึงออกแบบให้กลไกดังกล่าวเป็นส่วนหลัก และวางส่วนการฝึกโมเดลไว้เป็นส่วนขยายที่จะเปิดใช้เมื่อข้อมูลสะสมถึงระดับที่วิเคราะห์ไว้แล้วเท่านั้น
>
> ทั้งนี้การทดลองส่วน contextual bandit ซึ่งเป็นการเรียนรู้แบบเสริมกำลังที่นิยาม state, action และ reward ได้ครบถ้วน สามารถดำเนินการได้จนจบและให้ผล \_\_\_

**หมายเหตุถึงคนที่จะเขียนเล่ม:** ย่อหน้านี้**แข็งแรงกว่า**ย่อหน้า *"เราทำ RL แล้วดีขึ้น 3%"* ที่ไม่มี CI มาก เพราะมันตอบคำถามที่มีคนอยากรู้จริง มีตัวเลขประกอบทุกข้ออ้าง และแสดงว่าผู้ทำเข้าใจข้อจำกัดของวิธีที่ตัวเองใช้ · **งานที่รายงานผลเชิงลบอย่างมีระเบียบเป็นที่ยอมรับในวรรณกรรม**
