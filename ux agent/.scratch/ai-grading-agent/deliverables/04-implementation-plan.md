# 0. ข้อเท็จจริงสี่ข้อที่บีบทุกอย่างในแผนนี้

อ่านสี่ข้อนี้ก่อน แล้วทุกการตัดสินใจที่เหลือในเอกสารจะอธิบายตัวเองได้

## 0.1 ภาค 1/2569 ไม่ใช่ช่วงว่างสำหรับเขียนโค้ด แต่เป็นห้องทดลองที่มีของจริงอยู่แล้ว

วิชานี้**เปิดสอนทุกภาค** ภาค 1/2569 จึงมีนักศึกษาจริง มีงานราว 20 ชิ้น × ทั้งห้อง และ**อาจารย์ต้องตรวจอยู่แล้ว**

ถ้าเปลี่ยนวิธีบันทึกจาก "คะแนนรวม" เป็น **"คะแนนรายเกณฑ์ + เวลาที่ใช้ต่อชิ้น"** จะได้ gold set ของงานวิจัยมาแทบฟรี และเป็นข้อมูลที่**ไม่ถูก anchor โดยธรรมชาติ** เพราะยังไม่มี AI ให้ใครเห็น

## 0.2 ของที่เร่งด่วนที่สุดตอนนี้ไม่ใช่โค้ด และเส้นตายคือวันเปิดภาค

**ทุกสัปดาห์ที่ผ่านไปโดยไม่บันทึกรายเกณฑ์ คือข้อมูลที่หายถาวร** เก็บย้อนหลังไม่ได้

**deliverable ชิ้นแรกของทั้งโครงงานจึงเป็นสเปรดชีต ไม่ใช่ซอฟต์แวร์**

## 0.3 ภาคทดลองกับภาคที่ต้องสอบจบเป็นภาคเดียวกัน

ภาค 2/2569 เป็นทั้งภาคที่ใช้ระบบจริงและภาคที่ต้องสอบจบ **มีเฉพาะงานที่ตรวจเสร็จก่อน 31 มี.ค. 2570 เท่านั้นที่เข้าเล่มได้**

→ ตอนเขียนแผนการสอนของภาค 2 **ควรวางชิ้นงาน Figma ที่สำคัญไว้ครึ่งแรกของภาค**

## 0.4 ไม่มีภาคสำรอง — จึงต้องมีการซ้อมใหญ่

ถ้าเปิดใช้จริงครั้งแรกในภาค 2 แล้วพัง จะไม่มีภาคที่สองให้แก้ตัว (โครงงานจบก่อนภาค 1/2570 เปิด)

**การซ้อมใหญ่ปลายภาค 1 (พ.ย.–ธ.ค. 2569) ด้วย 1–2 ชิ้นงานคือแผนสำรองของความเสี่ยงข้อนี้** ถ้าตัดการซ้อมทิ้ง ต้องรู้ตัวว่ากำลังตัดแผนสำรองทิ้งไปด้วย

# 1. เส้นทางวิกฤต — ลำดับที่ห้ามสลับ

```
ตั้งค่ารายวิชา → นำเข้ารายชื่อ → สร้างกิจกรรม + rubric
      → นักศึกษาส่งงาน (แช่แข็งหลักฐานตอนกดส่ง)
      → อาจารย์กด "สั่งตรวจทั้งชุด" (= enqueue + ล็อกการส่ง)
      → AI ตรวจ → อาจารย์ยืนยัน/แก้ → นักศึกษาเห็นคะแนน
      → คะแนนไหลเข้า CLO attainment
```

**ทุกอย่างที่ไม่อยู่บนเส้นนี้คือส่วนขยาย** รวมถึงของที่ออกแบบละเอียดไปแล้วอย่างหน้าจัดการผู้ช่วยสอนและหน้าคัดลอกไปเทอมใหม่

**ทำไม CLO attainment ต่อท้ายได้โดยไม่ทำให้เส้นยาวขึ้นมาก:** มันไม่ใช่ฟีเจอร์ใหม่ แต่เป็นการคำนวณบนข้อมูลที่เส้นนี้ผลิตอยู่แล้ว ต้นทุนจริงอยู่ที่หน้าจอแสดงผลกับช่องกรอกคะแนนสอบ ไม่ใช่ที่ตัวเลข

# 2. Roadmap ห้าช่วง

> **⚠ วันเปิด/ปิดภาคที่ใช้ในเอกสารนี้เป็นค่าประมาณ ต้องยืนยันกับปฏิทินการศึกษา สจล. ตัวจริงก่อนใช้**

## ช่วง 0 — ส.ค. 2569 (~3 สัปดาห์): ของที่เส้นตายคือวันเปิดภาค

| งาน | ใคร | เส้นตาย |
|---|---|---|
| **ยืนยัน rubric ของชิ้นงานแรก ๆ** | **อาจารย์** (1–2 ชม.) | **ก่อนเปิดภาค 1** |
| **แบบฟอร์มบันทึกคะแนนรายเกณฑ์ + ช่องจับเวลา** (สเปรดชีต ไม่ต้องรอระบบ) | ทีม (~1 วัน) | **ก่อนเปิดภาค 1** |
| ทีมอ่าน spec pack แล้ว**แย้งและแก้** | ทีม | ปลาย ส.ค. |
| **ตกลงสัญญา JSON ที่ชั้นกฎคืนกลับมา** | ทีม | **สัปดาห์แรก** |
| **Spike 1:** vLLM บน RTX 5090 (Blackwell) รัน VLM 27–32B แบบ 4-bit ได้จริงไหม | ทีม | **15 ก.ย. 2569** |
| **Spike 2:** Figma API คืนพิกัดที่ปักหมุดหลักฐานได้จริงไหม | ทีม | **15 ก.ย. 2569** |
| เปิดลิงก์ Figma เก่า 5 ชิ้นดูว่ายังเปิดได้ไหม | อาจารย์ (15 นาที) | ก.ย. (ไม่เร่งแล้ว) |

**ทำไมสัญญา JSON ต้องล็อกในสัปดาห์แรก:** เป็นรอยต่อระหว่างคนในทีม ถ้าไม่ล็อก คนสายเว็บกับคนสายตรวจจะบล็อกกันเองทั้งภาค

**ทำไมสอง spike ห้ามเลื่อนไปหลังเริ่มเขียนหน้าจอ:** ถ้า spike ล้ม มันเปลี่ยน**สถาปัตยกรรม** ไม่ใช่เปลี่ยนหน้าจอ — ค้นพบทีหลังแปลว่าโค้ดที่เขียนไปแล้วส่วนหนึ่งต้องทิ้ง

## ช่วง 1 — ก.ย.–ต.ค. 2569: เส้นทางวิกฤตเดินได้ทั้งเส้น

**เป้าหมายเดียว: 31 ต.ค. 2569 เส้นทางวิกฤตเดินได้ตั้งแต่ต้นจนนักศึกษาเห็นคะแนน**

ใช้งานจริงจากภาค 1 ที่กำลังเกิดอยู่เป็นวัตถุดิบทดสอบ · ตรงกับหมุด **P0** ของการทดลอง

**ยังไม่ต้องสวย ยังไม่ต้องมีแดชบอร์ด แต่ฐานข้อมูลต้องถูกตั้งแต่แรก** — โครงการสืบย้อนที่มาของคะแนนและการแช่แข็ง `RubricVersion` **ใส่ทีหลังไม่ได้** เพราะเป็นรูปทรงของข้อมูล ไม่ใช่ฟีเจอร์

## ช่วง 2 — พ.ย.–ธ.ค. 2569: ซ้อมใหญ่ + ปิด gold set

| งาน | หมายเหตุ |
|---|---|
| **ใช้ระบบจริงกับ 1–2 ชิ้นงานสุดท้ายของภาค 1** | ตัวลดความเสี่ยงที่ราคาถูกที่สุดในแผนนี้ |
| gold set จากการตรวจของภาค 1 สะสมครบ | ได้มาจากแบบฟอร์มของช่วง 0 โดยไม่ต้องลงแรงเพิ่ม |
| **ตรวจซ้ำงานเดิม 20–30 ชิ้น ห่างกัน 2–3 สัปดาห์** (~6 ชม.) | **= เพดานมนุษย์ = ตัวหารของทั้งเล่ม** ต้องได้ก่อนปรับอะไรทั้งสิ้น |
| **แช่แข็ง test set 30–40 ชิ้น** | ห้ามแตะจนถึง 31 มี.ค. 2570 |
| ทีมทำ CLO attainment + ช่องกรอกคะแนน + หน้าสรุปความสอดคล้องฉบับย่อ | |

## ช่วง 3 — ม.ค.–ก.พ. 2570: ภาคทดลองจริง ครึ่งแรก

- ใช้ระบบคู่ขนานตั้งแต่**ชิ้นงานแรกของเทอม** ไม่ใช่รอให้ระบบนิ่งก่อน (ซ้อมมาแล้วในช่วง 2)
- **blind 20–30% ของทุกชิ้นงาน + จับเวลาต่อชิ้นทั้งสองโหมด**
- **28 ก.พ. 2570 — หยุดเพิ่มฟีเจอร์** หลังจากนี้แก้ได้เฉพาะบั๊กที่ขวางการเก็บข้อมูล

## ช่วง 4 — มี.ค.–พ.ค. 2570: แช่แข็ง เขียน สอบ

- **31 มี.ค. 2570 — แช่แข็ง เปิด test set ครั้งเดียว**
- **การเขียนเล่มต้องเริ่มตั้งแต่ ม.ค. ไม่ใช่ มี.ค.** — บทวรรณกรรมและบทออกแบบระบบเขียนได้ก่อนมีผล เพราะเนื้อหาอยู่ในเอกสารวิจัยและ spec pack ครบแล้ว **เหลือแค่บทผลการทดลองที่ต้องรอตัวเลข**

# 4. สองกับดักของการใช้ระบบคู่ขนานกับ Excel

## 4.1 กับดักที่ 1 — คู่ขนานไม่ได้แปลว่ามีคะแนนสองชุด

ถ้าปล่อยไว้ลอย ๆ ระบบจะมีคะแนนชุดหนึ่ง Excel มีอีกชุดหนึ่ง แล้วนักศึกษาเห็นตัวเลขไม่ตรงกัน — **เป็นความเสียหายที่ตกกับนักศึกษา ไม่ใช่ความไม่สะดวกของทีม**

**กฎที่ต้องล็อก: ทิศทางการคัดลอกเป็นทางเดียว — ระบบ → Excel เท่านั้น**

1. อาจารย์ตรวจและ**ยืนยันคะแนนในระบบก่อนเสมอ**
2. คัดลอกออกไป Excel
3. **ห้ามแก้คะแนนใน Excel โดยไม่ย้อนกลับมาแก้ในระบบ**

ถ้าทำกลับทางหรือแก้สองที่ ระบบจะเก็บข้อมูลที่ไม่ตรงกับสิ่งที่เกิดขึ้นจริง แล้ว**ตัวเลข agreement ทั้งหมดของงานวิจัยจะวางอยู่บนข้อมูลที่ผิด**

**ผลที่ไม่คาดคิดของกฎนี้:** มันดึง **ปุ่ม "คัดลอกสามคอลัมน์" กลับเข้า MVP** เพราะเป็นสะพานไป Excel · ส่วน**การดาวน์โหลดไฟล์ .xlsx/CSV ไม่ต้องมีใน MVP** เพราะในภาคทดลองไม่มีใครส่งไฟล์นั้นให้ใคร

## 4.2 กับดักที่ 2 — คู่ขนานทำให้ภาระอาจารย์ "เพิ่ม" ไม่ใช่ลด

ในภาค 2/2569 อาจารย์จะตรวจงานในระบบ **บวก**ดูแล Excel **บวก**ตรวจแบบ blind อีก 20–30% ของทุกชิ้นงาน

> **โครงงานนี้พิสูจน์ "ลดเวลาอาจารย์ทั้งเทอม" ไม่ได้ในภาคทดลองของตัวเอง** ถ้าเขียนในเล่มว่าลดได้ จะเป็นการเคลมที่**ข้อมูลของตัวเองขัดอยู่**

**สิ่งที่วัดได้จริงและต้องวัดแทน: เวลาต่อชิ้น** ในสองโหมด — ตรวจโดยเห็นข้อเสนอของ AI พร้อมหลักฐาน เทียบกับตรวจแบบ blind ที่ไม่เห็นอะไรเลย

ข้อมูลนี้**ได้มาฟรีจากโปรโตคอลที่ตกลงกันไว้อยู่แล้ว** เพราะทำ blind 20–30% อยู่แล้วด้วยเหตุผลอื่น เพียงแต่ต้องจับเวลาทั้งสองโหมด

→ **ระบบต้องจับเวลาที่ใช้ตรวจต่อชิ้นตั้งแต่ MVP** (ฟิลด์ `seconds_spent`)

→ **การเคลมของโครงงานเปลี่ยนจาก "ลดภาระอาจารย์" เป็น "ที่ความแม่นเท่านี้ ใช้เวลาต่อชิ้นเท่านี้"** ซึ่งคนอ่านต่อยอดเองได้และไม่มีทางถูกจับผิด

**ของแถมที่หาไม่ได้อีกหลังจากนี้:** ถ้าภาค 1 บันทึกเวลาที่ใช้ตรวจด้วยมือไว้ด้วย (แค่ช่องเดียวในแบบฟอร์ม) โครงงานจะได้ **baseline เวลาต่อชิ้นแบบไม่มีระบบช่วยเลย** ซึ่งเป็นตัวเทียบที่มีค่าที่สุดของงานทั้งเล่ม

# 5. แผนสำรองของความเสี่ยงหลัก

## R1 — กลางภาค 2 แล้ว AI ยังตรวจได้ไม่ดีพอ

**ไม่ใช่ความล้มเหลว ถ้าเตรียมกรอบไว้ก่อน** — คำถามวิจัยถูกวางเป็น**เส้นโค้ง** ซึ่งเป็นผลการทดลองทั้งตอนชันและตอนแบน และ H3 ทำนายล่วงหน้าแล้วว่า CI จะคร่อมศูนย์

**และมีของที่ส่งได้แม้ตัวเลขไม่สวย โดยไม่ต้องทำอะไรเพิ่ม:**

> **ชั้นกฎที่คำนวณได้แบบ deterministic ไม่พึ่งความแม่นของ LLM เลย** รวมกับสมุดคะแนน + CLO attainment + การสืบย้อนที่มา = **ระบบที่ใช้งานได้จริงและมีคุณค่าต่อรายวิชา แม้ชั้น LLM จะให้คะแนนไม่แม่น**

→ ทีมควรรู้ตั้งแต่วันนี้ว่า**ชั้นกฎคือตัวประกันความสำเร็จของโครงงาน ไม่ใช่ของแถมของชั้น LLM** เพราะมันเปลี่ยนลำดับความสำคัญของงาน

## R2 — Figma API ไม่คืนพิกัดที่ปักหมุดได้

**ถอยเป็นขั้น ไม่ใช่ล้มทั้งฟีเจอร์**

1. **หลักฐานอ้างชื่อ frame/layer เป็นข้อความ** — Figma API ให้แน่นอน ตรวจสอบด้วยตาได้ แค่ไม่ชี้จุดบนภาพ
2. สาย PDF ใช้หน่วยหลักฐานเป็น **หน้า + ช่อง** ซึ่งไม่กระทบเลย
3. ถ้าถอยจริง **ต้องแก้ต้นแบบหน้าจอตรวจงาน** เพราะหน้านั้นวางอยู่บนสมมติฐานว่ามีหมุด

## R3 — infra คณะไม่รองรับ (Blackwell / vLLM)

1. ลดขนาดโมเดลเป็น 7–12B แล้วยอมรับว่าความแม่นตกลง — **รายงานเป็นผลของข้อจำกัดฮาร์ดแวร์ ซึ่งเป็นผลที่มีค่าในตัวมันเอง**
2. ใช้ LLM API ระหว่างพัฒนา **แต่ต้องมีเพดานงบที่หยุดเรียกเองเมื่อชน** เพราะอาจารย์ออกค่าใช้จ่ายเอง
3. ชั้นเชื่อมต่อ LLM ออกแบบให้**สลับผู้ให้บริการได้**อยู่แล้ว — ความเสี่ยงนี้ถูกลดไปแล้วตั้งแต่ตอนตัดสินสถาปัตยกรรม

## R4 — ระบบพังในภาคทดลอง

ภาค 2 ไม่มีภาคสำรอง → **การซ้อมใหญ่ปลายภาค 1 คือแผนสำรองของความเสี่ยงข้อนี้**

# 6. การแบ่งงานในทีม

**รอยต่อคือสัญญา JSON ที่ชั้นกฎคืนกลับมา** ล็อกในสัปดาห์แรกแล้วทั้งสามคนเดินขนานกันได้

| คน | รับผิดชอบ | ได้บทไหนในเล่ม |
|---|---|---|
| **A — สายเว็บ** | รายวิชา · รายชื่อ · rubric · ส่งงาน · หน้าจอตรวจแบบ A · หน้าคะแนนนักศึกษา | ออกแบบระบบและส่วนติดต่อผู้ใช้ |
| **B — สายตรวจ** | ตัวอ่าน Figma/PDF · ชั้นกฎ · ชั้น LLM + vLLM · คิวงาน · การแช่แข็งหลักฐาน | สถาปัตยกรรมการตรวจด้วย AI |
| **C — สายวัดผล** | pipeline gold set · QWK/MAE/เพดานมนุษย์ · หน้าสรุปความสอดคล้อง · การทดลองทั้งหมด | **บทผลการทดลองทั้งบท** |

**งานของช่วง 0 (แบบฟอร์มบันทึกคะแนน) เป็นของคน C และเป็นชิ้นแรกที่ต้องเสร็จของทั้งโครงงาน**

**ถ้าทีมมี 2 คน:** ยุบ C เข้า B แล้ว**ตัดสาย preference learning ทิ้งตั้งแต่วันนี้** ไม่ต้องรอหมุด 31 ธ.ค. — เพราะมันกินเวลาคนเต็มคน และเป็นสายที่แผนการทดลองบอกเองว่าตัดได้โดยโครงงานยังครบ
