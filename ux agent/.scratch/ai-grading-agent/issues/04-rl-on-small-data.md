## Question

ข้อ 13 ของโจทย์ขอ "ระบบ RL เพื่อปรับ AI Agent ให้ทำงานดีขึ้น" — บนข้อมูลจริงที่มีอยู่ (คะแนนอาจารย์หลักสิบถึงหลักร้อยชิ้นต่อเทอม) RL รูปแบบใดเป็นไปได้บ้าง และรูปแบบใดเป็นไปไม่ได้ในเชิงปฏิบัติ?

ต้องการคำตอบที่ครอบคลุม

1. **ภูมิทัศน์ของวิธีการ** — RLHF (PPO), DPO, ORPO, KTO, GRPO, RLAIF, best-of-n / rejection sampling — แต่ละวิธีต้องการข้อมูลกี่ตัวอย่าง ต้องการ GPU แค่ไหน และให้ผลลัพธ์อะไร
2. **Reward model จากคะแนนอาจารย์** — เทรน reward model จากคู่ (ชิ้นงาน, คะแนน) หรือจากคู่เปรียบเทียบ (งาน A ดีกว่า B) ต้องใช้ข้อมูลเท่าไรจึงจะไม่ overfit; มีงานที่ทำสำเร็จบนข้อมูลระดับร้อยไหม
3. **ทางเลือกที่เบากว่า RL เต็มรูปแบบ** — contextual bandit สำหรับเลือก prompt/rubric variant, multi-armed bandit สำหรับเลือกกลยุทธ์การตรวจ, online learning ที่อัปเดตทีละตัวอย่าง — วิธีเหล่านี้ให้เรื่องเล่าเชิง RL ที่ถูกต้องตามหลักวิชาโดยใช้ข้อมูลน้อยกว่ามากหรือไม่
4. **LoRA / PEFT บนโมเดลเปิดขนาดเล็ก** — ต้นทุนจริง (GPU ชั่วโมง, VRAM) ของการ fine-tune โมเดลระดับ 7B-8B; ทำบน Colab/Kaggle ฟรีได้ไหม; คุณภาพเทียบกับโมเดล frontier ที่ใช้ prompt ดี ๆ
5. **การกำหนดปัญหาให้เป็น RL อย่างซื่อสัตย์** — ถ้าจะเรียกว่า RL ต้องมี state/action/reward อะไร; การเรียก "loop ที่ปรับ prompt จาก feedback" ว่า RL เป็นการใช้คำเกินจริงหรือไม่ และวรรณกรรมเรียกมันว่าอะไร (self-refine, reflection, textual gradient)
6. **งานวิจัยที่ใช้ RL กับ automated scoring โดยเฉพาะ** — มีไหม ผลเป็นอย่างไร
7. **คำแนะนำเชิงปฏิบัติ** — สำหรับ senior project 1 ปี ทีม 2-3 คน ที่ต้องส่งงานทันกำหนด: RL แบบใดคุ้มค่าที่จะทดลอง และแบบใดควรอยู่แค่ในบท "งานในอนาคต"

เน้นแหล่งปฐมภูมิ: arXiv, เอกสาร TRL/Unsloth/peft, model cards

## หมายเหตุบริบท

ข้อสรุปของ charting session คือ RL เป็น **experiment ที่ล้มได้** ไม่ใช่ฟีเจอร์ที่ต้อง ship — ticket นี้ต้องให้ข้อมูลพอที่จะออกแบบการทดลองที่มีโอกาสสำเร็จใน ticket 16

## Answer

ผลการวิจัยฉบับเต็ม **550 บรรทัด ครบทั้ง 7 หัวข้อ** อยู่ที่ [`research/04-rl-small-data.md`](../research/04-rl-small-data.md) — อ่านบทสรุปผู้บริหารตอนต้นไฟล์ก่อน แล้วค่อยเจาะหัวข้อที่ต้องใช้ ด้านล่างคือข้อสรุปที่ ticket อื่น ๆ ต้องใช้เป็นข้อมูลตั้งต้น

### 1. อะไรทำได้ อะไรทำไม่ได้ — ตัดสินแล้ว

| ทำได้แน่ | ทำได้ถ้าเก็บข้อมูลขยัน | ทำไม่ได้ (ปิดตาย) |
|---|---|---|
| prompt/rubric optimization (OPRO/GEPA-style) · best-of-n at inference · **contextual bandit** | KTO / ORPO + QLoRA บนโมเดล ≤ 8B ในฐานะ **experiment** | **reward model + PPO** (ต้องการ ≥ 10,000 คู่เปรียบเทียบ) · **GRPO เต็มรูป** (RLAES ใช้ essay 12,978 ชิ้น + A100/H20 แปดใบ) |

เหตุผลไม่ใช่เรื่องฝีมือ แต่เป็นเรื่องขนาด — โครงงานนี้ห่างจากงานที่ทำสำเร็จ **สองอันดับของขนาด** ทั้งแกนข้อมูลและแกนคอมพิวต์

### 2. ตัวเลขข้อมูลที่ต้องนับให้ถูก (ใช้กับ ticket 15 และ 16 โดยตรง)

| หน่วย | ปริมาณต่อเทอม | หมายเหตุ |
|---|---|---|
| คู่คะแนนระดับเกณฑ์ (ดิบ) | 1,600–3,360 | **หลอกตา** — สหสัมพันธ์กันสูงมาก |
| ชิ้นงานที่ถูกตรวจ | 320–480 | หน่วยของ bandit |
| **นักศึกษา (คลัสเตอร์อิสระ)** | **40–60** | **หน่วยที่กำหนดกำลังทางสถิติจริง และต้องใช้แบ่ง train/test** |
| **คู่คะแนนจาก blind mode** | **330–1,000** | **ตัวจำกัดจริงของโครงงาน** |

ประตูข้อมูล G0–G6 พร้อมเกณฑ์ตัวเลขและที่มาอยู่ใน §7.2.3

### 3. RL ตัวจริงตัวเดียวที่แผนนี้รับประกัน = contextual bandit

เลือก 1 จาก K grading strategy ด้วย Thompson sampling / LinUCB — มี state/action/reward/policy ครบตามนิยาม MDP (§5.4) ใช้ข้อมูลแค่ **≥ 30 observation ต่อ arm, K ≤ 6** และ **ไม่ต้องส่ง gradient เข้า LLM เลย**

**ข้อควรระวังที่ ticket 16 ต้องรับไป:** reward เป็น non-stationary เพราะ rubric เปลี่ยนเวอร์ชันได้ (ticket 10) → bandit ต้องเป็น **sliding-window** และทุกคู่คะแนนต้องผูก `rubric_version` ตั้งแต่วันแรก

### 4. เส้นแบ่งคำศัพท์ที่ต้องเขียนให้ตรงในเล่ม

- "loop ที่ปรับ prompt จาก feedback" = **self-refine / reflection / textual gradient** — **ไม่ใช่ RL** เรียกว่า RL เมื่อไรกรรมการจับได้ทันที
- **bandit = RL จริง** แต่ต้องเขียน MDP ครบทุกองค์ประกอบตาม §5.4
- และวรรณกรรมล่าสุดยืนยันเองว่าเส้นทางไม่เทรนไม่ได้ด้อยกว่า: **GEPA ชนะ GRPO เฉลี่ย 6% สูงสุด 20% โดยใช้ rollout น้อยกว่า 35 เท่า**

### 5. แผนหนึ่งปี P0–P4 (รายละเอียดใน §7.1)

P0 instrumentation + **แช่แข็ง test set ก่อนแตะ prompt ใด ๆ** (ไม่เทรน) → P1 prompt optimization + best-of-n (ไม่เทรน — **นี่คือ calibration loop ที่ต้อง ship**) → P2 contextual bandit → P3 KTO/ORPO **timebox แข็ง 4 สัปดาห์ ยอมล้มได้** → P4 เขียนเล่ม

**ตัด P3 ทิ้งทั้งหมดแล้วโครงงานยังครบ ยังมีองค์ประกอบ RL และยังสอบผ่าน** — นี่คือคุณสมบัติที่ตั้งใจออกแบบ ไม่ใช่แผนสำรอง

### 6. การวัดผลที่ห้ามพลาด (§7.3)

- QWK เพียงตัวเดียวไม่พอ — มี kappa paradox / prevalence effect (Doewes, Kurdhi & Saxena, EDM 2023) ต้องรายงาน 6 เมตริกพร้อมกัน
- **leakage 4 แหล่ง**: นักศึกษาคนเดียวกัน · งานกลุ่มเดียวกัน · criterion rows ของ submission เดียวกัน · โจทย์ซ้ำข้ามเทอม → ต้องใช้ **GroupKFold + cluster bootstrap ที่ระดับนักศึกษา**
- baseline ที่ต้องเทียบคือ **B4 (prompt ที่ optimize แล้ว)** ไม่ใช่ B3 — ถ้าเทียบผิด ตัวเลขจะสวยแบบไม่มีความหมาย
- **เพดานมนุษย์ต้องวัดเองกับอาจารย์จริง** เป้าคือ "QWK ระบบ ≥ 80% ของ QWK ระหว่างมนุษย์" ไม่ใช่ตัวเลขคงที่จากเปเปอร์

### 7. Anchoring — จุดที่เชื่อมกลับ ticket 12 โดยตรง

ถ้าอาจารย์เห็นคะแนน AI ก่อนตรวจ **ช่องที่ไม่ถูกแก้ไม่ได้แปลว่าเห็นด้วย** ข้อมูลทั้งชุดจะเอนเข้าหาคำตอบของ AI แล้วทุกเมตริกจะดีขึ้นโดยที่ระบบไม่ได้เก่งขึ้น

**ข้อสรุปเชิงออกแบบ: blind mode 20–30% ของทุกชิ้นงาน (ไม่ใช่ blind ทั้งชิ้นงานแรกแล้วเลิก) เป็นเงื่อนไขที่ทำให้ผลการทดลองทั้งโครงงานมีความหมาย ต้องมีตั้งแต่ P0** — ตรงกับกลไก `seeded_from_assessment_id` / `teacher_touched` ที่ตัดสินไว้แล้วใน ticket 12

งานวิจัยยังเสนอให้ **"วัด anchoring effect" เป็น contribution ของโครงงานเอง** ซึ่งเป็นผลงานที่ได้แน่นอนไม่ว่า RL จะสำเร็จหรือไม่

### 8. เกณฑ์ยกเลิกและการเขียนเล่มทั้งสองทาง

K1–K9 วัดได้ทุกข้อ (§7.4) เช่น milestone เลื่อน > 2 สัปดาห์ · ชั่วโมงที่ลงกับ RL > 25% ของเวลาทีม · deadline แข็ง 1 มี.ค. 2027 · CI คาบเกี่ยว · ถดถอย 2 ครั้งติด · พบ reward hacking · **ระบบหลักแย่ลง**

§7.6 แจกแจงสิ่งที่เขียนลงเล่มได้ทั้งกรณีสำเร็จและไม่สำเร็จ พร้อมเปเปอร์รองรับล่วงหน้าสำหรับผลลบ (arXiv:2603.20100, 2210.10760, 2310.01798) → **"ข้อมูลหลักร้อยไม่พอ" เป็น negative result ที่มีหลักฐาน ไม่ใช่ "ทำไม่ทัน"**

### 9. งบคอมพิวต์ (§7.5)

P3 QLoRA 7–8B บน T4 ≈ 1–3 ชม./รอบ × ≥ 6 รอบ ≈ **10–25 ชม. GPU** พอดีโควตา Kaggle หนึ่งสัปดาห์ · ใช้ **Kaggle เป็นเครื่องหลัก** เพราะ Colab ไม่รับประกันรุ่น GPU

### 10. ส่งต่อ

- **ticket 15 (ระบบทดสอบ rubric)** — blind mode 20–30% ต่อชิ้นงาน, การแช่แข็ง test set, และเมตริกทั้ง 6 ตัวเป็นข้อกำหนดของหน้าจอนี้
- **ticket 16 (ออกแบบการทดลอง RL)** — ใช้แผน P0–P4, ประตู G0–G6, kill criteria K1–K9 เป็นโครงตั้งต้น และรับข้อจำกัด sliding-window bandit ไปด้วย
- **ticket 09/17** — best-of-n at inference เป็นของที่ต้อง ship ไม่ใช่ของทดลอง
- **การเขียนเล่ม** — §5.2/§5.3 คือส่วนที่ต้องคัดลอกไปเป็นบท "ข้อจำกัดและการนิยามปัญหา" เพื่อกันคำถามกรรมการเรื่องการใช้คำว่า RL

### สิ่งที่ยังต้องยืนยันด้วยของจริง

- ตัวเลข human agreement ของ ASAP (QWK ≈ 0.72–0.85) มาจากแหล่งทุติยภูมิ **ยังไม่ได้ตรวจกับเอกสารต้นทาง** (กำกับไว้ในไฟล์แล้ว)
- เวลาต่อรอบทดลองใน §7.5.2 เป็นประมาณการเชิงวางแผน ต้องแทนที่ด้วยผล smoke test จริง
