## Question

เซิร์ฟเวอร์/โครงสร้างพื้นฐานของคณะที่ระบบนี้ต้องไปอยู่ ให้อะไรได้บ้าง?

สถาปัตยกรรมทั้งหมด (ticket 17) แขวนอยู่กับคำตอบนี้ ไม่มีอะไรให้ตัดสินใจใน ticket นี้ — มีแต่ข้อเท็จจริงที่ต้องไปเก็บมา

## Checklist ที่ต้องได้คำตอบ

**เครื่องและระบบปฏิบัติการ**
- [ ] OS อะไร เวอร์ชันไหน / เป็น VM, container host, หรือ bare metal
- [ ] CPU / RAM / พื้นที่ดิสก์ที่จัดสรรให้ได้
- [ ] มี GPU ไหม (ถ้ามี รุ่นอะไร VRAM เท่าไร) — กระทบ ticket 16 โดยตรง

**GPU Server ของภาควิชา** *(อาจารย์ยืนยัน 2026-08-06 ว่ามี — ticket 16 ต้องการรายละเอียดต่อไปนี้)*
- [ ] **VRAM ต่อการ์ด และจำนวนการ์ด** — ตัวเลขนี้ตัดสินว่าสาย D (fine-tune) ทำได้แค่ไหน: 16 GB = QLoRA 7–8B · 24 GB = QLoRA 13B (จุดที่คุ้มที่สุด) · 40 GB+ = เกินความจำเป็น
- [ ] จองใช้ต่อเนื่องได้ครั้งละกี่ชั่วโมง มีคิวแย่งกับงานอื่นไหม (ต้องการ **25–70 ชม.รวม** กระจายตลอดภาค 2)
- [ ] **เครื่องออกอินเทอร์เน็ตได้ไหม** — ต้องโหลด model weight จาก HuggingFace ครั้งละหลายสิบ GB ถ้าออกไม่ได้ต้องหาวิธีขนไฟล์เข้าไป
- [ ] CUDA / driver version · มี Docker หรือ conda ให้ใช้ไหม

- [ ] **แม้มี GPU แล้วก็ยังต้องมีงบ LLM API ก้อนเล็ก** สำหรับ baseline B2/B3 และการตรวจจริง (ticket 14: ~240 calls/ชิ้นงาน) — ถามด้วยว่ามีงบส่วนนี้จากไหน

**สิทธิ์และการติดตั้ง**
- [ ] นักศึกษา/อาจารย์มีสิทธิ์ root หรือ sudo ไหม
- [ ] ติดตั้ง Docker / Docker Compose ได้ไหม
- [ ] ถ้าไม่ได้ ติดตั้ง runtime อะไรได้บ้าง (Node.js, Python, PHP, Java) เวอร์ชันไหน
- [ ] มี reverse proxy กลาง (nginx/Apache) ที่ต้องผ่านไหม

**เครือข่าย**
- [ ] **เครื่องออกอินเทอร์เน็ตขาออกได้ไหม** — จำเป็นมาก เพราะต้องเรียก LLM API และ Figma API; ถ้าออกไม่ได้เลย โครงงานต้องเปลี่ยนสถาปัตยกรรมทั้งหมด
- [ ] ถ้าออกได้ ต้องผ่าน proxy ไหม ต้อง whitelist domain ล่วงหน้าไหม
- [ ] เข้าถึงจากนอกเครือข่ายคณะได้ไหม (นศ. ส่งงานจากบ้าน)

### 1. GPU: 5090 32 GB คือของดีเกินคาด แต่มีความเสี่ยงด้านซอฟต์แวร์

**สิ่งที่ 32 GB ต่อการ์ดเปิดให้ทำได้** (ตัวเลขประมาณ ต้อง spike ยืนยันจริง):

- โมเดล **vision-language** ระดับ 27–32B แบบ quantize 4-bit รันได้บนการ์ดเดียวพร้อม KV cache เหลือพอ — สำคัญมากเพราะงาน UX/UI ที่ต้องตรวจเป็น**ภาพ** ไม่ใช่ข้อความ โมเดลที่ตรวจงานได้จริงจึงต้องเป็น VLM ไม่ใช่ LLM ธรรมดา
- **QLoRA fine-tune ระดับ 13B ได้สบาย และน่าจะถึง 32B ได้ด้วย** — เดิมประเมินไว้ว่า 24 GB คือจุดคุ้มสุด ของจริงเกินไปหนึ่งขั้น
- **พ่วง 2 การ์ด = 64 GB** เปิดทางรันโมเดลใหญ่ขึ้นหรือ quantize หยาบน้อยลง (คุณภาพดีขึ้น) — แต่ 5090 **ไม่มี NVLink** ทั้งสองการ์ดคุยกันผ่าน PCIe ซึ่งช้ากว่า เหมาะกับ inference มากกว่า training แบบกระจาย

**ความเสี่ยงที่ต้องเขียนไว้ในเล่ม:** 5090 เป็นสถาปัตยกรรม Blackwell ซึ่งใหม่ ต้องใช้ CUDA และ PyTorch เวอร์ชันค่อนข้างใหม่ ไลบรารีบางตัวในสาย quantization/serving ตามไม่ทันในช่วงแรก — **ต้องมี spike ยืนยันว่า stack ที่เลือกรันบนการ์ดนี้ได้จริงก่อนล็อกสถาปัตยกรรม** ไม่ใช่สมมติว่าได้ (ticket 17)

**ยังไม่รู้และต้องถามต่อ:** GPU อยู่ในเครื่องเดียวกับ VM ที่ให้กลุ่มละ 1 ตัวหรือเป็นคนละเครื่อง — ถ้าคนละเครื่อง สถาปัตยกรรมต้องแยกเป็น *เว็บแอปบน VM* + *บริการ inference บนเครื่อง GPU* คุยกันผ่านเครือข่ายภายใน ซึ่งเป็นคนละแบบกับการรันรวมกันในเครื่องเดียว

### 2. ค่า API ที่อาจารย์ออกเอง — ข้อจำกัดใหม่ที่ต้องออกแบบรับ

นี่คือสิ่งที่เปลี่ยนไปจากแผนเดิมมากที่สุด เดิมสมมติว่าค่า API เป็นต้นทุนที่ไม่ต้องคิดมาก ตอนนี้กลายเป็น**เงินส่วนตัวของอาจารย์** และมีเงื่อนไขว่า "ไม่มาก ไม่ประจำ"

**ประมาณการคร่าว ๆ (ต้องวัดจริงด้วย spike ก่อนเชื่อ):**

- การตรวจจริงทั้งเทอม — ราว 300–400 หน่วยการตรวจ (48 คน แต่งานกลุ่มยุบเหลือ ~13 กลุ่ม) คูณ 2–3 calls ต่อหน่วย ที่มีภาพประกอบ → **หลักพันบาทต่อเทอม** ซึ่งยังพออยู่ในนิยาม "ไม่มาก"
- **ส่วนที่ทำให้บานคือการทดลอง** — baseline หลายตัวคูณจำนวนรอบซ้ำ คูณ gold set ทั้งชุด การรันซ้ำเพื่อวัด variance คือธรรมชาติของงานวิจัย และมันคือ "ประจำ" ตามนิยามของอาจารย์พอดี

**ข้อเสนอที่ตามมาโดยตรง — แบ่งงานตามแหล่ง:**

| งาน | รันที่ไหน | เหตุผล |
|---|---|---|
| ตรวจงานจริงทั้งเทอม | **โมเดลเปิดบน 5090** | ปริมาณมาก ทำซ้ำทุกสัปดาห์ = "ประจำ" ต้องไม่เสียเงินต่อครั้ง |
| ทดลอง baseline / วัด variance / รันซ้ำ | **โมเดลเปิดบน 5090** | ส่วนที่บานที่สุด และเป็นส่วนที่ GPU มีไว้เพื่อการนี้ |
| **เทียบกับโมเดลระดับบนสุด** (จุดอ้างอิงว่าโมเดลเปิดห่างแค่ไหน) | **LLM API แบบจ่ายเงิน** | ครั้งเดียวจบต่อรอบการทดลอง ไม่ประจำ ตรงเงื่อนไขอาจารย์พอดี |
| งานที่โมเดลเปิดทำไม่ไหวจริง ๆ | API เป็นรายกรณี | ต้องมีเพดานกันบาน |

**ข้อกำหนดใหม่ของระบบที่เกิดจากข้อนี้:** ต้องมี **ตัวนับต้นทุนและเพดานงบ** — บันทึกทุก call ว่าใช้ token เท่าไร คิดเป็นเงินเท่าไร รวมยอดต่อเดือน และ**หยุดเรียก API อัตโนมัติเมื่อชนเพดานที่ตั้งไว้** ไม่ใช่ให้ไปรู้ตอนได้บิล → ต้องเพิ่มใน ticket 17 และมีที่อยู่บนหน้าจอตั้งค่ารายวิชา (prototype หน้าจอ 02)

### 3. ผลต่อตั๋วอื่น

- **ticket 17 (สถาปัตยกรรม) — ปลดล็อกแล้ว** แต่ขอบเขตกว้างขึ้น: ต้องออกแบบสองเลเยอร์ (เว็บแอปบน VM + บริการ inference บน GPU) และต้องมีชั้นนับต้นทุน
- **ticket 18 (PDPA) — ปลดล็อกแล้ว** และง่ายลงมาก เพราะระเบียบอนุญาตให้ส่งข้อมูลออกได้อยู่แล้ว · แต่ควรเขียนไว้ว่าทางเลือก "ประมวลผลในเครื่องคณะทั้งหมด" มีอยู่จริงและใช้ได้ ซึ่งเป็นจุดแข็งที่เขียนลงเล่มได้
- **ticket 16 (การทดลอง RL) — สาย D (fine-tune) ไม่ตกแล้ว** 32 GB เกินเกณฑ์ที่ ticket 04 ตั้งไว้ · แต่ต้องเพิ่มความเสี่ยงเรื่องความใหม่ของ Blackwell เข้าไปในหัวข้อ risk
- **ticket 23 (ขอบเขต MVP)** — ยังบล็อกด้วย 17 ซึ่งตอนนี้เดินต่อได้แล้ว
