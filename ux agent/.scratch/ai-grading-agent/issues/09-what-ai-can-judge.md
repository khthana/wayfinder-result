# 09 — AI ตรวจอะไรในงาน UX/UI ได้จริง และอะไรที่ตรวจไม่ได้

Type: grilling
Status: resolved
Blocked by: 01, 02

## Question

ถ้าไม่โกหกตัวเอง AI ตรวจอะไรในงาน UX/UI ได้ดีพอที่จะเชื่อถือ และอะไรที่ต้องปล่อยให้อาจารย์ตัดสินเสมอ?

โจทย์เขียนว่า "ใช้ AI Agent ช่วยตรวจงาน" เหมือนเป็นเรื่องเดียว แต่จริง ๆ เกณฑ์แต่ละข้อมีความยากไม่เท่ากันคนละโลก — contrast ratio คำนวณได้แม่นยำ 100% จากข้อมูล Figma โดยไม่ต้องใช้ LLM เลย ขณะที่ "งานออกแบบนี้เหมาะกับกลุ่มผู้ใช้เป้าหมายหรือไม่" AI แทบตัดสินไม่ได้ ถ้าไม่แยกสองอย่างนี้ออกจากกัน ระบบจะให้คะแนนที่ดูน่าเชื่อถือแต่ไม่มีความหมาย และอาจารย์จะเลิกใช้ภายในเทอมเดียว

## สิ่งที่ต้องตัดสิน

1. **จัดชั้นเกณฑ์ตามความสามารถของ AI** — เอาเกณฑ์ที่ใช้จริงในวิชามาจัดเป็น 3 ชั้น
   - **ชั้นที่ 1 ตรวจได้ด้วยกฎ ไม่ต้องใช้ LLM** — เช่น contrast ตาม WCAG, จำนวนขนาดตัวอักษรที่ใช้, ความสม่ำเสมอของระยะห่าง, การมี/ไม่มี artboard ที่กำหนด, จำนวนหน้าจอ, การตั้งชื่อ layer
   - **ชั้นที่ 2 LLM ตรวจได้ดีพอ ถ้าให้หลักฐานครบ** — เช่น ความสอดคล้องของ user flow กับ persona ที่ นศ. เขียนเอง, การมีองค์ประกอบครบตามที่โจทย์กำหนด, ความชัดเจนของ information hierarchy, คุณภาพการเขียนอธิบายเหตุผล
   - **ชั้นที่ 3 ต้องให้อาจารย์ตัดสิน** — เช่น ความคิดสร้างสรรค์, ความเหมาะสมกับบริบทวัฒนธรรม, ความก้าวหน้าเทียบกับตัวนักศึกษาเอง
2. **สัดส่วนที่ยอมรับได้** — ถ้าเกณฑ์ชั้นที่ 3 กินคะแนนเกินครึ่ง คุณค่าของระบบจะเหลือน้อย ต้องคุยกันว่ายอมรับสัดส่วนเท่าไร และจะออกแบบ rubric ให้ AI ช่วยได้มากขึ้นโดยไม่บิดเบือนเจตนาการสอนได้อย่างไร
3. **AI ต้องแสดงอะไรประกอบคะแนน** — คะแนนเปล่า ๆ อาจารย์เชื่อไม่ได้และตรวจซ้ำไม่ได้ ต้องตัดสินว่าทุกคะแนนต้องมาพร้อม (ก) เหตุผลเป็นข้อความ (ข) หลักฐานอ้างอิงถึงจุดในชิ้นงาน (หน้าไหน frame ไหน) (ค) ระดับความมั่นใจ — อะไรบังคับ อะไรไม่บังคับ
4. **AI ปฏิเสธการตรวจได้ไหม** — ถ้าไฟล์เปิดไม่ได้ ส่งผิดรูปแบบ หรือชิ้นงานไม่เข้าเกณฑ์เลย ระบบควรตอบว่าอะไร (ให้ 0? ตีกลับ? ส่งต่ออาจารย์?)
5. **หน่วยของการตรวจ** — ตรวจทีละเกณฑ์แยกกัน (หลาย call) หรือตรวจทั้ง rubric ในครั้งเดียว — มีผลต่อคุณภาพ ต้นทุน และการ trace

## สิ่งที่ต้องได้เมื่อจบ ticket

- ตารางจัดชั้นเกณฑ์ 3 ชั้น พร้อมตัวอย่างเกณฑ์จริงจากวิชา
- ข้อกำหนดว่าผลการตรวจหนึ่งชิ้นต้องประกอบด้วยอะไรบ้าง (จะกลายเป็น data structure ใน ticket 12 และหน้าจอใน ticket 21)
- นโยบายเมื่อ AI ตรวจไม่ได้

## Answer

### สถาปัตยกรรมการตรวจ: สองชั้นที่แยกขาดจากกัน

**ชั้นที่ 1 — ตัววิเคราะห์เชิงกฎ (deterministic analyzer)**
เขียนเป็นโค้ดล้วน คำนวณจาก JSON ของ Figma ไม่มี LLM เกี่ยวข้อง ผลลัพธ์ทำซ้ำได้ 100% นักศึกษาอุทธรณ์ได้ และไม่มีค่าใช้จ่ายต่อครั้ง
**ชั้นที่ 2 — ผู้ตัดสินด้วย LLM**
รับ *ทั้ง* ภาพ render และ metrics JSON จากชั้นที่ 1 ไปตัดสินเกณฑ์ที่ต้องตีความ

**LLM ไม่แตะเกณฑ์ที่ชั้นที่ 1 ตรวจได้** — ไม่ให้คะแนนซ้ำ ไม่ override
เหตุผล: คะแนนนิ่ง ทำซ้ำได้เท่ากันทุกรอบ อธิบายได้ถึงระดับจุดที่ผิด และประหยัด token
ราคาที่ยอมจ่าย: ทีมต้องเขียนตัววิเคราะห์เอง และตอนสร้าง rubric ต้องระบุทุกหัวข้อว่าเป็นชั้นไหน

> **ห้าม** ให้ LLM นับเองจากภาพ (นับจำนวนขนาดฟอนต์ วัด contrast) — ทั้งช้า แพง และไม่นิ่ง ทั้งที่โค้ดคำนวณได้แม่นกว่า

### ตารางจัดชั้นเกณฑ์

**ชั้นที่ 1 — โค้ดให้คะแนน (43 สัญญาณจาก ticket 02 หัวข้อ 14)**

| กลุ่ม | ตัวอย่างสัญญาณ | ใช้เป็นหัวข้อประเมินได้เช่น |
|---|---|---|
| การเข้าถึง | contrast ตาม WCAG AA/AAA, ขนาดฟอนต์ < 12, ขนาด touch target 44×44 | "งานออกแบบผ่านเกณฑ์การเข้าถึงขั้นพื้นฐาน" |
| ตัวอักษร | จำนวน fontSize/fontFamily/fontWeight ที่ไม่ซ้ำ, type scale เป็นอัตราส่วนไหม, line-height, ความยาวบรรทัด | "มีระบบตัวอักษรที่เป็นระเบียบ" |
| สี | จำนวนสีที่ไม่ซ้ำ, ใช้ named style กี่ % | "มีระบบสีที่ควบคุมได้" |
| การจัดวาง | ใช้ auto-layout กี่ %, spacing เกาะ grid 8pt กี่ %, การจัดแนวคลาด 1-3px, element ล้น/ทับกัน | "ความสม่ำเสมอของระยะห่างและการจัดแนว" |
| ระบบคอมโพเนนต์ | จำนวน component, สัดส่วน instance, component ที่ไม่ถูกใช้, **% layer ที่ยังชื่อ default** | "ใช้ระบบคอมโพเนนต์และตั้งชื่อ layer เรียบร้อย" |
| ความครบถ้วน | จำนวนหน้าจอ, ขนาด artboard ตรง device preset | "ส่งงานครบตามที่โจทย์กำหนด" |
| user flow | มี prototype ไหม, **หน้าจอที่เข้าไม่ถึง (orphan)**, **หน้าจอตัน (dead end)**, ความลึกของ flow | "prototype เชื่อมต่อครบถ้วน ไม่มีหน้าจอตัน" |
| กระบวนการ | การกระจายของ version history, แก้ไขหลังกำหนดส่ง | ใช้เป็นข้อมูลประกอบ ไม่ควรเป็นคะแนนโดยตรง |

**ชั้นที่ 2 — LLM ตัดสินได้ถ้าให้หลักฐานครบ**

- ความชัดเจนของ information hierarchy (ใช้ metrics ตัวอักษร+ระยะห่างประกอบ)
- ความสอดคล้องของงานกับโจทย์/persona ที่นักศึกษาเขียนเอง
- คุณภาพ copy และ microcopy ภาษาไทย
- ความสมเหตุสมผลของ user flow **เชิงความหมาย** (ต่างจากชั้นที่ 1 ที่ตรวจแค่ว่ากราฟเชื่อมกันครบ — กราฟถูก ≠ flow สมเหตุสมผล)
- คุณภาพการเขียนอธิบายเหตุผลการออกแบบ
- ความครบขององค์ประกอบตามที่โจทย์กำหนดในเชิงเนื้อหา

**ชั้นที่ 3 — อาจารย์ตัดสินเสมอ**

- ความคิดสร้างสรรค์และความแปลกใหม่
- ความสวยงามเชิงสุนทรียะ และความเหมาะสมของ visual style กับกลุ่มเป้าหมาย
- ความเหมาะสมกับบริบทวัฒนธรรม
- ความก้าวหน้าเทียบกับตัวนักศึกษาเอง (ระบบไม่มีข้อมูลนี้ และไม่ควรมี)

### ทุกคะแนนจาก LLM ต้องมาพร้อมเหตุผลและหลักฐาน — บังคับทั้งคู่

หลักฐานต้องชี้ถึง **frame หรือหน้าที่เจาะจง** อย่างน้อยหนึ่งจุด กดแล้วเด้งไปเห็นภาพได้ทันที
ถ้า LLM อ้างหลักฐานไม่ได้ → **ถือว่าตรวจหัวข้อนั้นไม่ได้ ส่งต่ออาจารย์ ไม่เดาคะแนน**

เหตุผล: ตัวแปรที่ทำให้อาจารย์ยอมใช้ระบบต่อคือ *ตรวจซ้ำได้เร็วแค่ไหน* ไม่ใช่ AI แม่นแค่ไหน — คะแนนที่ตรวจซ้ำไม่ได้มีค่าเท่าศูนย์ และการบังคับอ้างหลักฐานยังทำให้ LLM แม่นขึ้นด้วย เพราะต้องหาของจริงมายืนยันก่อนตัดสิน

**ไม่เก็บค่าความมั่นใจที่ LLM รายงานเอง** — งานวิจัยชี้ว่าค่านี้ calibrate ไม่ได้ โมเดลมั่นใจเท่ากันทั้งตอนถูกและตอนผิด ถ้าต้องการวัดความมั่นใจจริงให้ตรวจซ้ำหลายรอบแล้วดูการกระจาย ซึ่งเก็บไว้ใช้เฉพาะตอนทดสอบ rubric (ticket 15) ไม่ใช้ในการตรวจปกติ

โครงสร้างผลการตรวจหนึ่งหัวข้อจึงเป็น (ส่งต่อ ticket 12 เป็น data structure และ ticket 21 เป็นหน้าจอ):

| ฟิลด์ | บังคับ | หมายเหตุ |
|---|---|---|
| คะแนน | ✓ | หรือค่า "ตรวจไม่ได้" |
| ระดับคุณภาพที่เลือก | ✓ | อ้างอิง level ใน rubric |
| เหตุผลเป็นข้อความ | ✓ | |
| หลักฐาน ≥ 1 จุด | ✓ | ชี้ frame/หน้า กดแล้วเด้งไปดูได้ |
| ที่มาของคะแนน | ✓ | ชั้นกฎ / LLM / อาจารย์ |
| สัญญาณเชิงกฎที่เกี่ยวข้อง | — | เฉพาะหัวข้อชั้นที่ 1 เก็บตัวเลขดิบไว้ด้วย |

### เมื่อตรวจไม่ได้

**ตรวจลิงก์ตั้งแต่ตอนกดส่ง** — ระบบยิง Figma API ทันทีที่นักศึกษาวางลิงก์ ถ้าเปิดไม่ได้ให้ขึ้นข้อความสีแดงพร้อมวิธีเปิดสิทธิ์ทันที ก่อนที่นักศึกษาจะปิดหน้าจอไป (ส่งต่อ ticket 20 — ต้องเขียนข้อความ error จริง ไม่ใช่ "เกิดข้อผิดพลาด")

> **ยกระดับโดย ticket 14 (2026-08-06): ไม่ใช่แค่ตรวจลิงก์ ต้องแช่แข็งเนื้อหา**
>
> ticket 14 ตัดสินว่า AI จะตรวจก็ต่อเมื่อ **หมดเวลาส่ง + อาจารย์กดสั่ง** ซึ่งอาจห่างจากเวลาที่นักศึกษากดส่งเป็นวัน ถ้าดึงไฟล์ตอนตรวจ นักศึกษาจะแก้งานต่อได้หลังหมดเวลาส่ง แล้ว**สิ่งที่ถูกตรวจจะไม่ใช่สิ่งที่ส่ง**
>
> ดังนั้นตอนกดส่งต้อง **ดึงและเก็บ Figma JSON + ภาพ frame ไว้เป็น snapshot ผูกกับ Submission เวอร์ชันนั้น** (ticket 08 เก็บทุกเวอร์ชันอยู่แล้ว) แล้วชั้นตรวจทั้งสองชั้นอ่านจาก snapshot เท่านั้น ไม่ยิง API ซ้ำ
>
> ผลพลอยได้: แก้ปัญหา rate limit ของ Figma API (ticket 02) ไปในตัว เพราะการดึงกระจายตามเวลาที่นักศึกษาทยอยส่ง แทนที่จะกระแทก 40 ครั้งพร้อมกันตอนกดตรวจ
**ถ้าเปิดได้แต่ AI ตรวจไม่ได้** (หาหลักฐานไม่เจอ ไฟล์ผิดรูปแบบ งานไม่เข้าเกณฑ์เลย) → เข้าคิวให้อาจารย์ตรวจเอง **ไม่ให้ 0 และไม่ตีกลับนักศึกษา**

เหตุผล: การให้ 0 เพราะระบบตรวจไม่ได้คือการลงโทษนักศึกษาสำหรับข้อจำกัดของระบบ ส่วนการตีกลับตอนตี 2 นักศึกษาไม่มีทางรู้ทัน

### หน่วยของการตรวจ — หนึ่ง call ต่อหนึ่งหัวข้อประเมิน

*(ตัดสินพร้อมเหตุผล — ทักท้วงได้)*

เกณฑ์ชั้นที่ 2 ตรวจแยกทีละหัวข้อ ไม่รวมทั้ง rubric ใน call เดียว เพราะ

1. **calibration ทำงานราย criterion** — ticket 03 ชี้ว่าหน่วยที่ปรับได้จริงคือรายหัวข้อ ถ้ารวม call เดียวจะแยกไม่ออกว่าหัวข้อไหนเพี้ยน
2. **เลี่ยง halo effect** — ถ้าตัดสินทุกหัวข้อในคำตอบเดียว คะแนนหัวข้อแรกจะลากหัวข้อถัดไป ทำให้ความสัมพันธ์ระหว่างหัวข้อสูงเกินจริงและเสียข้อมูลวินิจฉัย
3. **ประหยัดตอนปรับ** — แก้ถ้อยคำหัวข้อเดียวแล้วตรวจใหม่เฉพาะหัวข้อนั้น ไม่ต้องรันทั้ง rubric ใหม่ทั้งชุด ซึ่งเป็นค่าใช้จ่ายก้อนใหญ่ที่สุดของช่วง calibration

ต้นทุนที่เพิ่ม: rubric ที่มี 4 หัวข้อชั้นที่ 2 = 4 calls ต่องานหนึ่งชิ้น บรรเทาได้ด้วย prompt caching เพราะภาพและ metrics ชุดเดียวกันถูกใช้ซ้ำทุก call

### สิ่งที่ยังทำไม่ได้ใน ticket นี้ — ต้องใช้ rubric ของจริง

ข้อ 2 ของ ticket (สัดส่วนคะแนนที่ตกอยู่ในชั้นที่ 3) **ตอบไม่ได้จนกว่าจะเห็น rubric ที่อาจารย์ใช้จริงในวิชา** — ถ้าชั้นที่ 3 กินคะแนนเกินครึ่ง คุณค่าของระบบจะเหลือน้อยและต้องคุยกันเรื่องการออกแบบ rubric ใหม่

**สิ่งที่ต้องเตรียมก่อนทำ ticket 10:** rubric จริงของชิ้นงานอย่างน้อย 2 ชิ้นในวิชา UX/UI พร้อมน้ำหนักคะแนน

ปลดล็อก ticket 14 และ 23
