# 10 — โครงสร้างของ rubric และการจัดการเวอร์ชัน

Type: grilling
Status: resolved
Blocked by: 08

## Question

rubric หนึ่งตัวประกอบด้วยอะไร ชิ้นงานหนึ่งมีหลาย rubric แล้วคะแนนรวมกันอย่างไร และเมื่อแก้ rubric แล้วคะแนนที่ให้ไปแล้วเป็นอย่างไร?

โจทย์ข้อ 7 บอกว่า "ใน 1 ชิ้นงานจะมี 1 rubric ขึ้นไป" ซึ่งฟังดูเรียบง่าย แต่พอรวมกับข้อ 8 (ระบบปรับ rubric ให้ตรงอาจารย์) จะเกิดปัญหาทันที: **ถ้าระบบแก้ถ้อยคำ rubric เพื่อ calibrate แล้วคะแนนที่ให้ไปก่อนหน้ายังใช้ได้ไหม** ถ้าตอบผิดตรงนี้ ระบบจะเปรียบเทียบคะแนนข้ามเวลาไม่ได้เลย และงานวิจัยทั้งชิ้นจะพัง

## สิ่งที่ต้องตัดสิน

1. **โครงสร้างภายใน rubric**
   - Criterion มีอะไรบ้าง (ชื่อ, คำอธิบาย, น้ำหนัก, คะแนนเต็ม)
   - ระดับคุณภาพ (level) เป็นแบบไหน — จำนวนระดับคงที่ทั้ง rubric หรือกำหนดต่อ criterion; ให้คะแนนเป็นระดับ (1-4) หรือเป็นตัวเลขต่อเนื่อง; ต้องมีคำบรรยายทุกระดับไหม (จำเป็นมากถ้าจะให้ AI ตรวจ)
   - มี criterion ซ้อนกลุ่ม (หมวด → เกณฑ์ย่อย) ไหม หรือแบนราบชั้นเดียว
   - น้ำหนักเป็นร้อยละ หรือเป็นคะแนนดิบที่บวกกัน
2. **"หลาย rubric ต่อหนึ่งชิ้นงาน" หมายถึงอะไรกันแน่** — เป็นการแบ่งงานชิ้นใหญ่ตามมิติ (เช่น rubric ด้าน visual design + rubric ด้าน process) หรือเป็นการที่ผู้ตรวจต่างคนใช้ rubric ต่างกัน; แต่ละ rubric มีน้ำหนักต่อคะแนนรวมของชิ้นงานเท่าไร; ต้องตรวจครบทุก rubric ไหมจึงจะถือว่าตรวจเสร็จ
3. **การใช้ซ้ำ** — rubric เป็นของชิ้นงานชิ้นเดียว หรือเป็นของกลางที่หลายชิ้นงานหยิบไปใช้; มีคลัง rubric template ระดับรายวิชาหรือระดับระบบไหม
4. **การกำหนดเวอร์ชัน (สำคัญที่สุด)**
   - เมื่อแก้ rubric จะสร้างเวอร์ชันใหม่เสมอ หรือแก้ทับได้ถ้ายังไม่มีใครถูกตรวจ
   - คะแนนทุกก้อนต้องอ้างอิง rubric เวอร์ชันที่ใช้ตรวจจริงไหม (คำแนะนำ: ต้อง — ดู ticket 12)
   - ถ้าแก้ rubric กลางเทอม นักศึกษาที่ตรวจไปแล้วต้องตรวจใหม่ไหม หรือปล่อยให้คะแนนอยู่บนเวอร์ชันเก่า และรายงาน CLO จะรวมคะแนนข้ามเวอร์ชันได้อย่างไร
   - การเปลี่ยนแบบใดถือว่า "ไม่กระทบคะแนน" (แก้คำผิด) และแบบใด "กระทบ" (เปลี่ยนน้ำหนัก เพิ่ม/ลบ criterion)
5. **AI ช่วย draft rubric ได้แค่ไหน** — โจทย์ระบุให้ AI ช่วย draft CLO อยู่แล้ว จะให้ช่วย draft rubric จาก CLO ด้วยไหม และผลลัพธ์ต้องผ่านการอนุมัติของอาจารย์ก่อนใช้เสมอหรือไม่
6. **ความเชื่อมโยงกับ CLO** — criterion ผูกกับ CLO ที่ระดับไหน หนึ่งต่อหนึ่งหรือหลายต่อหลาย (รายละเอียดการคำนวณอยู่ที่ ticket 13 แต่โครงสร้างการผูกตัดสินที่นี่)

## สิ่งที่ต้องได้เมื่อจบ ticket

- โครงสร้างข้อมูลของ rubric/criterion/level พร้อมตัวอย่างจริงจากวิชา UX/UI หนึ่งชุดเต็ม
- กฎการกำหนดเวอร์ชันที่เขียนเป็นประโยคชัดเจน
- คำตอบว่าคะแนนข้ามเวอร์ชัน rubric นำมารวมกันได้หรือไม่ และถ้าไม่ได้ ระบบจะเตือนอาจารย์อย่างไร

## Answer

### 1. โครงสร้างภายใน rubric

**แบนสองชั้น: RubricVersion → Criterion → Level** ไม่มีเกณฑ์ซ้อนเกณฑ์ ถ้าอาจารย์อยากจัดหมวด ให้แยกเป็นคนละ rubric (ดูข้อ 2) แทนการซ้อนชั้น เพราะการซ้อนชั้นทำให้การคำนวณน้ำหนักและการผูก CLO กำกวมทันที

**Rubric (ตัวคงที่ข้ามเวอร์ชัน)**

| ฟิลด์ | หมายเหตุ |
|---|---|
| `rubric_id` | ตัวตนถาวร ใช้อ้างว่า "rubric ตัวเดียวกัน" ข้ามเวอร์ชัน |
| `owner` | ชิ้นงานหนึ่งชิ้น (`assignment_id`) — rubric ทุกตัวเป็นของชิ้นงานเสมอ |
| `name` | เช่น "ด้านงานออกแบบ" |
| `weight_points` | คะแนนเต็มของ rubric ตัวนี้ในชิ้นงาน (ตัวเลขดิบ) |
| `source_template_id` | ถ้าก๊อปมาจากคลัง — ชี้กลับไปที่ template ต้นทาง (nullable) |

**RubricVersion**

| ฟิลด์ | หมายเหตุ |
|---|---|
| `version_id`, `rubric_id`, `version_no` | เลขเวอร์ชันเรียง 1, 2, 3 ภายใน rubric เดียวกัน |
| `level_count` | **จำนวนระดับคงที่ทั้ง rubric** — ทุก criterion มีระดับเท่ากัน |
| `status` | `draft` / `active` / `retired` — ตรวจได้เฉพาะ `active` |
| `created_by`, `created_at`, `change_note` | เหตุผลที่แก้ บังคับกรอก |
| `derived_from_version_id` | เวอร์ชันก่อนหน้า (nullable สำหรับ v1) |
| `ai_drafted` | true ถ้า AI ร่างเนื้อหาให้ (ดูข้อ 6) |
| `approved_by`, `approved_at` | ต้องมีก่อนขึ้น `active` เสมอ |

**Criterion** (อยู่ใต้ RubricVersion — แก้เกณฑ์ = สร้างเวอร์ชันใหม่ ไม่ได้แก้แถวเดิม)

| ฟิลด์ | หมายเหตุ |
|---|---|
| `criterion_id` | ตัวตนถาวรข้ามเวอร์ชัน (เกณฑ์ "contrast" ใน v1 กับ v2 คือ id เดียวกัน) — จำเป็นสำหรับกราฟ calibration รายเกณฑ์ |
| `version_id`, `order` | |
| `name`, `description` | |
| `max_points` | **คะแนนเต็มเป็นตัวเลขดิบ** ผลรวมของทุก criterion ต้องเท่ากับ `weight_points` ของ rubric |
| `judged_by` | `rule` / `llm` / `human_only` — มาจาก ticket 09 ชั้นที่ 1 vs 2 vs 3 |
| `rule_signals[]` | ถ้า `judged_by = rule` — ชี้ว่าใช้สัญญาณตัวไหนจาก 43 ตัว (research 02 §14) |
| `llm_guidance` | คำสั่งเพิ่มเติมที่ส่งให้ LLM เท่านั้น **นักศึกษาไม่เห็น** |

**Level** (อยู่ใต้ Criterion)

| ฟิลด์ | หมายเหตุ |
|---|---|
| `level_no` | 1..`level_count` |
| `descriptor` | **บังคับกรอกทุกช่อง ห้ามว่าง** ระบบไม่ให้ publish เวอร์ชันที่ descriptor ไม่ครบ |
| `points` | คะแนนที่ได้เมื่อตกระดับนี้ ค่าตั้งต้นแบ่งเท่า ๆ กันจาก `max_points` แต่แก้ได้ |

**คะแนนเป็นระดับ ไม่ใช่ค่าต่อเนื่อง** ผู้ตรวจ (คนหรือ AI) เลือกระดับ ระบบแปลงเป็นคะแนนเอง เหตุผล: descriptor คือสิ่งที่ LLM ใช้ตัดสิน ถ้าปล่อยเป็นตัวเลขลอย LLM จะเดา และตารางเทียบคะแนน AI–อาจารย์จะวัด QWK ไม่ได้ (research 03 §2)

**น้ำหนักกรอกเป็นคะแนนดิบ ระบบคำนวณร้อยละให้ดู** — ตรงกับวิธีคิดของอาจารย์และตรงกับที่ต้องกรอกลง มคอ.5 ระบบเตือนถ้าผลรวมไม่ตรงกับคะแนนเต็มที่ประกาศไว้

### 2. หลาย rubric ต่อหนึ่งชิ้นงาน = แบ่งตามมิติของงาน

ชิ้นงานหนึ่งชิ้นมี rubric ได้หลายตัว แต่ละตัวคือ **มิติหนึ่งของงาน** พร้อมคะแนนเต็มของตัวเอง เช่น

- "ออกแบบหน้าจอแอปสั่งอาหาร" เต็ม 20 คะแนน
  - rubric "ด้านงานออกแบบ" 14 คะแนน (ตรวจจากไฟล์ Figma)
  - rubric "ด้านเหตุผลและการนำเสนอ" 6 คะแนน

**ไม่ใช่** การให้ผู้ตรวจต่างคนใช้ rubric ต่างกัน — ทุกผู้ตรวจใช้ชุดเดียวกันเสมอ มิฉะนั้นจะเทียบคะแนน AI กับอาจารย์ไม่ได้ ซึ่งขัดกับหัวใจของโครงงาน (ticket 08 ข้อ 4)

**ต้องตรวจครบทุก rubric จึงถือว่าตรวจเสร็จ** สถานะการตรวจของชิ้นงาน = `ตรวจครบ` ต่อเมื่อทุก criterion ของทุก rubric มีผลแล้ว rubric ที่เป็น `human_only` ล้วนจะทำให้ชิ้นงานค้างสถานะ `รอผู้สอน` เสมอ ซึ่งเป็นพฤติกรรมที่ถูกต้อง ไม่ใช่บั๊ก

### 3. การใช้ซ้ำ — คลัง template ระดับรายวิชา + ก๊อปตอนหยิบใช้

- **RubricTemplate** อยู่ที่ระดับ **Course** (ตัวรายวิชา ไม่ใช่ Course Offering) จึงข้ามเทอมได้ตามธรรมชาติ โครงสร้างภายในเหมือน RubricVersion ทุกประการ แต่ไม่มีคะแนนผูกอยู่
- หยิบ template มาใช้ = **ก๊อปเนื้อหาทั้งชุดเป็น RubricVersion ใหม่ของชิ้นงานนั้น** พร้อมบันทึก `source_template_id`
- **แก้ในชิ้นงานไม่กระทบ template และไม่กระทบชิ้นงานอื่น** — นี่คือเหตุผลทั้งหมดที่เลือกก๊อป ไม่ใช้ร่วม
- **แก้ template ไม่ไหลกลับไปหาชิ้นงานที่หยิบไปแล้ว** — เป็นสิ่งที่ต้องการ ไม่ใช่ข้อจำกัด: คะแนนที่ให้ไปแล้วต้องนิ่ง
- หน้าจอ template มีปุ่ม "ดูว่าชิ้นงานไหนหยิบตัวนี้ไปใช้บ้าง" เพื่อให้อาจารย์ตามไปอัปเดตเองได้ถ้าต้องการ

### 4. การกำหนดเวอร์ชัน — กฎที่เขียนเป็นประโยค

> **กฎที่ 1 — RubricVersion ที่มีการตรวจเกิดขึ้นแล้วแม้เพียงหนึ่งครั้ง จะแก้ไม่ได้อีกตลอดไป** ทุกการแก้หลังจากนั้นสร้างเวอร์ชันใหม่เสมอ
>
> **กฎที่ 2 — ก่อนมีการตรวจครั้งแรก แก้ทับได้อิสระ** เวอร์ชันที่ยังไม่มี Assessment ใดชี้อยู่ ถือว่ายังไม่ผูกมัด
>
> **กฎที่ 3 — คะแนนทุกก้อนอ้าง `version_id` ที่ใช้ตรวจจริง ไม่ใช่ `rubric_id`** (ต่อยอดที่ ticket 12)
>
> **กฎที่ 4 — คะแนนเก่าคาอยู่บนเวอร์ชันเก่า ไม่ตรวจใหม่โดยอัตโนมัติ** อาจารย์สั่งตรวจซ้ำได้เอง แต่ระบบไม่ทำให้เอง
>
> **กฎที่ 5 — ทุกเวอร์ชันต้องมีอาจารย์อนุมัติก่อนขึ้น `active`** ไม่ว่าใครจะเป็นคนร่าง

**การแก้แบบไหนบังคับให้ขึ้นเวอร์ชันใหม่**

| ประเภทการแก้ | ขึ้นเวอร์ชันใหม่ | เหตุผล |
|---|---|---|
| แก้คำผิด/จัดรูปแบบ ที่ไม่เปลี่ยนความหมาย | ไม่ | ไม่กระทบการตัดสิน |
| **แก้ถ้อยคำ descriptor** | **ใช่** | descriptor คือสิ่งที่ LLM ใช้ตัดสินโดยตรง — เคสในฉากตัวอย่างคือเคสนี้ |
| แก้ `max_points` หรือ `points` ของระดับ | ใช่ | เปลี่ยนฐานคะแนน |
| เพิ่ม/ลบ criterion | ใช่ | |
| เปลี่ยน `judged_by` | ใช่ | เปลี่ยนว่าใครตรวจ = เปลี่ยนความหมายของคะแนน |
| แก้การผูก CLO หรือสัดส่วน | ใช่ | กระทบรายงาน CLO ย้อนหลัง |
| แก้ `llm_guidance` | ใช่ | เปลี่ยนพฤติกรรมผู้ตรวจ แม้นักศึกษาไม่เห็นความต่าง — **แก้โดย ticket 15 ดูด้านล่าง** |

> **แก้กลับโดย ticket 15 (2026-08-06): `llm_guidance` ย้ายออกจาก RubricVersion**
>
> ticket 15 พบว่าถ้า `llm_guidance` อยู่ใน RubricVersion จะเกิดปัญหาบังคับใช้ไม่ได้: loop ปรับจูนต้องแก้คำอธิบายสำหรับ AI **ทุกชิ้นงาน** ถ้าทุกครั้งดัน RubricVersion ใหม่ ตัวเลขเวอร์ชัน rubric จะวิ่งขึ้นเรื่อย ๆ ทั้งที่**เกณฑ์ที่นักศึกษาถูกตัดสินไม่ได้เปลี่ยนเลย** ทำให้เส้นแบ่ง "อะไรคือการเปลี่ยนกติกา" หายไป
>
> **ของใหม่:** `llm_guidance` + anchor example + few-shot + พารามิเตอร์ calibration ย้ายไปอยู่ใน entity ใหม่ **`JudgePromptVersion`** ที่มีเวอร์ชันของตัวเอง แถวนี้จึงอ่านว่า "แก้ `llm_guidance` = **JudgePromptVersion** ใหม่ ไม่ใช่ RubricVersion ใหม่"
>
> **เส้นแบ่งว่าอะไรอยู่ชั้นไหน ตัดสินด้วยคำถามเดียว:** *"ถ้านักศึกษาอ่านข้อความนี้ตอนกำลังทำงาน เขาจะทำงานต่างไปจากเดิมไหม?"* — ถ้าต่าง แปลว่าเป็นเกณฑ์ที่ไม่ได้บอกล่วงหน้า **ต้องขึ้นเป็น RubricVersion ใหม่** และใช้กับชิ้นงานถัดไปเท่านั้น · ถ้าไม่ต่าง (แค่ขยายความสิ่งที่อาจารย์ตั้งใจอยู่แล้ว) อยู่ชั้น JudgePrompt ได้
>
> เคสของ ticket 14 (AI เข้าใจเกณฑ์ผิดทั้งชั้น แล้วอาจารย์แก้ `descriptor`) **ยังเป็น RubricVersion ใหม่เหมือนเดิม** เพราะแก้ที่ descriptor ไม่ใช่ที่ llm_guidance

**เส้นแบ่ง "แก้คำผิด" ตัดสินโดยอาจารย์ ไม่ใช่ระบบ** ระบบตั้งค่าเริ่มต้นเป็น "ขึ้นเวอร์ชันใหม่" ทุกครั้งที่แตะ descriptor แล้วให้ติ๊ก "การแก้นี้ไม่กระทบความหมาย" เพื่อลดระดับลงเป็นการแก้ทับ พร้อมบันทึกว่าใครติ๊กและเมื่อไร — เป็นการเลือกฝั่งที่ผิดแล้วยังกู้ได้

**หมายเหตุเรื่อง prompt** — research 03 สรุปว่าต้องแยก *rubric ที่นักศึกษาเห็น* ออกจาก *prompt ที่ส่งให้ LLM* ~~ทั้งสองอยู่ใน RubricVersion เดียวกันคนละฟิลด์~~ **แก้โดย ticket 15: แยกเป็นคนละ entity ที่มีเวอร์ชันของตัวเอง** (`RubricVersion.descriptor` กับ `JudgePromptVersion.llm_guidance`) สิ่งที่นักศึกษาเห็นเปลี่ยนก็ต่อเมื่อ `descriptor` เปลี่ยนเท่านั้น — **แต่ ticket 15 เพิ่มเงื่อนไขความโปร่งใส: นักศึกษาขอดูเนื้อหาชั้น JudgePrompt ที่ใช้ตรวจงานของตัวเองได้เสมอ** (ไม่ประกาศอัตโนมัติ แต่ปฏิเสธไม่ได้) ผลที่ตามมาคือทุกข้อความในชั้นนั้น**ต้องเขียนเป็นภาษาที่นักศึกษาอ่านรู้เรื่อง ห้ามเป็นเทคนิค prompt engineering ที่อธิบายให้คนฟังไม่ได้**

### 5. คะแนนข้ามเวอร์ชันรวมกันได้ไหม

**รวมได้ แต่ระบบต้องเตือน** — ไม่ห้าม เพราะการห้ามจะทำให้อาจารย์ตัดเกรดไม่ได้เลยเมื่อแก้ rubric กลางเทอม ซึ่งจะเกิดขึ้นแน่นอน

ระบบแสดงป้าย **"คะแนนชิ้นงานนี้มาจาก rubric 2 เวอร์ชัน"** บน:
- หน้ารวมคะแนนของชิ้นงาน
- รายงาน CLO (ticket 13)
- ไฟล์ส่งออก (ticket 22) — เป็นคอลัมน์ `rubric_version` รายแถว ไม่ใช่แค่หมายเหตุท้ายไฟล์

กดที่ป้ายแล้วเห็น: ใครอยู่เวอร์ชันไหน แก้อะไรระหว่างเวอร์ชัน และปุ่ม **"ตรวจซ้ำเฉพาะคนที่ใช้เวอร์ชันเก่า"** ที่สั่ง AI ตรวจใหม่บนเวอร์ชันล่าสุด — ผลที่ได้เป็น Assessment ก้อนใหม่ ไม่ทับก้อนเดิม (ticket 08 ข้อ 4) อาจารย์เลือกเองว่าจะยึดก้อนไหนเป็นคะแนนจริง

**ข้อยกเว้นที่เข้มกว่า:** ถ้าเวอร์ชันใหม่ **เพิ่มหรือลบ criterion** ระบบเปลี่ยนป้ายเตือนจากเหลืองเป็นแดง ระบุว่า "โครงสร้างเกณฑ์ไม่ตรงกัน คะแนนไม่ควรนำมาเทียบกันตรง ๆ" เพราะคะแนนเต็มคนละฐาน — และ **ตัดคู่คะแนนที่ข้ามเวอร์ชันนั้นออกจากการคำนวณ QWK อัตโนมัติ** เพื่อไม่ให้กราฟ calibration เพี้ยน

### 6. AI ช่วย draft rubric

- AI ร่างได้จาก **CLO ของรายวิชา + โจทย์ของชิ้นงาน + ระดับ Bloom ของ CLO** ผลลัพธ์คือ criterion พร้อม descriptor ครบทุกระดับ
- **ต้องผ่านการอนุมัติของอาจารย์เสมอก่อนใช้ตรวจ** ไม่มีทางลัด
- ระบบบันทึกรายช่องว่า **ช่องไหน AI ร่าง ช่องไหนอาจารย์แก้** — เป็นข้อมูลวิจัยชั้นดี: วัดได้ว่า AI ร่าง rubric ได้ใกล้เคียงอาจารย์แค่ไหน และช่องประเภทไหนที่ AI มักพลาด
- AI **ไม่** กรอกน้ำหนักคะแนนให้ — เสนอเป็นคำแนะนำได้ แต่ช่องต้องว่างให้อาจารย์กรอกเอง เพราะน้ำหนักคือการตัดสินใจเชิงหลักสูตร ไม่ใช่เชิงภาษา

### 7. การผูก CLO

**CriterionCLOLink** — many-to-many พร้อมสัดส่วน

| ฟิลด์ | หมายเหตุ |
|---|---|
| `criterion_id` (ของเวอร์ชันนั้น), `clo_id`, `share` | ร้อยละ ผลรวมของ link ทั้งหมดของ criterion หนึ่ง = 100% |

- **criterion ที่ไม่ผูก CLO เลยก็ได้** เช่น "ส่งงานตรงเวลา ตั้งชื่อไฟล์ถูก" — คะแนนเข้าคะแนนชิ้นงานแต่ไม่เข้ารายงาน CLO
- **หน้าจอต้องมีตัวช่วยกรอกสัดส่วน** — ค่าตั้งต้นแบ่งเท่ากันตามจำนวน CLO ที่ติ๊ก อาจารย์ปรับได้
- **ระบบเตือนตอนปิดเทอมถ้ามี CLO ที่ไม่มี criterion ไหนทั้งเทอมวัดเลย** — เตือนที่ระดับรายวิชา ไม่ใช่ระดับชิ้นงาน (ชิ้นงานเดียววัดครบทุก CLO ไม่ใช่เรื่องปกติ) สูตรคำนวณอยู่ที่ ticket 13
