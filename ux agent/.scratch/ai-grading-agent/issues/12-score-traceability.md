# 12 — การสืบย้อนที่มาของคะแนน (provenance)

Type: grilling
Status: resolved
Blocked by: 08, 10, 11

## Question

เมื่อเปิดดูคะแนนของนักศึกษาหนึ่งคนหนึ่งช่อง ระบบต้องตอบได้ว่าตัวเลขนี้มาจากไหน — ต้องเก็บอะไรบ้างจึงจะตอบได้ครบ?

โจทย์ข้อ 9 เขียนสั้น ๆ ว่า "trace ได้ว่าคะแนนมาจากไหน" แต่นี่คือข้อกำหนดที่หนักที่สุดข้อหนึ่งของระบบ เพราะคะแนนหนึ่งตัวเลขอาจผ่านมือ AI ครั้งหนึ่ง อาจารย์แก้อีกครั้งหนึ่ง มาจากงานกลุ่มที่กระจายให้รายคน คำนวณด้วย rubric เวอร์ชันที่ตอนนี้ถูกแก้ไปแล้ว และถูกเอาไปรวมเป็น CLO attainment อีกทอด — ถ้าไม่ออกแบบให้ดีตั้งแต่ต้น ระบบจะตอบคำถามง่าย ๆ อย่าง "ทำไมหนูได้ 7 ไม่ใช่ 8" ไม่ได้

## สิ่งที่ต้องตัดสิน

1. **หน่วยที่เล็กที่สุดของคะแนนที่เก็บ** — เก็บที่ระดับ (นักศึกษา × ชิ้นงาน) หรือละเอียดถึง (นักศึกษา × ชิ้นงาน × rubric × criterion) — คำแนะนำคือละเอียดที่สุด เพราะ CLO attainment (ticket 13) ต้องใช้ระดับ criterion และ calibration (ticket 15) ต้องเทียบคะแนนรายเกณฑ์
2. **ข้อมูลที่ต้องแนบกับทุกคะแนน** — พิจารณาแต่ละอย่างว่าจำเป็นหรือไม่
   - ใครให้ (AI รุ่นไหน เวอร์ชัน prompt ไหน / อาจารย์คนไหน)
   - เมื่อไร
   - rubric เวอร์ชันไหน criterion ไหน
   - เหตุผลเป็นข้อความ และหลักฐานอ้างอิงถึงจุดในชิ้นงาน
   - มาจากการส่งครั้งไหน (ถ้าส่งหลายเวอร์ชัน)
   - มาจากงานกลุ่มหรือเดี่ยว ถ้ากลุ่มมาจากกลุ่มไหน กระจายด้วยกฎอะไร
   - ค่าใช้จ่าย/token ที่ใช้ (มีประโยชน์ต่อการวางแผนงบและต่อรายงาน)
3. **การแก้คะแนน** — เมื่ออาจารย์แก้คะแนนที่ AI ให้ จะ **ทับ** ของเดิม หรือ **เพิ่มชั้นใหม่** ทับไว้โดยยังเก็บของเดิม — คำแนะนำคือเพิ่มชั้น เพราะข้อ 8 ต้องใช้ส่วนต่างระหว่างคะแนน AI กับคะแนนอาจารย์เป็นสัญญาณเรียนรู้; ถ้าทับทิ้ง สัญญาณนั้นหายไปตลอดกาล
4. **ประวัติการแก้ไข** — เก็บทุกครั้งที่แก้ หรือเก็บแค่ค่าล่าสุด + ค่าแรกของ AI; ต้องบันทึกเหตุผลตอนแก้ไหม
5. **คะแนนที่คำนวณต่อ** — คะแนนรวมของชิ้นงาน คะแนนรวมของรายวิชา และ CLO attainment เป็นค่าที่ **เก็บไว้** หรือ **คำนวณสดทุกครั้ง**; ถ้าเก็บไว้ ต้องคำนวณใหม่เมื่อไร (แก้คะแนน แก้ rubric แก้น้ำหนัก)
6. **หน้าจอที่ต้องตอบคำถามนี้** — เมื่อคลิกคะแนนหนึ่งช่อง อาจารย์ควรเห็นอะไร นักศึกษาควรเห็นอะไร (เหมือนกันไหม — โดยเฉพาะ "AI ให้ 6 อาจารย์แก้เป็น 8" นักศึกษาควรเห็นหรือไม่ เป็นคำถามเชิงนโยบายที่ต้องตอบ)
7. **การลบ** — เมื่อลบชิ้นงานหรือถอนนักศึกษาออก คะแนนและร่องรอยหายไปด้วยไหม (เกี่ยวกับ PDPA ใน ticket 18)

## สิ่งที่ต้องได้เมื่อจบ ticket

- โครงสร้างข้อมูลของคะแนนหนึ่งก้อน พร้อมทุกฟิลด์ที่ต้องเก็บ
- กฎการซ้อนชั้นระหว่างคะแนน AI กับคะแนนอาจารย์ เขียนเป็นประโยคชัดเจน
- ตัวอย่างเดินเรื่องหนึ่งเคส: งานกลุ่ม 3 คน AI ตรวจแล้วอาจารย์แก้ 2 เกณฑ์ แล้วปรับคะแนนรายคนหนึ่งคน — ไล่ให้ครบว่าเก็บอะไรกี่ก้อน และหน้าจอแสดงอะไร

## Answer

### 1. หน่วยเก็บที่เล็กที่สุด

**CriterionScore — หนึ่งแถวต่อ (การตรวจหนึ่งครั้ง × เกณฑ์หนึ่งข้อ)** ไม่มีอะไรเล็กกว่านี้ และ **ไม่มีคะแนนก้อนไหนถูกเก็บโดยไม่ผ่านหน่วยนี้** คะแนนชิ้นงาน คะแนน rubric คะแนนรวมของนักศึกษา และค่า CLO ทั้งหมดคำนวณขึ้นมาจากแถวเหล่านี้เสมอ

เหตุผลที่ไม่เก็บหยาบกว่านี้: ticket 09 ตัดสินว่าตรวจทีละหัวข้อประเมิน · ticket 03 ต้องการ calibration รายเกณฑ์ · ticket 13 ต้องการกระจายคะแนนเข้า CLO ตามสัดส่วนของเกณฑ์ ทั้งสามอย่างพังทันทีถ้าเก็บแค่คะแนนรวมของชิ้นงาน

### 2. โครงสร้างข้อมูล — 5 ก้อน

**(1) Assessment — การตรวจหนึ่งครั้งโดยผู้ตรวจหนึ่งราย**

| ฟิลด์ | หมายเหตุ |
|---|---|
| `assessment_id` | |
| `submission_id` + `submission_version_no` | **ชี้เวอร์ชันที่ตรวจจริง ไม่ใช่เวอร์ชันล่าสุด** (ticket 08) |
| `rubric_version_id[]` | ทุกเวอร์ชันของ rubric ที่ใช้ในการตรวจครั้งนี้ (ticket 10 กฎที่ 3) |
| `grader_type` | `ai` / `teacher` / `ta` |
| `grader_ref` | ถ้าคน: `user_id` · ถ้า AI: `model_id` + `analyzer_version` (เวอร์ชันโค้ดชั้นที่ 1) + **`judge_prompt_version_id`** (แทน `prompt_version` เดิม — **แก้โดย ticket 15**: prompt/anchor/calibration ย้ายไปเป็น entity `JudgePromptVersion` ต่างหาก ดู [ticket 15 §5](15-calibration-loop-design.md)) + **`temperature`, `seed`** (ticket 15 §10 — ต้องมีเพื่อให้ทำซ้ำได้ และเพราะรอบวัดความไม่มั่นใจรันซ้ำ 3 ครั้งที่ temperature > 0) |
| `is_authoritative` | **มีได้ก้อนเดียวต่อหนึ่ง submission** — ก้อนที่นับเป็นคะแนนจริง |
| `status` | `กำลังตรวจ` / `ตรวจครบ` / `รอผู้สอน` |
| `seeded_from_assessment_id` | ถ้าเป็นการตรวจที่เปิดมาแล้วเห็นคะแนน AI อยู่ก่อน (nullable — ดูข้อ 6) |
| `started_at`, `completed_at` | |
| `cost` | จำนวน token และค่าใช้จ่ายโดยประมาณ (เฉพาะ `grader_type = ai`) |
| `blind_mode` | **เพิ่มโดย ticket 14** — true = ผู้ตรวจถูกซ่อนคะแนน AI ไว้ตอนตรวจ |
| `revealed_at` | **เพิ่มโดย ticket 14** — เวลาที่ผู้ตรวจกดเปิดดูคะแนน AI (nullable) · การแก้หลังเวลานี้ยังบันทึกปกติ แต่**คะแนนที่ใช้วิเคราะห์คือค่า ณ ก่อน `revealed_at`** ซึ่งกู้ได้จาก ScoreEdit chain |
| `blind_cancelled_by` | **เพิ่มโดย ticket 14** — ถ้าผู้ตรวจยกเลิก blind ของชิ้นนี้ ต้องบันทึกว่าใครยกเลิก และตัดชิ้นนี้ออกจากชุดข้อมูลวิจัย |
| `dataset_split` | **เพิ่มโดย ticket 15** — `measurement` / `improvement` / `test` / `none` · **กำหนดตอนเลือกชิ้นงาน ไม่ใช่ตอนวิเคราะห์** และเปลี่ยนย้อนหลังไม่ได้ · ระบบต้อง**ปฏิเสธ**คำสั่ง optimization ใด ๆ ที่พยายามอ่านแถว `test` แล้วบันทึกความพยายามนั้นไว้ · นี่คือฟิลด์ที่ทำให้เส้นแบ่ง Measurement/Improvement ของ ticket 15 §1 บังคับใช้ได้จริงแทนที่จะเป็นแค่ระเบียบวินัยของคนใช้ |
| `retry_count` | **เพิ่มโดย ticket 15** — จำนวนครั้งที่เรียก LLM ซ้ำเพราะล้มเหลว (คู่กับคิวของ ticket 14 §7) |

**(2) CriterionScore — คะแนนหนึ่งเกณฑ์ในการตรวจหนึ่งครั้ง**

| ฟิลด์ | หมายเหตุ |
|---|---|
| `assessment_id`, `criterion_id` | |
| `level_no` + `points` | `points` คัดลอกมาจาก Level ตอนตรวจ **ไม่ใช่ join สด** เพราะ rubric เวอร์ชันเก่าอาจถูก retire |
| `points_raw` | **เพิ่มโดย ticket 15** — คะแนน**ก่อน**ผ่านการชดเชยเชิงตัวเลข (offset/linear ต่อเกณฑ์) ส่วน `points` คือค่าหลังชดเชยที่ใช้จริง · ต้องเก็บทั้งคู่ ไม่งั้นเปลี่ยนวิธี calibrate ทีหลังแล้วคำนวณย้อนหลังไม่ได้ และวัดไม่ได้ว่า calibration ช่วยจริงหรือไม่ (research 03 §6.4) |
| `uncertainty_samples` | **เพิ่มโดย ticket 15** — ผลจากการรัน LLM ซ้ำ 3 ครั้งที่ temperature > 0 **เก็บทั้ง 3 ค่า ไม่ใช่ค่าเฉลี่ย** · ใช้เป็น proxy ของความไม่มั่นใจเพื่อเลือกชิ้นงานเข้ารอบ 3 เพราะ API เชิงพาณิชย์ไม่คืน logprob · nullable — เก็บเฉพาะชิ้นที่อยู่ในรอบคัดเลือก ไม่ใช่ทุกการตรวจ (ต้นทุน ×3) |
| `rationale` | เหตุผล — บังคับ (ticket 09) |
| `evidence[]` | ชี้จุดในไฟล์: `node_id`, ชื่อเฟรม, พิกัด, ภาพ crop ที่ถ่ายไว้ตอนตรวจ — บังคับอย่างน้อย 1 รายการ |
| `rule_signals` | ค่าดิบจากชั้นที่ 1 เช่น `{contrast_fail_count: 7}` (เฉพาะเกณฑ์ `rule`) |
| `teacher_touched` | true ถ้าผู้ตรวจแก้ค่านี้จริง ไม่ใช่ปล่อยไว้ตามที่ระบบเติมให้ (ดูข้อ 6) |
| `is_pending` | true = ยังไม่มีใครให้คะแนน เช่น B2 ที่ AI ตรวจไม่ได้ |
| `carried_from_assessment_id` | **เพิ่มโดย ticket 14** — ตอนสั่ง AI ตรวจใหม่เฉพาะบางเกณฑ์หลังแก้ rubric เกณฑ์ที่ไม่ได้แก้จะถูก**คัดลอกผลเดิมมา ไม่เรียก AI ซ้ำ** ฟิลด์นี้ชี้ว่าคัดลอกมาจากการตรวจครั้งไหน · **จำเป็นตอนนับจำนวนตัวอย่างเพื่องานวิจัย** ถ้านับแถวที่คัดลอกมาด้วย จำนวนข้อมูลจะพองเกินจริง (ตรงกับกับดักการนับหน่วยข้อมูลใน [research 04 §7.2](../research/04-rl-small-data.md)) |

**(3) ScoreEdit — บันทึกการแก้ (append-only ไม่ลบ ไม่แก้)**

| ฟิลด์ | หมายเหตุ |
|---|---|
| `criterion_score_id`, `edited_by`, `edited_at` | |
| `level_from` → `level_to`, `points_from` → `points_to` | |
| `reason` | **บังคับเมื่อค่าใหม่ต่างจากค่าที่ AI ให้** ไม่บังคับเมื่อเป็นการแก้ค่าของตัวเองซ้ำ (แก้พิมพ์ผิด) |
| `differs_from_ai` | ธงที่ทำให้ query หา "ทุกครั้งที่อาจารย์ไม่เห็นด้วยกับ AI" ได้ในคิวรีเดียว |

**(4) IndividualAdjustment — การปรับคะแนนรายบุคคล** (ตัดสินไว้แล้วที่ ticket 11) วางทับคะแนนกลุ่ม ไม่เขียนทับ · `delta` เป็นบวกหรือลบก็ได้ · `reason` บังคับ · เก็บผู้ปรับและเวลา

**(5) GradeSnapshot — การปิดคะแนน**

| ฟิลด์ | หมายเหตุ |
|---|---|
| `snapshot_id`, `offering_id`, `scope` | ปิดได้ทั้งเทอม หรือเฉพาะชิ้นงาน |
| `frozen_at`, `frozen_by`, `note` | |
| `rows[]` | คะแนนของทุกคนทุกชิ้น ณ วินาทีที่ปิด — **คัดลอกค่า ไม่ใช่ pointer** |

**(6) JudgePromptVersion — ตัวตรวจฝั่ง AI ที่มีเวอร์ชันของตัวเอง** *(เพิ่มโดย ticket 15)*

| ฟิลด์ | หมายเหตุ |
|---|---|
| `judge_prompt_version_id`, `offering_id`, `version_no` | |
| `system_prompt` | ชั้น D |
| `guidance_by_criterion` | คำขยายความรายเกณฑ์ (คือ `llm_guidance` ที่ย้ายมาจาก ticket 10) — ชั้น B |
| `anchor_set[]` | ตัวอย่างงานพร้อมคะแนนและเหตุผล ชี้ไปที่ `submission_id` จริง — ชั้น A |
| `calibration_params` | offset/linear ต่อเกณฑ์ พร้อมระบุว่า fit จากงานกี่ชิ้นและชุดไหน — ชั้น C |
| `gate_results` | ผลการรันประตู D1–D3 ตอนอนุมัติเวอร์ชันนี้ **บันทึกไว้แม้ผ่านโดยไม่มีหลักฐานเชิงสถิติ** |
| `activated_at`, `retired_at` | **หนึ่งเวอร์ชัน = หนึ่งชิ้นงาน ห้ามสลับกลางชิ้นงาน** เพื่อให้ทุกคนในชิ้นงานเดียวกันถูกตรวจด้วยตัวตรวจเดียวกัน |
| `visible_to_students` | คงที่ = true — นักศึกษาขอดูเวอร์ชันที่ใช้ตรวจงานตัวเองได้เสมอ (ไม่แสดงอัตโนมัติ) |

**(7) CalibrationProposal — ข้อเสนอปรับจูนหนึ่งข้อ** *(เพิ่มโดย ticket 15)*

| ฟิลด์ | หมายเหตุ |
|---|---|
| `proposal_id`, `assignment_id`, `layer` | ชั้น A/B/C/D |
| `criterion_id`, `before`, `after` | ข้อความหรือตัวเลขก่อน/หลัง |
| `evidence` | จากงานกี่ชิ้น bias เท่าไร ผลที่คาดบน dev set |
| `status`, `decided_by`, `decided_at`, `reject_reason` | **อาจารย์กดรับ/ปฏิเสธทีละข้อ · เหตุผลที่ปฏิเสธคือข้อมูลวิจัยในตัวมันเอง** (AI เสนออะไรที่อาจารย์ไม่เอา และทำไม) |
| `resulting_judge_prompt_version_id` | ข้อที่ถูกรับรวมกันเป็นเวอร์ชันใหม่หนึ่งเวอร์ชัน |

หลังปิดแล้ว แก้คะแนนเดิมไม่ได้ ต้องสร้าง snapshot ใหม่ที่ `supersedes` ตัวเก่า พร้อมเหตุผล — ตรงกับความเป็นจริงของการยื่นแก้เกรด

### 3. กฎการซ้อนชั้น — เขียนเป็นประโยค

> **กฎที่ 1 — การตรวจหนึ่งครั้งของผู้ตรวจหนึ่งราย เป็นก้อนของตัวเองเสมอ** AI ตรวจ = Assessment ก้อนหนึ่ง อาจารย์ตรวจ = อีกก้อนหนึ่ง **ไม่มีการเขียนทับข้ามก้อนตลอดกาล**
>
> **กฎที่ 2 — คะแนนที่นับจริงคือก้อนที่ติดธง `is_authoritative`** ถ้ามีอาจารย์ตรวจ ธงอยู่ที่ก้อนของอาจารย์เสมอ ถ้ามีแต่ AI ตรวจ ธงอยู่ที่ก้อนของ AI และหน้าจอต้องบอกชัดว่า "ยังไม่ผ่านการตรวจของผู้สอน"
>
> **กฎที่ 3 — คะแนนสุทธิของนักศึกษาหนึ่งคน = คะแนนจากก้อน authoritative + ผลรวม IndividualAdjustment ของคนนั้น** คำนวณเสมอ ไม่เก็บเป็นค่านิ่ง ยกเว้นใน GradeSnapshot
>
> **กฎที่ 4 — การแก้ค่าใน Assessment ก้อนหนึ่ง ไม่ทำลายค่าเดิม** ค่าปัจจุบันอยู่ที่ CriterionScore ประวัติทั้งสายอยู่ที่ ScoreEdit
>
> **กฎที่ 5 — ทุกครั้งที่อาจารย์ให้ค่าต่างจาก AI ต้องมีเหตุผล** เพราะส่วนต่างพร้อมเหตุผลคือข้อมูลตั้งต้นทั้งหมดของ ticket 15 (ทดสอบ rubric) และ ticket 16 (RL)

### 4. คำนวณสดหรือเก็บนิ่ง

**คำนวณสดทุกครั้ง** ทั้งคะแนน rubric คะแนนชิ้นงาน คะแนนรวมเทอม และค่า CLO — เพราะทุกอย่างมีทางถูกแก้ย้อนหลังได้ (อาจารย์แก้เกณฑ์ ปรับรายคน ตรวจซ้ำบน rubric เวอร์ชันใหม่) ค่านิ่งจะเพี้ยนเงียบ ๆ

**ยกเว้นตอนปิดคะแนน** — GradeSnapshot คือจุดเดียวที่ freeze ตัวเลข ใช้ตอนส่งเกรดและตอนกรอก มคอ.5 ถ้าไม่มีจุดนี้ อาจารย์จะไม่มีทางตอบได้ว่า "ตัวเลขที่ส่งไปเมื่อวันที่ 15 คืออะไร"

**เรื่อง cache** — ถ้าช้า ให้ทำ materialized view ที่คำนวณใหม่ทั้งก้อนเมื่อมี CriterionScore/Adjustment ใด ๆ เปลี่ยน **ห้ามอัปเดตแบบ incremental** เพราะเป็นบ่อเกิดของคะแนนเพี้ยนที่หาไม่เจอ

### 5. หน้าจอแสดงอะไร

| ข้อมูล | อาจารย์ | นักศึกษา |
|---|---|---|
| คะแนนรายเกณฑ์สุดท้าย + เหตุผล + หลักฐานชี้จุด | ✅ | ✅ |
| คะแนนกลุ่ม | ✅ | ✅ (สมาชิกเห็นร่วมกัน) |
| คะแนนสุทธิของตัวเอง + เหตุผลการปรับ | ✅ ทุกคน | ✅ เฉพาะของตัวเอง |
| **คะแนนที่ AI ให้** | ✅ วางคู่กัน | ❌ |
| ประวัติการแก้ ScoreEdit | ✅ | ❌ |
| `rule_signals` ค่าดิบ | ✅ | ✅ เฉพาะที่อธิบายเป็นภาษาคนได้ เช่น "พบข้อความตกเกณฑ์ AA 7 จุด" |
| ผู้ตรวจเป็นใคร | ✅ ชื่อจริง | บอกแค่ "ตรวจโดยผู้สอน" |
| ต้นทุน token | ✅ | ❌ |

**หลักคือ อาจารย์เป็นเจ้าของคะแนนแต่เพียงผู้เดียวในสายตานักศึกษา** ระบบไม่บอกนักศึกษาว่าเดิม AI ให้เท่าไร เหตุผล: ถ้าบอก นักศึกษาจะเปิดประเด็นอุทธรณ์ที่ผิดเรื่อง — เถียงกับคะแนน AI ที่ไม่ใช่คะแนนจริง หรือใช้ส่วนต่างเป็นหลักฐานว่าอาจารย์ลำเอียง ข้อมูลยังเก็บครบในฐานและอาจารย์เห็นทั้งหมด **ปิดจากสายตา ไม่ใช่ปิดการบันทึก**

หน้าจอนักศึกษาต้องมีป้ายว่า **"ตรวจโดยผู้สอน"** เทียบกับ **"ผลเบื้องต้น ยังไม่ผ่านการตรวจของผู้สอน"** — ความโปร่งใสที่นักศึกษาต้องการจริง ๆ คือรู้ว่าคะแนนนี้ผ่านตาคนหรือยัง ไม่ใช่รู้ว่าเครื่องให้เท่าไร

### 6. กับดักที่ต้องกันไว้ตั้งแต่ตอนนี้ — anchoring

ถ้าหน้าจอตรวจงานของอาจารย์เปิดมาแล้วเห็นคะแนนที่ AI ให้อยู่ก่อน **อาจารย์จะถูกยึดโยงกับตัวเลขนั้น** (research 01) ผลคือช่องที่อาจารย์ "ไม่แก้" ไม่ได้แปลว่าเห็นด้วย แต่แปลว่าไม่ได้คิดใหม่ ซึ่งทำให้ค่า agreement สูงเกินจริงและ ticket 15/16 เรียนจากข้อมูลที่ปนเปื้อน

กันสามชั้น:

1. `seeded_from_assessment_id` บันทึกว่าการตรวจครั้งนี้เห็นคะแนน AI มาก่อนหรือไม่
2. `teacher_touched` รายเกณฑ์ แยก "ยืนยันจริง" ออกจาก "ปล่อยไว้ตามเดิม"
3. **ในโหมดทดสอบ rubric (ticket 15) อาจารย์ตรวจแบบไม่เห็นคะแนน AI เสมอ** — เป็นข้อบังคับ ไม่ใช่ตัวเลือก ข้อมูล calibration ที่นับได้จริงมาจากการตรวจแบบนี้เท่านั้น
4. ในการใช้งานปกติ อาจารย์เลือกได้ว่าจะเปิดมาเห็นคะแนน AI เลย (เร็ว) หรือกรอกเองก่อนแล้วค่อยเทียบ (สะอาด) — ระบบบันทึกว่าเลือกโหมดไหน

### 7. การเก็บและการลบ (PDPA)

- **เก็บตามระเบียบของมหาวิทยาลัย** (ต้องไปหาตัวเลขจริงมาใส่ — เพิ่มเป็นการบ้านใน map) หลังพ้นกำหนด **ถอดชื่อออกแล้วเก็บต่อเพื่องานวิจัย**
- **สิ่งที่ถอดออก:** ชื่อ-รหัสนักศึกษา อีเมล ลิงก์ Figma ส่วนตัว ชื่อไฟล์ที่มีชื่อคน และ **ข้อความเหตุผลการปรับคะแนนรายบุคคล** (มักมีข้อความเชิงพฤติกรรมที่ระบุตัวคนได้ เช่น "ไม่เข้ากลุ่มเลยตลอดสองสัปดาห์")
- **สิ่งที่เก็บต่อ:** คู่คะแนน AI–อาจารย์ เหตุผลรายเกณฑ์ ค่า `rule_signals` เวอร์ชัน rubric และ prompt — คือแก่นข้อมูลของงานวิจัยทั้งหมด และไม่ระบุตัวคน
- **ถอนรายวิชากลางเทอม:** ไม่ลบทันที ทำเครื่องหมาย `withdrawn` และซ่อนออกจากรายงาน CLO — คะแนนต้องอยู่จนพ้นกำหนดอุทธรณ์
- **ลบชิ้นงาน:** ห้าม hard delete ถ้ามี Assessment ใดชี้อยู่ ให้ทำเป็น `archived` แทน
- รายละเอียดความยินยอมและสิทธิ์เข้าถึงอยู่ที่ ticket 18

### 9. ส่งต่อ

- **ticket 13** — คำนวณ CLO จาก CriterionScore ของก้อน authoritative เท่านั้น และต้องตัดสินว่าใช้คะแนนกลุ่มหรือคะแนนสุทธิ (มีผลต่อค่า attainment รายคน)
- **ticket 15** — `differs_from_ai` + `teacher_touched` + โหมดตรวจแบบไม่เห็นคะแนน AI คือฐานข้อมูลทั้งหมดของระบบทดสอบ rubric
- **ticket 18** — ระเบียบการเก็บข้อมูลของมหาวิทยาลัยและรายการฟิลด์ที่ต้องถอดชื่อ
- **ticket 21** — โจทย์ยุบ 25 แถวให้อ่านได้ในหน้าจอเดียว
- **ticket 22** — ไฟล์ส่งออกต้องมีคอลัมน์ `rubric_version` และอ้าง GradeSnapshot ที่ใช้
