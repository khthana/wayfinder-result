# 15 — ออกแบบ calibration loop และระเบียบวิธีสร้าง gold set

Type: grilling
Status: resolved
Blocked by: 03 ✅, 14 ✅, 07 ⏳ (ยังไม่เสร็จ — แก้โดยออกแบบระเบียบวิธีเป็นสองทางตามผลของ 07 ดู §2)

## Question

ระบบจะ "เรียนรู้ให้ตรงกับอาจารย์" ด้วยกลไกอะไรที่เป็นรูปธรรม วัดด้วยตัวเลขอะไร และเมื่อไรถือว่าตรงพอแล้ว?

นี่คือหัวใจของโจทย์ข้อ 8 และเป็นส่วนที่ทำให้โครงงานนี้เป็นงานวิจัย ไม่ใช่แค่ระบบ CRUD ที่ต่อ LLM ผลของ ticket นี้ต้องเป็นระเบียบวิธี (methodology) ที่เขียนลงบทที่ 3 ของรายงานได้เลย

## สิ่งที่ต้องตัดสิน

1. **นิยาม gold set** — ชุดข้อมูลที่ถือเป็น "คำตอบที่ถูกต้อง" สร้างขึ้นอย่างไร
   - ใช้งานเก่าจาก ticket 07 กี่ชิ้น ต้อง re-grade ด้วย rubric ใหม่กี่ชิ้น
   - อาจารย์ตรวจกี่รอบต่อชิ้น; ถ้าตรวจสองรอบห่างกันสองสัปดาห์แล้วให้คะแนนต่างกัน จะยึดอันไหน
   - แบ่ง train / validation / test อย่างไร — **ต้องมีชุด test ที่ไม่เคยถูกใช้ปรับ prompt เลย** ไม่งั้นตัวเลขที่รายงานจะเป็นการหลอกตัวเอง
   - ขนาดขั้นต่ำที่ยอมรับได้คือเท่าไร (อ้างอิงตัวเลขจาก ticket 03)
2. **สิ่งที่ loop นี้ปรับได้** — ตัดสินว่าอนุญาตให้ระบบแก้อะไรบ้าง เรียงจากเสี่ยงน้อยไปมาก
   - เลือก few-shot example ชุดใหม่จากงานที่อาจารย์ตรวจแล้ว (เสี่ยงน้อย เห็นผลเร็ว)
   - แก้ถ้อยคำคำอธิบายของ criterion/level ให้ชัดขึ้น (ต้องให้อาจารย์อนุมัติก่อน เพราะกระทบความหมายของ rubric)
   - ปรับค่าชดเชยเชิงตัวเลขต่อ criterion (แก้อาการให้คะแนนสูง/ต่ำกว่าอาจารย์เป็นระบบ)
   - แก้ system prompt ของ agent
   - **ข้อสำคัญ:** ถ้าระบบแก้ถ้อยคำ rubric เอง จะกระทบเวอร์ชัน rubric ตาม ticket 10 ต้องตกลงให้ตรงกันว่าการแก้เพื่อ calibrate สร้างเวอร์ชันใหม่หรือแยกเก็บเป็น "prompt layer" ที่ไม่ใช่ตัว rubric ทางการ
3. **ตัวชี้วัด** — เลือกจาก ticket 03 ว่าจะรายงานอะไร (คำแนะนำ: QWK ต่อ criterion + MAE ของคะแนนรวม + exact/adjacent agreement) และวัดที่ระดับ criterion หรือระดับชิ้นงาน หรือทั้งสอง
4. **เกณฑ์ความสำเร็จ** — ต้องได้ตัวเลขเท่าไรจึงถือว่าระบบใช้ได้จริง และต้องเทียบกับอะไรเป็นฐาน (baseline) — เสนอสามฐาน: เดาคะแนนกลางทุกครั้ง, LLM ตรวจด้วย rubric ดิบไม่ปรับอะไร, และความสอดคล้องของอาจารย์กับตัวเองเมื่อตรวจซ้ำ (เพดานบน)
5. **จังหวะการทำงานของ loop** — ปรับทุกครั้งที่อาจารย์แก้คะแนน / สะสมครบ N ชิ้นแล้วปรับ / อาจารย์กดสั่งปรับเอง — และใครอนุมัติการเปลี่ยนแปลงก่อนนำไปใช้จริง
6. **การป้องกันการถดถอย** — ก่อนรับ prompt/rubric เวอร์ชันใหม่ ต้องรันกับชุด test เดิมแล้วเทียบคะแนนก่อนเสมอไหม; ถ้าเวอร์ชันใหม่แย่ลงต้องย้อนกลับอัตโนมัติไหม
7. **สิ่งที่ต้องเก็บเพื่อการวิจัย** — ทุกครั้งที่ตรวจต้องบันทึกอะไรบ้างจึงจะเขียนบทวิเคราะห์ผลได้ (เวอร์ชัน prompt, โมเดล, seed/temperature, ผลดิบ, คะแนนอาจารย์, ส่วนต่าง, เวลา, ต้นทุน)

## สิ่งที่ต้องได้เมื่อจบ ticket

- ระเบียบวิธีสร้าง gold set เขียนเป็นขั้นตอนที่ทำตามได้
- แผนภาพ calibration loop (ป้อนอะไรเข้า ปรับอะไร วัดอะไร ตัดสินใจอย่างไร)
- ตารางตัวชี้วัดพร้อมเกณฑ์ความสำเร็จที่เป็นตัวเลข และ baseline ทั้งสามตัว
- รายการข้อมูลที่ต้องบันทึกทุกครั้งที่ตรวจ (ส่งต่อให้ ticket 12 และ 22)

### 2. Gold set — ออกแบบเป็นสองทางตามผลของ ticket 07

**ticket 07 ยังไม่เสร็จ แต่ไม่ต้องรอ** เพราะทั้งสองทางใช้ระเบียบวิธีเดียวกัน ต่างกันแค่จุดตั้งต้นและตารางเวลา

| | **ทาง A — คลังงานเก่าใช้ได้** | **ทาง B — คลังงานเก่าใช้ไม่ได้** |
|---|---|---|
| เงื่อนไข | มีงานเก่าที่เปิดไฟล์ได้ ≥ 60 ชิ้น กระจายทุกช่วงคะแนน และผ่านเรื่องความยินยอม/จริยธรรมวิจัย | ลิงก์ตาย / เหลือแต่ PDF ที่ดึง JSON ไม่ได้ / ติดเรื่องความยินยอม |
| gold set เริ่มต้น | **re-grade งานเก่า 40–60 ชิ้นด้วย rubric ใหม่** ก่อนเปิดเทอม | ไม่มี — สร้างสดระหว่างภาค 1 |
| ได้อะไรเพิ่ม | มี anchor set + error taxonomy + baseline ตัวแรก **ก่อน** นักศึกษาส่งงานชิ้นแรก | เริ่มวัดได้จริงหลังชิ้นงานที่ 2–3 ของภาค 1 |
| ผลต่อตารางเวลา | P1 (prompt optimization) เริ่มได้ ต.ค. 2026 ตามแผน research 04 | P1 เลื่อนไป พ.ย.–ธ.ค. 2026 · **P3 ยังทันแต่หน้าต่างแคบลง** |
| ความเสี่ยงที่ต้องเขียนในเล่ม | งานเก่าอาจมาจากโจทย์คนละแบบ → **ห้าม calibrate ข้ามประเภทงาน** (research 03 §6.3) ใช้เป็น anchor/dev ได้ แต่**ห้ามใช้เป็น test set** ของภาคปัจจุบัน | N ต่อการตัดสินใจแต่ละครั้งน้อยลง ต้องยอมรับ CI ที่กว้างกว่าและรายงานตามจริง |

**ทางไหนก็ตาม ระเบียบวิธีสร้าง gold set เหมือนกัน 6 ขั้น**

1. **เลือกงานแบบ stratified ตามระดับคะแนนที่คาด** ไม่ใช่สุ่มล้วน — ป้องกันไม่ให้ระดับหายาก (ระดับ 1 และ 2) ไม่มีตัวอย่างเลย ซึ่งเกิดขึ้นเสมอถ้าสุ่มล้วนในชั้นที่คนส่วนใหญ่ทำได้ดี
2. **ปกปิดที่มา** — ตัดชื่อ รหัส และคะแนนเดิมออกก่อนอาจารย์ตรวจ สลับลำดับใหม่
3. **อาจารย์ตรวจโดยไม่เห็นคะแนน AI** (โหมด blind ของ ticket 14) ทีละเกณฑ์ตาม rubric ที่จะใช้จริง
4. **ตรวจซ้ำรอบสองห่างจากรอบแรก 2–3 สัปดาห์ สลับลำดับใหม่ เฉพาะ 20–30 ชิ้น** — นี่คือ **ตัวหารของงานวิจัยทั้งเล่ม** (research 03 §3.3) ทำได้ด้วยอาจารย์คนเดียวถ้าไม่มีผู้ตรวจคนที่สอง
5. **เมื่อสองรอบไม่ตรงกัน**: เก็บทั้งสองค่าไว้ดิบ ๆ เพื่อคำนวณเพดานมนุษย์ แล้วให้อาจารย์ **ตัดสินค่าสุดท้าย (adjudicated value)** อีกครั้งโดยเห็นทั้งสองค่า — ค่านี้เท่านั้นที่เป็น gold label **ห้ามใช้ค่าเฉลี่ยของสองรอบ** เพราะจะได้ค่าที่ไม่ตรงกับระดับใดใน rubric เลย และทำลายโครงสร้าง ordinal
6. **ล็อก test set ทันทีที่สร้างเสร็จ** — เก็บแยก มี checksum ระบบต้องปฏิเสธการรัน optimization ใด ๆ ที่แตะข้อมูลชุดนี้

**การแบ่งชุดข้อมูล — แบ่งที่ระดับนักศึกษา ไม่ใช่ระดับแถว**

research 04 §7.3 ระบุแหล่ง leakage 4 แหล่ง (นักศึกษาคนเดียวกัน · งานกลุ่มเดียวกัน · เกณฑ์หลายข้อของ submission เดียวกัน · โจทย์ซ้ำข้ามเทอม) ดังนั้น

- ใช้ **GroupKFold โดย group = นักศึกษา** (ถ้าเป็นงานกลุ่ม group = กลุ่ม)
- สัดส่วน **dev 60% / test 40%** ตาม research 03 §2.4 ข้อ 6
- คำนวณ CI ด้วย **cluster bootstrap ที่ resample ระดับนักศึกษา** ไม่ใช่ระดับเซลล์ ไม่งั้น CI จะแคบเกินจริง

### 3. งบตรวจของอาจารย์ — 100–150 ชิ้น/เทอม แบ่งเป็น 5 รอบ

ประมาณ **15–20 ชิ้นต่อสัปดาห์** กระจายทั้งเทอม ไม่ใช่กองไว้สัปดาห์เดียว

| รอบ | จำนวน | วิธีเลือก | กองไหน | เอาไปทำอะไร |
|---|---|---|---|---|
| **0** | 20–30 | สุ่ม + **ตรวจซ้ำโดยอาจารย์คนเดิมหลัง 2–3 สัปดาห์** | Measurement | **หาเพดานมนุษย์** — ตัวหารของทั้งงานวิจัย |
| **1** | 20–30 | stratified ตามระดับคะแนนที่คาด | Improvement | สร้าง anchor set + error taxonomy |
| **2** | 30–40 | **สุ่มล้วน → ล็อกเป็น test set แช่แข็ง** | Measurement | รายงานผลครั้งเดียวตอนจบ **ห้ามแตะระหว่างทาง** |
| **3** | 30–50 | uncertainty + boundary | Improvement | fit calibration, ปรับคำอธิบายชั้น AI |
| **4** | ต่อเนื่อง | **ทุกครั้งที่อาจารย์แก้คะแนนในระบบจริง** | Improvement (ปนเปื้อน anchoring) | สะสม N ให้โตขึ้นเรื่อย ๆ |

**รอบ 4 เป็นของฟรีที่มีมูลค่าสูงสุดของทั้งระบบ** — การออกแบบ UI ให้ทุกการแก้คะแนนกลายเป็น labeled data โดยอัตโนมัติ คือฟีเจอร์ที่แยกโครงงานนี้ออกจากระบบตรวจงานทั่วไป **แต่ต้องติดธงว่าปนเปื้อน anchoring** (ticket 12/14) และ **ห้ามใช้เป็น measurement**

**การเลือกชิ้นในรอบ 3 — วัดความไม่มั่นใจอย่างไรเมื่อ API ไม่คืน logprob**

ให้ AI ตรวจงานชิ้นเดียวกัน 3 ครั้งด้วย temperature > 0 แล้วใช้ **ความแปรปรวนระหว่างคำตอบเป็น proxy ของความไม่มั่นใจ** (research 03 §7.3) — ใช้ได้ทันทีกับ API เชิงพาณิชย์ทุกตัว และ **สอดคล้องกับ ticket 09 ที่ห้ามเก็บค่าความมั่นใจที่ LLM รายงานเอง** เพราะนี่คือความไม่มั่นใจที่วัดจากพฤติกรรมจริง ไม่ใช่ตัวเลขที่โมเดลบอกเอง

### 4. สิ่งที่ loop ปรับได้ — 4 ชั้น เรียงจากเสี่ยงน้อยไปมาก

| ชั้น | ปรับอะไร | N ขั้นต่ำ | ใครอนุมัติ | สร้าง rubric เวอร์ชันใหม่ไหม |
|---|---|---|---|---|
| **A** | **เลือก anchor example ชุดใหม่** จากงานที่อาจารย์ตรวจแล้ว | 10–30 | อาจารย์ดูรายการตัวอย่างแล้วกดรับ | ไม่ |
| **B** | **คำอธิบายชั้น AI** (ขยายความเกณฑ์ให้ AI เข้าใจตรง) | 10–30 | **อาจารย์อนุมัติทีละข้อ พร้อมเห็นข้อความก่อน/หลัง** | ไม่ (แต่ดู §5) |
| **C** | **ชดเชยเชิงตัวเลขต่อเกณฑ์** — offset → linear → isotonic | 20–30 / 40–60 / 100+ | อาจารย์เห็นตัวเลขและเหตุผล | ไม่ |
| **D** | **system prompt ของ agent** | 60+ | อาจารย์อนุมัติ + ต้องผ่านประตูกันถดถอย | ไม่ |

**ลำดับที่ต้องบังคับ: เจอ bias แล้วแก้ที่ชั้น C ก่อน ไม่ใช่ชั้น B หรือ D**

research 03 §6.1 ให้เหตุผลไว้สามข้อ — bias คงที่คือสิ่งที่วัดได้ถูกที่สุดเมื่อ N น้อย (ที่ N = 50 ตรวจจับ bias 0.25 ระดับได้ที่ power 0.81 ขณะที่ ΔQWK ขนาดเดียวกันจากการแก้ prompt ต้องใช้ N เป็นร้อย) · การแก้ prompt มีผลข้างเคียงข้ามเกณฑ์ที่คาดเดาไม่ได้ · และ "ระบบหักคะแนนเกณฑ์นี้ลง 0.7 เพราะจาก 60 ชิ้นที่อาจารย์ตรวจ ระบบให้สูงกว่าเฉลี่ย 0.7" เป็นประโยคที่ audit ได้ ต่างจาก "เราแก้คำในเกณฑ์"

**กฎแยกแยะที่ใช้ตัดสินหน้างาน**

> **ถ้า bias คงที่ทุกระดับคะแนน → ชั้น C (ชดเชยตัวเลข)**
> **ถ้า bias ต่างกันตามระดับ เช่นให้สูงเกินเฉพาะงานอ่อน → เป็นปัญหาความเข้าใจ ต้องไปชั้น B**

และ **ที่ N หลักสิบให้ใช้ calibration ที่มีพารามิเตอร์น้อยที่สุดเท่าที่ทำได้** (offset > linear > isotonic) ตาม arXiv:2606.01034 · **ต้อง fit บน dev แล้ววัดบน test เท่านั้น** · **calibrate ต่อเกณฑ์ ไม่ใช่ต่อคะแนนรวม** เพราะ bias แต่ละเกณฑ์ไปคนละทิศและจะกลบกันเอง · **ห้าม calibrate ข้ามประเภทงาน** · **เก็บทั้งคะแนนดิบและคะแนนหลัง calibrate**

### 5. คำอธิบายสองชั้น — เส้นแบ่งที่ต้องบังคับด้วยคำถามเดียว

**โครงสร้าง**

| ชั้น | เก็บที่ไหน | นักศึกษาเห็น | เปลี่ยนแล้วเกิดอะไร |
|---|---|---|---|
| **ชั้น 1 — rubric ทางการ** | `RubricVersion` (ticket 10) | เห็นตั้งแต่ตอนได้รับโจทย์ | **RubricVersion ใหม่** เวอร์ชันที่ตรวจไปแล้วแก้ไม่ได้ตลอดไป |
| **ชั้น 2 — คำอธิบายสำหรับ AI** | `JudgePromptVersion` แยกเป็น entity ของตัวเอง | **ไม่แสดงโดยอัตโนมัติ แต่ขอดูได้เสมอ** | `JudgePromptVersion` ใหม่ ไม่กระทบ rubric |

ชั้น 2 บรรจุ: คำขยายความของแต่ละเกณฑ์ · anchor example พร้อมคะแนนและเหตุผล · few-shot · พารามิเตอร์ calibration ของชั้น C · system prompt

**เส้นแบ่งบังคับใช้ด้วยคำถามข้อเดียว**

> **"ถ้านักศึกษาอ่านข้อความนี้ตอนกำลังทำงาน เขาจะทำงานต่างไปจากเดิมไหม?"**
>
> - **ไม่ต่าง** → เป็นการขยายความให้ AI เข้าใจตรงกับที่อาจารย์เข้าใจอยู่แล้ว → **ชั้น 2 ได้**
> - **ต่าง** → เท่ากับมีเกณฑ์ที่ไม่ได้บอกล่วงหน้า → **ต้องขึ้นชั้น 1 เป็น RubricVersion ใหม่** และใช้กับชิ้นงานถัดไปเท่านั้น

ตัวอย่าง: "ให้ถือว่าคำว่า *ความสม่ำเสมอ* หมายถึงความสม่ำเสมอของระบบดีไซน์ ไม่ใช่ความสวยงาม" = **ชั้น 2** เพราะเป็นความหมายที่อาจารย์ตั้งใจอยู่แล้ว · แต่ "ต้องมีอย่างน้อย 3 breakpoint" = **ชั้น 1** เพราะเป็นข้อกำหนดใหม่ที่นักศึกษาไม่มีทางรู้

**เปิดให้นักศึกษาดูได้ถ้าขอ** (การตัดสินใจของอาจารย์ 2026-08-06)

- หน้าคะแนนของนักศึกษามีลิงก์ **"ดูคำอธิบายที่ระบบใช้ตรวจ"** แสดง `JudgePromptVersion` ที่ใช้กับชิ้นงานนั้นจริง ๆ (ไม่ใช่เวอร์ชันล่าสุด)
- **ข้อบังคับที่ตามมาและมีค่ามาก: ทุกข้อความในชั้น 2 ต้องเขียนเป็นภาษาไทยที่นักศึกษาอ่านรู้เรื่อง** ห้ามเป็นเทคนิค prompt engineering ที่อธิบายให้คนฟังไม่ได้ (เช่น "You MUST be strict", "think step by step แล้วหักคะแนน") — เพราะรู้ว่าอาจถูกเปิดดู
- ข้อบังคับนี้ทำหน้าที่เป็น **ตัวกรองคุณภาพในตัวเอง**: ถ้าเขียนให้นักศึกษาอ่านรู้เรื่องไม่ได้ แปลว่ากำลังจูนให้ AI เดาถูกโดยไม่ได้ทำให้ AI เข้าใจ ซึ่งเป็น reward hacking รูปแบบหนึ่งตาม research 04 §7.7
- **ไม่แสดงโดยอัตโนมัติ** เพราะระหว่างเทอมชั้น 2 เปลี่ยนได้หลายรอบ ถ้าประกาศทุกรอบจะกลายเป็นการเปลี่ยนกติกากลางเกมในสายตานักศึกษา ทั้งที่ความหมายของเกณฑ์ไม่ได้เปลี่ยน

**แก้กลับเข้า ticket 10:** ฟิลด์ `Criterion.llm_guidance` ย้ายออกจาก `RubricVersion` ไปอยู่ใน `JudgePromptVersion` — กฎเดิมของ ticket 10 ที่ว่า "แก้ `llm_guidance` = เวอร์ชันใหม่" จึงหมายถึงเวอร์ชันของ JudgePrompt ไม่ใช่ของ rubric

### 6. ตัวชี้วัด — รายงาน 6 ตัวพร้อมกันเสมอ

| ตัวชี้วัด | ระดับที่วัด | ทำไมต้องมี |
|---|---|---|
| **Exact / adjacent agreement** | เกณฑ์ | CI แคบกว่า QWK ที่ N เดียวกัน และสื่อสารกับอาจารย์ได้ตรงที่สุด → **ใช้เป็นตัวรายงานหลัก** |
| **QWK** | เกณฑ์ + ชิ้นงาน | ตัวเลขที่วงการ AES ใช้ แต่มี kappa paradox — **ห้ามรายงานเดี่ยว** |
| **MAE** | ชิ้นงาน | ผลกระทบต่อคะแนนจริงที่นักศึกษาได้ |
| **Bias (ค่าเฉลี่ยส่วนต่าง) ต่อเกณฑ์** | เกณฑ์ | เป็นตัวสั่งการชั้น C โดยตรง และวัดได้แม่นที่สุดที่ N น้อย |
| **การกระจายของระดับที่ออก** | เกณฑ์ | จับอาการ regression to the mean ที่พบบ่อยมากใน LLM judge |
| **สัดส่วนที่ตรวจไม่ได้ / ต้องส่งต่อมนุษย์** | ชิ้นงาน | ตัวเลขนี้แย่ลงได้เงียบ ๆ ขณะที่ QWK ดีขึ้น |

**ทุกตัวต้องรายงานพร้อม 95% CI จาก cluster bootstrap ที่ระดับนักศึกษา** และ **ทุกการเปรียบเทียบสองเวอร์ชันต้องเป็น paired บนงานชุดเดียวกัน** แล้ว bootstrap ที่ผลต่าง (research 03 §2.4)

**หน่วยวิเคราะห์คือ (งาน × เกณฑ์)** — 40 ชิ้น × 7 เกณฑ์ = 280 การตัดสิน ทำให้วัด bias รายเกณฑ์ได้ **แต่ effective N ต่ำกว่ามาก** เพราะคะแนนภายในงานเดียวกันสหสัมพันธ์กันสูง (research 04 §7.2.1) — ต้องเขียนข้อจำกัดนี้ในเล่มตรง ๆ

**สามกองที่ต้องแยกนับเสมอ** (จาก ticket 14): ตรวจแบบ blind / เปิดดูคะแนน AI แล้วแก้ / ยืนยันยกชั้นโดยไม่เปิดดู — **กองแรกเท่านั้นที่ใช้รายงาน agreement ได้**

### 7. เกณฑ์ความสำเร็จ — ประกาศล่วงหน้าก่อนเริ่มทดลอง

> **เกณฑ์หลัก (pre-registered): AI–อาจารย์ agreement ต่ำกว่า อาจารย์–อาจารย์ (หรืออาจารย์–ตัวเองเมื่อตรวจซ้ำ) ไม่เกิน 0.10 QWK**

กรอบนี้มาจาก Williamson, Xi & Breyer (2012) ที่วงการ automated essay scoring ใช้จริง และป้องกันตัวได้ในห้องสอบดีกว่า "QWK ≥ 0.70" ลอย ๆ มาก — เพราะ **งาน open-ended เชิงออกแบบมีมนุษย์สองคนตรงกันเพียง 55–75% เท่านั้น** (Jonsson & Svingby 2007 review 75 งานวิจัย) การไล่ให้ AI ทำได้ 90% คือการไล่ตามเสียงรบกวน ไม่ใช่ความแม่นยำ

**รูปแบบประโยคที่จะเขียนในเล่ม**

> "AI–teacher QWK = 0.68 [0.58, 0.79] เทียบกับ teacher–teacher QWK = 0.71 [0.60, 0.81] — ต่างกัน 0.03 ซึ่งอยู่ในเกณฑ์ที่ประกาศไว้ล่วงหน้า"

**เกณฑ์รอง (รายงานด้วยเสมอ แต่ไม่ใช่ตัวตัดสิน)**: adjacent agreement ≥ 90% · |bias| ทุกเกณฑ์ < 0.25 ระดับ · สัดส่วนที่ต้องส่งต่อมนุษย์ไม่เพิ่มขึ้น

**Baseline ที่ต้องเทียบ — 4 ตัว ไม่ใช่ 3**

| # | Baseline | ทำไมต้องมี |
|---|---|---|
| B0 | เดาระดับกลางทุกครั้ง | พื้นล่างสุด · ถ้าชนะไม่ขาดแปลว่าไม่มีอะไรเกิดขึ้น |
| B1 | ให้คะแนนตามการกระจายของอาจารย์แบบสุ่ม | จับกรณีที่ QWK สูงเพราะ marginal ตรงกัน ไม่ใช่เพราะตัดสินถูก |
| B2 | LLM ตรวจด้วย rubric ดิบ ไม่มี anchor ไม่มี calibration | **คือ "ก่อน" ของโครงงานนี้** |
| B3 | LLM + prompt ที่ optimize แล้ว (ปลาย P1) | **research 04 §7.3 เตือนไว้ชัด: สาย RL ต้องเทียบตัวนี้ ไม่ใช่ B2** ไม่งั้นเครดิตของ prompt optimization จะถูกนับเป็นของ RL |
| — | เพดานมนุษย์ | ไม่ใช่ baseline แต่เป็น **ตัวหาร** |

### 8. จังหวะ loop และการอนุมัติ

**สะสมครบหนึ่งชิ้นงานแล้วเสนอเป็นชุด อาจารย์อนุมัติทีละข้อ**

1. อาจารย์ตรวจงานชิ้นงานนั้นจนจบและกดประกาศคะแนน (ticket 14)
2. ระบบวิเคราะห์ส่วนต่างทั้งชิ้นงาน แล้วสร้าง **ข้อเสนอ (proposal)** เป็นชุด — แต่ละข้อระบุ: ชั้นที่จะแก้ (A/B/C/D) · เกณฑ์ที่กระทบ · หลักฐาน (จากงานกี่ชิ้น bias เท่าไร) · ข้อความก่อน/หลัง · ผลที่คาดบน dev set
3. **อาจารย์กดรับ/ปฏิเสธทีละข้อ** ปฏิเสธแล้วต้องบอกเหตุผลสั้น ๆ — ข้อมูลนี้เองเป็นบทวิเคราะห์ที่ดีในเล่ม (AI เสนออะไรที่อาจารย์ไม่เอา และทำไม)
4. ข้อที่ถูกรับรวมกันเป็น **JudgePromptVersion ใหม่หนึ่งเวอร์ชัน** ผ่านประตู §9 แล้วจึงใช้กับชิ้นงานถัดไป

**เหตุผลที่ไม่ปรับทุกครั้งที่อาจารย์แก้คะแนน** — research 03 §5.4 เตือนว่าที่ N น้อย การปรับถี่ ๆ คือ overfit ที่รับประกันได้ และจะทำให้นักศึกษาที่ส่งงานชิ้นเดียวกันถูกตรวจด้วยระบบคนละเวอร์ชัน ซึ่งเป็นปัญหาความเป็นธรรม ไม่ใช่แค่ปัญหาทางสถิติ

**เหตุผลที่ไม่รอให้อาจารย์กดสั่งเอง** — ถ้าอาจารย์ลืมกด loop ก็ไม่เกิด และจะไม่มีข้อมูลว่า loop ได้ผลจริงหรือไม่ ซึ่งทำให้โครงงานไม่มีผลการทดลองจะรายงาน

**หนึ่ง JudgePromptVersion = หนึ่งชิ้นงาน** — เวอร์ชันเปลี่ยนได้เฉพาะระหว่างชิ้นงาน ห้ามเปลี่ยนกลางชิ้นงาน เพื่อให้ทุกคนในชิ้นงานเดียวกันถูกตรวจด้วยระบบเดียวกันเสมอ

### 9. ประตูกันการถดถอย

**ทุก JudgePromptVersion ใหม่ต้องผ่านสามด่านก่อนใช้จริง ไม่มีข้อยกเว้น**

| ด่าน | เงื่อนไข | ถ้าไม่ผ่าน |
|---|---|---|
| **D1 — ไม่ถดถอยบน dev เดิม** | รันบน dev set ทั้งชุด เทียบ paired กับเวอร์ชันปัจจุบัน · **ห้ามมีเกณฑ์ใดที่ agreement แย่ลงเกิน 5pp** | ปฏิเสธทั้งชุด แสดงว่าเกณฑ์ไหนพัง |
| **D2 — ไม่ทำให้สัดส่วนตรวจไม่ได้เพิ่ม** | สัดส่วนที่ต้องส่งต่อมนุษย์ต้องไม่เพิ่มเกิน 5pp | ปฏิเสธ — ระบบที่แม่นขึ้นแต่ยอมแพ้บ่อยขึ้นไม่ได้ช่วยอาจารย์ |
| **D3 — ผลรวมดีขึ้นจริงแบบ paired** | ขอบล่างของ 95% CI ของ ΔQWK แบบ paired ต้อง > 0 หรืออย่างน้อยไม่ติดลบ | ให้ผ่านได้ถ้า D1/D2 ผ่านและอาจารย์ยืนยัน แต่**ต้องบันทึกว่าผ่านโดยไม่มีหลักฐานเชิงสถิติ** |

- **ย้อนกลับได้ในคลิกเดียวเสมอ** เพราะทุกเวอร์ชันเก็บครบและคะแนนทุกแถวชี้เวอร์ชันที่ใช้ตรวจจริง (ticket 12)
- **ห้ามย้อนกลับอัตโนมัติ** — ต้องเป็นการตัดสินใจของอาจารย์ที่มีบันทึก ไม่งั้นระบบจะแกว่งไปมาโดยไม่มีใครรู้ว่าตอนนี้ใช้เวอร์ชันอะไรอยู่
- **ห้ามแตะ test set ในทุกด่าน** — ระบบต้องปฏิเสธคำสั่งที่พยายามอ่าน test set นอกช่วงรายงานผลปลายโครงงาน และบันทึกความพยายามนั้นไว้
