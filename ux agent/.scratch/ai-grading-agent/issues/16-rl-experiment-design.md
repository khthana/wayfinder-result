# 16 — ออกแบบการทดลอง RL ให้เป็นงานวิจัยที่ล้มได้อย่างมีศักดิ์ศรี

Type: grilling
Status: resolved
Blocked by: 04 ✅, 15 ✅

## Question

การทดลอง RL ในโครงงานนี้จะตั้งคำถามวิจัยว่าอะไร ทำอย่างไร ใช้ทรัพยากรเท่าไร และจะรู้ได้อย่างไรว่าสำเร็จหรือล้มเหลว?

จาก charting session ตกลงกันแล้วว่า **RL คือ experiment ไม่ใช่ฟีเจอร์ที่ต้อง ship** — ticket นี้ต้องทำให้ข้อตกลงนั้นเป็นรูปธรรม คือออกแบบการทดลองที่ถ้าผลออกมาเป็นลบ ก็ยังเป็นผลการทดลองที่เขียนรายงานได้และโครงงานยังจบตรงเวลา

## สิ่งที่ต้องตัดสิน

1. **คำถามวิจัย** — เลือกหนึ่งข้อให้คมและวัดได้ ตัวอย่าง
   - "การเรียนรู้จาก feedback ของอาจารย์แบบ preference learning ทำให้ agreement ระหว่าง AI กับอาจารย์สูงขึ้นกว่าการปรับ prompt เพียงอย่างเดียวหรือไม่"
   - "ต้องใช้ตัวอย่างที่อาจารย์ตรวจกี่ชิ้น จึงจะเห็นการปรับปรุงที่มีนัยสำคัญ"
   - "โมเดลเปิดขนาดเล็กที่ปรับด้วยข้อมูลของวิชานี้ เทียบกับโมเดล frontier ที่ใช้ prompt ดี ๆ ให้ผลต่างกันแค่ไหน" (คำถามนี้มีคุณค่าเชิงปฏิบัติสูง เพราะเชื่อมกับต้นทุนและ PDPA)
2. **วิธีที่จะทดลองจริง** — เลือกจากที่ ticket 04 หามาได้ 1-2 วิธี ไม่ใช่ทั้งหมด และระบุว่าทำไมเลือกวิธีนั้น
3. **นิยาม state / action / reward** — ถ้าจะเรียกว่า RL ต้องกำหนดให้ชัด reward มาจากอะไร (ส่วนต่างระหว่างคะแนน AI กับอาจารย์? การที่อาจารย์ยอมรับคะแนนโดยไม่แก้?) และมีปัญหา reward hacking แบบไหนที่ต้องระวัง
4. **ทรัพยากร** — ต้องใช้ GPU อะไร ที่ไหน (เครื่องคณะจาก ticket 06 / Colab / Kaggle / เช่าชั่วโมง) ใช้เวลากี่ชั่วโมง ค่าใช้จ่ายเท่าไร ใครจ่าย
5. **กรอบเวลาและจุดตัดสินใจ (สำคัญที่สุด)** — กำหนดวันที่ชัดเจนว่าถ้าถึงวันนั้นแล้วยังไม่เห็นสัญญาณบวก จะหยุดและเขียนเป็นผลเชิงลบ — ป้องกันไม่ให้การทดลองกลืนเวลาที่ต้องใช้สร้างระบบหลัก
6. **การเชื่อมกับระบบจริง** — ถ้าการทดลองสำเร็จ จะนำผลกลับเข้าระบบอย่างไร หรือจะอยู่แยกเป็นสคริปต์วิจัยเท่านั้น (คำแนะนำ: แยก ไม่ต้องต่อเข้าระบบใน MVP)
7. **ทางถอยที่ให้เกียรติโจทย์** — ถ้า RL เต็มรูปแบบทำไม่ได้จริง จะรายงานอะไรแทน (เช่น ผลการทดลองที่แสดงว่าข้อมูลระดับนี้ไม่พอ พร้อมการวิเคราะห์ว่าต้องมีเท่าไรจึงจะพอ ซึ่งเป็นผลงานที่มีคุณค่าในตัวเอง)

## สิ่งที่ต้องได้เมื่อจบ ticket

- คำถามวิจัยหนึ่งข้อที่เขียนเป็นประโยคเดียว
- แผนการทดลองเป็นขั้นตอน พร้อมข้อมูลที่ต้องใช้และทรัพยากรที่ต้องมี
- เกณฑ์สำเร็จ/ล้มเหลวที่เป็นตัวเลข และ **วันที่ตัดสินใจหยุด**
- ย่อหน้าทางถอยที่พร้อมใช้ถ้าผลออกมาเป็นลบ

## Answer

> ยกไปเป็น **บทที่ 3 ส่วนการออกแบบการทดลอง** และ **บทที่ 5 ข้อจำกัด** ได้โดยตรง · ต่อยอดจาก [research 04](../research/04-rl-small-data.md) และใช้โครงระเบียบวิธีของ [ticket 15](15-calibration-loop-design.md) ทั้งชุด **ห้ามสร้าง test set ใหม่**

### 1. คำถามวิจัย — หนึ่งประโยค

> **ที่ระดับข้อมูลของรายวิชาเดียว (นักศึกษา 40–60 คน 2 ภาคการศึกษา) การปรับ prompt อัตโนมัติ กับการเรียนรู้จากความชอบของอาจารย์ (preference learning) ทำให้ agreement ระหว่าง AI กับอาจารย์เพิ่มขึ้นเป็นเส้นโค้งอย่างไรเมื่อจำนวนชิ้นงานที่อาจารย์ตรวจเพิ่มขึ้น และต้องใช้กี่ชิ้นจึงจะแยกสองวิธีนี้ออกจากกันได้อย่างมีนัยสำคัญ**

**สามคำถามย่อยที่ตอบไปพร้อมกัน**

- **RQ1 (เส้นโค้ง):** agreement เพิ่มขึ้นเท่าไรต่อชิ้นงานที่อาจารย์ตรวจ และเส้นโค้งเริ่มแบนที่ N เท่าไร
- **RQ2 (เปรียบเทียบ):** ที่ N เท่ากัน สายไหนดีกว่า และจุดที่สลับอันดับ (ถ้ามี) อยู่ที่ N เท่าไร
- **RQ3 (นัยเชิงปฏิบัติ):** ถ้าอาจารย์มีเวลาตรวจได้ X ชิ้นต่อเทอม ควรลงแรงไปที่ทางไหน

**ทำไมกรอบนี้ล้มไม่ได้โดยโครงสร้าง** — เส้นโค้งการเรียนรู้ **เป็นผลการทดลองไม่ว่าจะชันหรือแบน** ถ้าชัน = เรียนรู้ได้จริง มีตัวเลขบอกว่าต้องใช้เท่าไร · ถ้าแบน = ข้อมูลระดับนี้ไม่พอ **พร้อมหลักฐานเชิงปริมาณและการประมาณว่าต้องมีเท่าไรจึงจะพอ** ซึ่งเป็นคำตอบที่มีค่าต่อทุกคนที่คิดจะทำระบบแบบเดียวกันในวิชาเดียว · เทียบกับการตั้งคำถามว่า "RL ทำให้ดีขึ้นไหม" ที่ถ้าผลออกมาว่าไม่ ก็เหลือแค่ "ไม่พบความแตกต่าง" ซึ่งอ่อนกว่ามากในห้องสอบ

**สมมติฐานที่ประกาศล่วงหน้า (pre-registered)** — เขียนลงเล่มก่อนเริ่มเก็บข้อมูล เพื่อไม่ให้เป็นการอธิบายผลย้อนหลัง

| # | สมมติฐาน | ฐานที่มา |
|---|---|---|
| H1 | ทั้งสองสายให้เส้นโค้งที่ **ชันมากช่วง N = 0–60 แล้วแบนเร็ว** | research 03 §2.3 — ที่ N หลักสิบ bias ต่อเกณฑ์คือสิ่งที่แก้ได้คุ้มที่สุด และแก้ได้เร็ว |
| H2 | **สายปรับ prompt ชนะที่ทุกค่า N ในช่วงที่โครงงานนี้เอื้อมถึง** | GEPA ชนะ GRPO 6% เฉลี่ย / 20% สูงสุด ด้วย rollout น้อยกว่า 35 เท่า |
| H3 | ผลต่างระหว่างสองสาย **มี CI คร่อมศูนย์ตลอด** ที่ N ≤ 200 | research 03 §2.3 — paired ΔQWK ต้องการ N ~150–300 จึงจะตรวจจับผลต่าง 0.15 ได้ที่ power 0.9 และผลต่างที่คาดในที่นี้เล็กกว่านั้น |
| H4 | ตัวที่ขยับ agreement ได้มากที่สุดต่อหน่วยแรง **ไม่ใช่ทั้งสองสาย แต่คือ anchor example + offset ต่อเกณฑ์** | research 03 §6.1 |

**ถ้า H3 เป็นจริงตามคาด นั่นคือผลของโครงงาน ไม่ใช่ความล้มเหลวของโครงงาน** — และเป็นเหตุผลที่ต้องเขียน H3 ไว้ล่วงหน้า

### 2. สองสายที่นำมาเทียบ และ arm ควบคุม

| สาย | ทำอะไร | แตะ weight ของโมเดลไหม | เรียกว่า RL ได้ไหม |
|---|---|---|---|
| **สาย P — prompt optimization** | ใช้ GEPA/OPRO ค้นหาถ้อยคำของ guidance + เลือกชุด anchor อัตโนมัติ โดยมี agreement บน dev เป็น objective | ไม่ | **ไม่** — วรรณกรรมเรียก self-refine/reflective prompt search |
| **สาย D — preference learning** | DPO/ORPO บนโมเดลเปิดที่ปรับด้วย LoRA จากคู่ (คำตัดสินที่อาจารย์ยอมรับ vs คำตัดสินที่อาจารย์แก้) | ใช่ (LoRA adapter) | **กึ่ง** — เป็น preference optimization ที่พัฒนามาจาก RLHF แต่ไม่มี reward model และไม่มี rollout |
| **สาย B — contextual bandit** *(arm ที่สาม เดินขนานไปด้วย)* | เลือก "กลยุทธ์การตรวจ" ต่อชิ้นงาน แล้วเรียนรู้จากผลย้อนกลับ | ไม่ | **ใช่ — RL ตัวจริงเพียงตัวเดียวในโครงงาน** |

**ทำไมเอาทั้งสามมา ไม่ใช่แค่สองสายที่คำถามวิจัยพูดถึง** — สาย B ราคาถูกที่สุด (ไม่ต้อง GPU ไม่ต้องเทรน ใช้ ~30 observation ต่อ arm) และเป็นตัวเดียวที่ทำให้เล่มพูดคำว่า RL ได้โดยไม่ผิดนิยาม จึงวางเป็น **ฐานที่ต้องมี** ส่วนคำถามวิจัยหลักยังเป็นการเทียบ P กับ D ตามที่ตกลง

**Baseline ใช้ B0–B3 ของ ticket 15 ทั้งชุด** — ย้ำจุดที่พลาดกันบ่อย: **สาย D ต้องเทียบกับ B3 (สาย P ที่ optimize แล้ว) ไม่ใช่ B2 (prompt ดิบ)** ไม่งั้นเครดิตของการปรับ prompt จะถูกนับเป็นผลงานของ preference learning

### 3. วิธีสร้างเส้นโค้งการเรียนรู้

**แกน x = จำนวนชิ้นงานที่อาจารย์ตรวจแบบ blind** ไม่ใช่จำนวนแถวคะแนน — เพราะนี่คือต้นทุนจริงที่อาจารย์จ่าย และเป็นคำตอบที่เอาไปใช้ได้ ("ต้องตรวจกี่ชิ้น")

**จุดบนแกน x:** N ∈ {20, 40, 60, 80, 100} ในภาค 1 · ต่อไปถึง {150, 200, 250} เมื่อรวมภาค 2

**ขั้นตอน**

1. **สุ่มชุดย่อยแบบซ้อนกัน (nested)** — ชุด N=20 ต้องเป็นสับเซ็ตของ N=40 เสมอ เพื่อให้เส้นโค้งสะท้อน "ข้อมูลเพิ่มขึ้น" ไม่ใช่ "บังเอิญได้ชุดที่ง่ายกว่า"
2. **สุ่มซ้ำ 3 ชุดต่อหนึ่งค่า N** (seed ต่างกัน) แล้วรายงานค่าเฉลี่ย ± ช่วง — **ถ้าไม่ทำซ้ำ เส้นโค้งจะขึ้น ๆ ลง ๆ จากเสียงรบกวนล้วน ๆ และตีความไม่ได้เลย**
3. **สุ่มที่ระดับนักศึกษา/กลุ่ม** (GroupKFold) ไม่ใช่ระดับแถว — กันการรั่ว 4 แหล่งของ research 04 §7.3
4. **ทุกจุดวัดผลบน test set ชุดเดียวกันที่แช่แข็งไว้** จาก ticket 15 รอบ 2 · ระหว่างทางใช้ dev set เท่านั้น · test เปิดครั้งเดียว
5. **จำนวนรอบทั้งหมด: 3 seed × 4 ค่า N × 2 สาย = 24 รอบ** เป็นตัวเลขที่ทำจริงได้ในหนึ่งภาค ถ้าเห็นว่าเยอะเกินให้ตัดค่า N ทิ้ง ไม่ใช่ตัดจำนวน seed
6. **CI ด้วย cluster bootstrap ที่ resample ระดับนักศึกษา** และการเทียบ P กับ D ต้องเป็น **paired บนงานชุดเดียวกัน** แล้ว bootstrap ที่ผลต่าง

> **กับดักที่ต้องเขียนกันไว้ในเล่ม:** ถ้าเส้นโค้งขึ้นแล้วลงแล้วขึ้น อย่ารีบตีความว่า "โมเดลเรียนรู้แล้วลืม" — ที่ N ระดับนี้ ความแกว่งขนาดนั้นอธิบายได้ด้วยเสียงรบกวนอย่างเดียว การทำ 3 seed ต่อจุดมีไว้เพื่อให้เห็นข้อนี้ด้วยตาตัวเอง ไม่ใช่แค่เพื่อความสวยของกราฟ

### 4. นิยาม state / action / reward

**สาย D (preference learning) — ไม่ใช่ MDP ต้องเขียนให้ตรง**

DPO ไม่มี state transition ไม่มี rollout มีแค่คู่เปรียบเทียบ **ในเล่มต้องเขียนว่า "preference optimization" และอธิบายว่าต่างจาก RLHF เต็มรูปตรงที่ไม่มี reward model และไม่มีการ sample จากนโยบายระหว่างเทรน** — เขียนผิดตรงนี้คือจุดที่กรรมการจับได้ง่ายที่สุด

**การสร้างคู่ preference — จุดที่ทำผิดกันบ่อย**

วิธีตรงไปตรงมาคือเอา "คำตัดสินของอาจารย์" เป็นตัวชนะ และ "คำตัดสินของ AI" เป็นตัวแพ้ **แต่ทำแบบนั้นไม่ถูก** เพราะข้อความของอาจารย์อยู่นอกการกระจายของโมเดล DPO จะไล่ตามสไตล์การเขียนแทนที่จะไล่ตามการตัดสิน ให้ทำแบบนี้แทน

1. ให้โมเดล **สร้างคำตัดสินเอง k = 4 แบบ** ต่อหนึ่ง (ชิ้นงาน × เกณฑ์)
2. **ตัวชนะ** = ตัวที่ระดับคะแนนตรงกับอาจารย์ที่สุด · **ตัวแพ้** = ตัวที่ห่างที่สุด
3. ถ้า k ตัวให้ระดับเดียวกันหมด **ทิ้งคู่นั้น** — ไม่มีสัญญาณให้เรียน
4. ใช้เฉพาะคู่จาก **งานที่ตรวจแบบ blind** เท่านั้น (ข้อ 6)

วิธีนี้เป็น best-of-n distillation ที่ใช้ได้จริงเมื่อ N น้อย และหลีกเลี่ยงปัญหา distribution shift

**สาย B (contextual bandit) — อันนี้เป็น RL จริงและนิยามได้ครบ**

| องค์ประกอบ | นิยามในโครงงานนี้ |
|---|---|
| **context (state)** | ประเภทชิ้นงาน · เกณฑ์ที่กำลังตรวจ · `rubric_version_id` · สัญญาณจากชั้น analyzer (จำนวนเฟรม จำนวน component ผลตรวจ contrast) · ความยาว/ความซับซ้อนของไฟล์ |
| **action (arm)** | กลยุทธ์การตรวจ 5 ตัว: (1) zero-shot · (2) few-shot 3 anchor · (3) best-of-3 แล้ว majority · (4) ให้บรรยายก่อนให้คะแนน · (5) โมเดลเล็กแทนโมเดลใหญ่ |
| **reward** | `1 − |ระดับที่ AI ให้ − ระดับที่อาจารย์ให้| / (จำนวนระดับ − 1)` ∈ [0,1] · **มาช้า** (รู้ผลตอนอาจารย์ตรวจเสร็จ) · **วัดได้เฉพาะบนชิ้นที่ blind** |
| **policy** | Thompson sampling หรือ LinUCB |
| **สิ่งที่ทำให้ยากกว่าตำรา** | **reward ไม่นิ่ง** — เมื่อ rubric หรือ JudgePromptVersion เปลี่ยน ค่าที่เคยเรียนมาก็เก่าทันที ต้องใช้ **bandit แบบ sliding window หรือ discount** และใส่ `rubric_version` เป็นส่วนหนึ่งของ context |

**ต้นทุนของ arm ต่างกัน** (best-of-3 แพงกว่า zero-shot 3 เท่า) จึงควรใช้ **reward สุทธิ = ความแม่น − λ × ต้นทุน** และรายงานผลทั้งแบบคิดและไม่คิดต้นทุน — ตัวนี้ทำให้ผลการทดลองมีคำตอบเชิงปฏิบัติที่นำไปใช้ได้ทันที

### 5. Reward hacking ที่ต้องระวัง และวิธีตรวจจับ

| # | รูปแบบ | ทำไมเกิด | วิธีตรวจจับ |
|---|---|---|---|
| RH1 | **ให้ระดับกลางทุกครั้ง** | MAE ต่ำที่สุดถ้าการกระจายกระจุกกลาง | ดู **การกระจายของระดับที่ออก** เทียบกับของอาจารย์ · QWK จะพังทันทีแม้ MAE ดูดี |
| RH2 | **เดาจากการกระจายของชั้น ไม่ได้ดูงาน** | ถ้ารู้ว่าชั้นนี้ส่วนใหญ่ได้ระดับ 3 การเดา 3 ก็ได้ reward สูง | **การทดสอบสลับงาน (swap test)** — ป้อนไฟล์ของนักศึกษาคนอื่นเข้าไปโดยคงบริบทอื่นไว้ ถ้าคะแนนแทบไม่เปลี่ยน แปลว่าไม่ได้ดูงานจริง |
| RH3 | **เขียนเหตุผลยาวและน่าเชื่อจนอาจารย์ไม่แก้** | reward วัดจาก "อาจารย์ไม่แก้" ก็จะจูงใจให้ทำให้อาจารย์เชื่อ ไม่ใช่ให้ตัดสินถูก | **นี่คือเหตุผลที่ reward ต้องนับเฉพาะชิ้นที่ blind** — ถ้าอาจารย์ไม่เห็นคะแนนและเหตุผลของ AI ตอนตรวจ ช่องทางนี้ก็ปิด |
| RH4 | **จูนไปที่ตัววัด** จากการเปิด test set ซ้ำ | ทำโดยไม่รู้ตัวได้ง่ายมาก | ฟิลด์ `dataset_split` ของ ticket 12 + ระบบปฏิเสธและบันทึกทุกครั้งที่มีการพยายามอ่าน test |

> **swap test ควรเขียนเป็นการทดลองย่อยในเล่ม ไม่ใช่แค่ขั้นตอนตรวจสอบภายใน** — มันตอบคำถามที่กรรมการถามแน่ ๆ ว่า "รู้ได้อย่างไรว่า AI ดูงานจริง ไม่ได้เดา" ด้วยตัวเลข ทำได้ถูกมาก (รันซ้ำ 20–30 ชิ้น) และให้ผลที่มีความหมายไม่ว่าออกมาทางไหน

### 6. ข้อมูลที่ใช้ได้ และข้อมูลที่ใช้ไม่ได้

**ใช้ได้กับสาย D และ B: เฉพาะคู่คะแนนจากชิ้นที่ตรวจแบบ blind เท่านั้น** — คะแนนที่อาจารย์ให้หลังเห็นคะแนน AI แล้ว **ไม่ใช่ป้ายกำกับอิสระ** ถ้าเอามาเทรน โมเดลจะเรียนรู้จากคำตอบที่ตัวเองมีส่วนเขียน

| ปริมาณที่คาด | จำนวน |
|---|---|
| ชิ้นงานที่อาจารย์ตรวจ blind ต่อภาค | 100–150 (งบของ ticket 15) |
| คู่คะแนนระดับเกณฑ์ต่อภาค | ~330–1,000 |
| **นักศึกษา/กลุ่มที่เป็นคลัสเตอร์อิสระ** | **40–60 — นี่คือ N จริงของงานวิจัย** |
| รวมสองภาค | ~660–2,000 คู่ · 80–120 คลัสเตอร์ |

**ต้องเขียนย่อหน้านี้ในบทที่ 3 ตรง ๆ** — ตัวเลข 2,000 ดูเหมือนพอสำหรับ DPO แต่ effective N คือหลักสิบ ทุก CI ต้องคำนวณจากคลัสเตอร์ ไม่ใช่จากจำนวนแถว การรายงานว่า "มีข้อมูล 2,000 ตัวอย่าง" โดยไม่พูดถึงคลัสเตอร์คือการรายงานที่ทำให้เข้าใจผิด

### 7. ทรัพยากร — มี GPU Server ของภาควิชา

**เปลี่ยนแผนไปในทางที่ดีขึ้นชัดเจน** — research 04 วางแผนไว้บน Kaggle (T4 16GB จำกัด 30 ชม./สัปดาห์ เซสชันละ 12 ชม.) การมีเครื่องของภาคทำให้สาย D กลายเป็นของที่ทำได้สบายขึ้นมาก และ **แก้ปัญหา PDPA ไปในตัว** เพราะงานนักศึกษาไม่ต้องออกนอกคณะ

**แต่ต้องระวังสองข้อ**

1. **GPU Server ไม่ได้แก้ค่า API ของโมเดล frontier** — baseline B2/B3 และการตรวจจริงประจำวันยังเรียก API ภายนอก (ticket 14: ~240 calls ต่อชิ้นงาน) เครื่องของภาคช่วยเฉพาะสาย D กับการรันโมเดลเปิด **จึงยังต้องมีงบ API ก้อนเล็ก หรือยอมใช้โมเดลเปิดที่โฮสต์เองเป็นตัวตรวจหลัก** — เป็นการตัดสินใจที่ต้องทำใน ticket 17
2. **ยังไม่รู้สเปกจริง** ซึ่งเป็นตัวกำหนดว่าเทรนโมเดลขนาดไหนได้

**ตารางตัดสินตาม VRAM ต่อการ์ด** (จาก research 04 §4 — เอาไปเทียบทันทีที่ ticket 06 ได้คำตอบ)

| VRAM | ทำอะไรได้ | ข้อเสนอ |
|---|---|---|
| 16 GB (T4/V100) | QLoRA 7–8B ได้ · 13B ไม่ไหว | ใช้ Qwen/Llama ระดับ 7–8B — พอสำหรับคำถามวิจัยนี้ |
| 24 GB (RTX 3090/4090/A5000) | QLoRA 13B ได้สบาย · LoRA 7–8B แบบไม่ quantize ได้ | **จุดที่คุ้มที่สุด** |
| 40–80 GB (A100/H100) | 30B+ ได้ · full fine-tune 7B ได้ | เกินความจำเป็นของโจทย์นี้ ใช้ทำหลายรอบขนานแทนจะคุ้มกว่า |

**คำถามที่ต้องเพิ่มเข้า [ticket 06](06-faculty-infra-survey.md)** — VRAM ต่อการ์ดและจำนวนการ์ด · จองต่อเนื่องได้กี่ชั่วโมง มีคิวแย่งกับใครไหม · **ออกอินเทอร์เน็ตได้ไหม** (ต้องโหลดโมเดลจาก HuggingFace ครั้งละหลายสิบ GB) · CUDA/driver version และมี Docker ไหม · **วางข้อมูลงานนักศึกษาบนเครื่องนั้นได้ไหมตามระเบียบ สจล.** (ผูกกับ ticket 18)

**ประมาณการเวลาเครื่อง**: QLoRA 7–8B บนข้อมูลระดับนี้ ≈ 1–3 ชม./รอบ × 24 รอบ ≈ **25–70 ชม.** กระจายได้ตลอดภาค 2 — ไม่ใช่ภาระที่หนักสำหรับเครื่องที่มีอยู่แล้ว

### 8. ปฏิทินและจุดตัดสินใจหยุด

สอบจบปลายภาค 2/2569 (ราว เม.ย.–พ.ค. 2570) **วันที่ด้านล่างคือวันตัดสินใจจริง ไม่ใช่วันประมาณ**

| วันที่ | ประตู | ถ้าไม่ผ่าน |
|---|---|---|
| **31 ต.ค. 2569** | **P0 เสร็จ** — ระบบบันทึกครบตาม ticket 15 §10 · เริ่ม blind ตั้งแต่ชิ้นงานแรก · ตรวจซ้ำรอบ 0 เสร็จ **มีเพดานมนุษย์เป็นตัวเลขแล้ว** | **หยุดสาย RL ทั้งหมดทันที** ทุ่มเวลาที่เหลือให้ระบบหลัก — ไม่มีเพดานมนุษย์ = ไม่มีตัวหาร = ทุกตัวเลขหลังจากนี้ตีความไม่ได้ |
| **31 ธ.ค. 2569** *(จบภาค 1)* | มีคู่คะแนน blind ≥ **300 คู่** จากนักศึกษา ≥ **35 คลัสเตอร์** · สาย P รันครบอย่างน้อย 2 จุดบนเส้นโค้ง | **ตัดสาย D (P3) ทิ้ง** เดินต่อด้วยสาย P + bandit เท่านั้น รายงานเป็นข้อจำกัดด้านข้อมูล |
| **28 ก.พ. 2570** | **จุดตัดสินใจหลัก** — สาย D ต้องรันจบ end-to-end บนข้อมูลจริงอย่างน้อย 1 รอบ (ไม่ต้องชนะ แค่ต้องรันจบและมีตัวเลข) | **หยุดสาย D เขียนเป็นผลเชิงลบตามย่อหน้า §10** ห้ามต่อเวลา |
| **31 มี.ค. 2570** | **แช่แข็งการทดลอง** — ไม่รันอะไรใหม่อีก **เปิด test set ครั้งเดียว** คำนวณผลทั้งหมด | ไม่มีทางเลือกอื่น — วันนี้เป็นวันตายตัว |
| **เม.ย.–พ.ค. 2570** | เขียนเล่ม + สอบ | |

**กฎเหล็กสองข้อ**

1. **ห้ามเลื่อนวันที่ 28 ก.พ. ไม่ว่าผลจะ "ใกล้จะได้แล้ว" แค่ไหน** — research 04 §7.7 ระบุว่านี่คือกับดักที่กลืนโครงงานบ่อยที่สุด และ "ใกล้จะได้แล้ว" คือความรู้สึกที่เกิดได้ตลอดเวลาโดยไม่สัมพันธ์กับความจริง
2. **31 มี.ค. คือวันเปิด test set ครั้งเดียว** ถ้าเปิดแล้วผลไม่ถูกใจ ห้ามกลับไปแก้แล้วเปิดใหม่ — ถ้าทำ ตัวเลขในเล่มจะไม่ใช่ผลการทดลองอีกต่อไป และต้องเขียนกำกับว่าเปิดกี่ครั้ง

### 9. การเชื่อมกับระบบจริง

**แยกออกจากระบบ ไม่ต่อเข้า MVP** — สาย P และสาย D อยู่ในรูป **สคริปต์วิจัยที่อ่านข้อมูลจากฐานเดียวกันแบบอ่านอย่างเดียว** ไม่มีสิทธิ์เขียนกลับ

| สิ่งที่นำกลับเข้าระบบได้ | วิธี |
|---|---|
| ผลของสาย P | **นำกลับได้และควรนำกลับ** — ออกมาเป็น `JudgePromptVersion` ใหม่ที่ต้องผ่านประตู D1–D3 ของ ticket 15 เหมือนข้อเสนออื่น ๆ ไม่มีสิทธิ์พิเศษ |
| ผลของสาย D (LoRA adapter) | **ไม่นำกลับใน MVP** — จะเปลี่ยนสถาปัตยกรรมจาก "เรียก API" เป็น "โฮสต์โมเดลเอง" ซึ่งเป็นการตัดสินใจระดับ ticket 17 ไม่ใช่ผลพลอยได้ของการทดลอง |
| ผลของสาย B (bandit) | **นำกลับได้ในเทอมถัดไป** — เป็นตารางเลือกกลยุทธ์ต่อ context ซึ่งฝังเป็นค่าคงที่ได้โดยไม่ต้องมี bandit ทำงานจริงในระบบ |

**เหตุผล** — ถ้าการทดลองต่ออยู่กับระบบที่นักศึกษาใช้จริง เวลาการทดลองพัง คะแนนของนักศึกษาก็พังด้วย และจะไม่มีใครกล้าทดลองอะไรอีกเลยตลอดโครงงาน

### 10. ย่อหน้าทางถอย — เขียนไว้ให้ใช้ได้ทันที

> ใช้แทนหัวข้อ "ผลการทดลองส่วน RL" ได้เลยถ้าถึง 28 ก.พ. 2570 แล้วสาย D ไปไม่ถึงไหน แก้แค่ตัวเลข

> **ผลการทดลองด้านการเรียนรู้จากความชอบของผู้สอน**
>
> การทดลองนี้ตั้งคำถามว่า ที่ระดับข้อมูลของรายวิชาเดียว การเรียนรู้จากความชอบของผู้สอนให้ผลต่างจากการปรับ prompt อัตโนมัติหรือไม่ และต้องใช้ชิ้นงานที่ผู้สอนตรวจกี่ชิ้นจึงจะแยกสองวิธีออกจากกันได้
>
> ผลปรากฏว่า **ที่จำนวนข้อมูลสูงสุดที่เก็บได้จริงในสองภาคการศึกษา (\_\_\_ คู่คะแนนจากนักศึกษา \_\_\_ คน) ช่วงความเชื่อมั่น 95% ของผลต่างระหว่างสองวิธียังคร่อมศูนย์ (Δ QWK = \_\_\_ [\_\_\_, \_\_\_])** กล่าวคือข้อมูลระดับนี้ไม่เพียงพอที่จะสรุปว่าวิธีใดดีกว่า ผลนี้ตรงกับสมมติฐาน H3 ที่ประกาศไว้ล่วงหน้าก่อนเริ่มเก็บข้อมูล และสอดคล้องกับการทบทวนวรรณกรรมที่พบว่างานที่ใช้ preference learning กับการให้คะแนนอัตโนมัติสำเร็จนั้นใช้ข้อมูลระดับหมื่นชิ้น ซึ่งห่างจากข้อมูลของรายวิชาเดียวสองอันดับของขนาด
>
> จากเส้นโค้งการเรียนรู้ที่วัดได้ **ประมาณการว่าต้องมีคู่คะแนนอิสระประมาณ \_\_\_ คู่ จากนักศึกษาไม่น้อยกว่า \_\_\_ คน จึงจะตรวจจับผลต่างขนาด 0.15 QWK ได้ที่ power 0.8** ซึ่งเทียบเท่ากับการเก็บข้อมูลต่อเนื่อง \_\_\_ ภาคการศึกษา หรือการขยายไปยังรายวิชาอื่นในหลักสูตรพร้อมกัน \_\_\_ รายวิชา
>
> ผลเชิงลบนี้มีนัยเชิงปฏิบัติที่ชัดเจน: **สำหรับผู้สอนที่ต้องการนำ AI มาช่วยตรวจงานในรายวิชาเดียว การลงแรงไปที่การออกแบบตัวอย่างอ้างอิงและการชดเชยความเอนเอียงเชิงตัวเลขรายเกณฑ์ ให้ผลตอบแทนต่อหน่วยแรงสูงกว่าการฝึกโมเดลอย่างมีนัยสำคัญ** ระบบที่พัฒนาขึ้นจึงออกแบบให้กลไกดังกล่าวเป็นส่วนหลัก และวางส่วนการฝึกโมเดลไว้เป็นส่วนขยายที่จะเปิดใช้เมื่อข้อมูลสะสมถึงระดับที่วิเคราะห์ไว้แล้วเท่านั้น
>
> ทั้งนี้การทดลองส่วน contextual bandit ซึ่งเป็นการเรียนรู้แบบเสริมกำลังที่นิยาม state, action และ reward ได้ครบถ้วน สามารถดำเนินการได้จนจบและให้ผล \_\_\_ (ดูหัวข้อ \_\_\_)

**หมายเหตุถึงนักศึกษาที่จะเขียนเล่ม** — ย่อหน้านี้แข็งแรงกว่าย่อหน้า "เราทำ RL แล้วดีขึ้น 3%" ที่ไม่มี CI มาก เพราะมันตอบคำถามที่มีคนอยากรู้จริง มีตัวเลขประกอบทุกข้ออ้าง และแสดงว่าผู้ทำเข้าใจข้อจำกัดของวิธีที่ตัวเองใช้ · งานที่รายงานผลเชิงลบอย่างมีระเบียบเป็นที่ยอมรับในวรรณกรรม (arXiv:2603.20100, 2210.10760, 2310.01798)
