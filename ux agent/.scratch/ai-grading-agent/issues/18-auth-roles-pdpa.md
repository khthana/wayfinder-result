# 18 — บทบาทผู้ใช้ การยืนยันตัวตน และ PDPA

Type: grilling
Status: resolved (7 ส.ค. 69)
Blocked by: 06 (คลี่แล้ว — ดู §การยืนยันตัวตน)

## Question

ใครเข้าใช้ระบบได้บ้าง เข้าอย่างไร เห็นอะไรได้บ้าง และการส่งข้อมูลนักศึกษาไปให้ LLM ภายนอกทำได้แค่ไหน?

ข้อสุดท้ายคือประเด็นที่มักถูกมองข้ามจนกระทั่งวันสอบ: ระบบนี้ส่งผลงานและข้อมูลของนักศึกษาจริงออกไปยัง API ต่างประเทศ ซึ่งเป็นเรื่องที่ต้องตอบให้ได้ทั้งในเชิงกฎหมายและในเชิงเอกสารโครงงาน

## สิ่งที่ต้องตัดสิน

1. **บทบาท** — มีกี่บทบาท (อาจารย์ผู้สอน / ผู้ช่วยสอน / นักศึกษา / ผู้ดูแลระบบ) และแต่ละบทบาททำอะไรได้; คนหนึ่งเป็นอาจารย์ในวิชาหนึ่งและเป็นนักศึกษาในอีกวิชาได้ไหม; วิชาหนึ่งมีอาจารย์หลายคนไหม
2. **การเข้าสู่ระบบ** — ตามผลจาก ticket 06: ใช้ SSO ของสถาบัน / Google login / ระบบบัญชีของตัวเอง — ถ้าทำเอง ต้องมีขั้นตอนลืมรหัสผ่าน ยืนยันอีเมล และการเก็บรหัสผ่านที่ปลอดภัย ซึ่งกินเวลาพัฒนาพอสมควร
3. **การเข้าระบบครั้งแรกของนักศึกษา** — รายชื่อนำเข้าจาก Excel แล้ว นศ. เข้าระบบครั้งแรกอย่างไร (ระบบสร้างบัญชีให้แล้วส่งลิงก์? นศ. สมัครเองแล้วจับคู่ด้วยรหัสนักศึกษา?) และจะจัดการกรณีจับคู่ไม่ได้อย่างไร
4. **ขอบเขตการมองเห็น** — นักศึกษาเห็นเฉพาะของตัวเองและของกลุ่มตัวเอง; เห็นคะแนนเพื่อนไหม; เห็นคะแนนเฉลี่ยของชั้นไหม; อาจารย์เห็นข้ามวิชาที่ไม่ได้สอนไหม; ผู้ช่วยสอนตรวจได้แต่แก้ rubric ไม่ได้ใช่ไหม
5. **PDPA และข้อมูลส่วนบุคคล**
   - ข้อมูลอะไรบ้างที่ถือเป็นข้อมูลส่วนบุคคล (ชื่อ รหัสนักศึกษา อีเมล ผลงาน คะแนน)
   - **ต้องส่งชื่อ/รหัสนักศึกษาไปกับ prompt ไหม** — คำแนะนำคือไม่ต้อง ควรลบข้อมูลระบุตัวตนก่อนส่งให้ LLM ทุกครั้ง ซึ่งลดความเสี่ยงและยังลด bias จากการที่ AI รู้ว่างานเป็นของใครด้วย
   - ผลงานของนักศึกษาที่ส่งไปยัง LLM ผู้ให้บริการเก็บไว้ฝึกโมเดลไหม — ต้องตรวจสอบและระบุในเอกสาร
   - ต้องมีหน้าขอความยินยอมไหม ข้อความว่าอย่างไร ปฏิเสธได้ไหม (ถ้าปฏิเสธแล้วต้องให้อาจารย์ตรวจเองใช่ไหม)
   - เก็บข้อมูลไว้กี่ปี ลบเมื่อไร นักศึกษาขอลบข้อมูลของตนได้ไหม
6. **บันทึกการใช้งาน (audit log)** — ต้องบันทึกอะไรบ้าง (ใครดูคะแนนใคร ใครแก้คะแนน ใครส่งออกข้อมูล) — เชื่อมกับ ticket 12

## สิ่งที่ต้องได้เมื่อจบ ticket

- ตารางสิทธิ์ บทบาท × การกระทำ
- วิธีการเข้าสู่ระบบที่เลือก พร้อมขั้นตอนการเข้าใช้ครั้งแรกของนักศึกษา
- นโยบายข้อมูลส่วนบุคคลเขียนเป็นข้อความที่ยกไปใส่เอกสารโครงงานและหน้าขอความยินยอมได้
- กฎการลบข้อมูลระบุตัวตนก่อนส่งให้ LLM

## ผลลัพธ์ (7 ส.ค. 69)

ได้มาจากการสัมภาษณ์อาจารย์ 10 คำถาม ทีละข้อ ทุกข้อมีคำตอบที่แนะนำมาให้พร้อมเหตุผลและราคาที่ต้องจ่าย อาจารย์เลือกตามคำแนะนำ 7 ข้อ และเลือกต่างออกไป 3 ข้อ (ข้อ 3, 4, 5) — ที่ต่างถูกบันทึกไว้พร้อมเหตุผลของอาจารย์ เพราะเป็นจุดที่ทีมโครงงานอาจอยากถกใหม่

**ข้อเท็จจริงที่ค้นเอง ไม่ได้ถาม** — `dig kmitl.ac.th MX` ชี้ไปที่ `aspmx.l.google.com` และ alt1–alt4 มี `google-site-verification` 5 รายการ และ SPF include `_spf.google.com` แปลว่า **สจล. ใช้ Google Workspace อยู่แล้ว** ซึ่งเป็นข้อที่ ticket 06 ค้างไว้ จึงถือว่าคลี่แล้วโดยไม่ต้องรอฝ่าย IT

### 1. การยืนยันตัวตน

**Google Sign-In จำกัดโดเมนด้วย `hd=kmitl.ac.th`** — ไม่มีระบบบัญชีของตัวเอง

| ได้อะไร | เหตุผล |
|---|---|
| ไม่เก็บรหัสผ่านเลยแม้แต่ hash เดียว | ความเสี่ยงข้อมูลรั่วที่หนักที่สุดหายไปทั้งก้อน |
| ไม่ต้องสร้างหน้าลืมรหัสผ่าน ยืนยันอีเมล เปลี่ยนรหัสผ่าน | ประหยัดเวลาพัฒนาจริงหลายวัน — เป็นงานที่ไม่มีคุณค่าทางวิชาการเลย |
| อีเมลที่ได้กลับมาคือกุญแจจับคู่กับรายชื่อที่นำเข้า | ไม่ต้องออกแบบรหัสเชิญหรือลิงก์ตั้งรหัสผ่าน |
| ไม่ต้องขออนุมัติจากฝ่าย IT | เพราะ Google Workspace ของสถาบันมีอยู่แล้ว ไม่ใช่การขอเชื่อม SSO ตัวใหม่ |

**session** — ใช้ session cookie ฝั่งเซิร์ฟเวอร์ อายุ 12 ชั่วโมง ต่ออายุเมื่อมีการใช้งาน ไม่มี "จำฉันไว้" เพราะเครื่องในห้องแล็บเป็นเครื่องใช้ร่วม
**นโยบายรหัสผ่าน** — ไม่มี เพราะไม่มีรหัสผ่าน (ข้อนี้ตอบข้อค้างใน §4.2 ของเอกสาร 01 โดยการทำให้คำถามหายไป ไม่ใช่โดยการตอบ)

### 2. สองขั้นของการเข้าถึง — ขั้นตอนที่อาจารย์กำหนดเอง

อาจารย์ปฏิเสธข้อเสนอเดิมของผม (ไม่สร้างบัญชีล่วงหน้า ให้จับคู่ตอนล็อกอินครั้งแรก) และกำหนดโครงสร้างเป็นสองขั้นที่แยกเจ้าของกัน

| ขั้น | ใครทำ | ทำอะไร | ผลลัพธ์ |
|---|---|---|---|
| 1 | **ผู้ดูแลระบบ** | นำเข้าตารางที่มี `รหัสนักศึกษา` + `ชื่อ-นามสกุล` | บัญชีนั้น**ล็อกอินได้** แต่ยังไม่เห็นวิชาใดเลย |
| 2 | **อาจารย์** | enroll นักศึกษาเข้า section ที่ตนสอน | นักศึกษา**เห็นวิชานั้น** และส่งงานได้ |

**ไม่ต้องมีคอลัมน์อีเมลในไฟล์นำเข้า** เพราะอีเมลนักศึกษาของ สจล. มีรูปแบบคงที่คือ `<รหัสนักศึกษา>@kmitl.ac.th` ระบบจึงสร้างอีเมลจากรหัสได้เอง แล้วใช้อีเมลนั้นจับคู่กับสิ่งที่ Google ส่งกลับมาตอนล็อกอิน — จุดนี้เป็นข้อเท็จจริงที่อาจารย์ยืนยัน ถ้ารูปแบบอีเมลเปลี่ยน (เช่น หลักสูตรนานาชาติ หรือ นศ. ต่างชาติ) ต้องมีช่องกรอกอีเมลด้วยมือเป็นทางออก

**อาจารย์ผู้สอนใช้รูปแบบอีเมลคนละแบบ** (`ชื่อ.นามสกุลย่อ@kmitl.ac.th`) จึงต้องนำเข้าด้วยอีเมลตรง ๆ ไม่ derive

#### กรณีล็อกอินสำเร็จแต่ไม่มีบัญชี — **ปฏิเสธ**

อาจารย์เลือกให้ปิดประตู ผมเสนอให้สร้างบัญชีสถานะ "รอตรวจสอบ" อัตโนมัติ อาจารย์ไม่เอา เหตุผลที่รับได้คือ admin ต้องรู้ว่ามีใครพยายามเข้า และในเทอมทดลอง admin กับอาจารย์เป็นคนเดียวกันจึงไม่มีคอขวดจริง

สิ่งที่ต้องทำเพื่อชดเชยความเสี่ยงที่ตามมา

- ข้อความบนจอต้อง**บอกว่าให้ติดต่อใครและติดต่ออย่างไร** ไม่ใช่ "เกิดข้อผิดพลาด" หรือ "คุณไม่มีสิทธิ์เข้าใช้งาน"
- **บันทึกความพยายามที่ถูกปฏิเสธไว้** พร้อมอีเมลและเวลา — รายการนี้คือรายชื่อนักศึกษาที่ตกหล่นจากการนำเข้า ซึ่งเป็นของที่ admin ต้องตามเก็บอยู่แล้ว การเก็บ log จึงกลายเป็นฟีเจอร์ ไม่ใช่แค่ความปลอดภัย
- หน้า admin ต้องมีปุ่ม "สร้างบัญชีจากรายการที่ถูกปฏิเสธ" กดครั้งเดียวจบ ไม่ต้องพิมพ์รหัสใหม่

> **ความเสี่ยงที่เหลืออยู่และต้องเขียนในเอกสาร** — ถ้าวันส่งงาน admin ไม่ว่าง นักศึกษาที่ตกหล่นจะส่งงานไม่ได้ และผลคือคะแนนศูนย์ ไม่ใช่แค่ความไม่สะดวก ต้องมีทางออกนอกระบบ (ส่งงานทางอีเมลแล้วอาจารย์นำเข้าให้ทีหลัง) เขียนไว้ในประมวลรายวิชา

#### ใครสร้างบัญชีได้

**เฉพาะผู้ดูแลระบบ** — ผมเสนอให้อาจารย์สร้างได้ด้วยเพื่อกันคอขวด อาจารย์เลือกให้ทะเบียนบัญชีมีเจ้าของคนเดียว และในเทอมทดลอง**อาจารย์สวมบทบาทผู้ดูแลระบบเอง** จึงไม่ต้องรอใคร ข้อดีคือชื่อ-นามสกุลจะไม่เพี้ยนจากการที่หลายคนต่างคนต่างกรอก

### 3. บทบาทและการสวมหลายบทบาท

**โครงข้อมูล** — บทบาทผูกกับ *การเปิดสอน (course offering)* ไม่ผูกกับคน คนหนึ่งคนมีบัญชีเดียว (เพราะมีอีเมลสถาบันเดียว) แล้วในแต่ละ section ถือบทบาทอะไรก็ว่าไปตามนั้น ส่วนสิทธิ์ผู้ดูแลระบบเป็น**ธงแยกต่างหาก**ที่ไม่ผูกกับวิชาใดเลย

**หน้าจอ** — อาจารย์เลือกให้มี **ปุ่มสลับบทบาทที่ชัดเจน** พร้อมแถบบอกสถานะค้างไว้ตลอดว่าตอนนี้อยู่ในบทบาทใด ผมเสนอแบบไม่ต้องสลับ (แสดงทุกอย่างที่มีสิทธิ์) แต่แบบสลับดีกว่าในสองแง่ที่ผมประเมินต่ำไป: **audit log อ่านแล้วเถียงไม่ได้** เพราะผู้ใช้เจตนาเข้าโหมดนั้นก่อนลงมือ และ**เมนูแต่ละโหมดสั้นลงมาก** ซึ่งสำคัญเพราะอาจารย์คนเดียวถือสามบทบาทพร้อมกันได้

**สลับได้เฉพาะบทบาทที่ตัวเองถือจริง** ปุ่มไม่ใช่การเพิ่มสิทธิ์ เป็นการเลือกมุมมอง

กรณีที่ต้องรองรับและรองรับได้ด้วยโครงนี้ — TA ที่เป็นนักศึกษาปริญญาโท (เป็นผู้ช่วยสอนวิชาหนึ่ง เป็นนักศึกษาอีกวิชาหนึ่ง) · อาจารย์ที่ไปลงเรียนวิชาอื่น · อาจารย์ที่เป็นผู้ดูแลระบบด้วย

**หนึ่ง section มีอาจารย์ได้หลายคน สิทธิ์เท่ากันทุกคน** — ไม่มีแนวคิด "อาจารย์หลัก" เพราะการสอนร่วมเป็นเรื่องปกติ และการบังคับให้มีคนเดียวจะจบลงที่การใช้บัญชีร่วมกัน ซึ่งทำลาย audit log ทั้งระบบ *(ข้อนี้เป็นข้อสันนิษฐานที่ตั้งไว้ อาจารย์ยังไม่ได้ค้าน)*

#### จุดที่ต้องระวังในการสร้างจริง

**แถวที่สำคัญที่สุดในตารางนี้คือแถว "ดูไฟล์งานนักศึกษา" ของผู้ดูแลระบบ** — เอกสาร 01 §4.2 เขียนไว้ว่าผู้ดูแลระบบ "ไม่ควรเห็นเนื้อหางานนักศึกษา" ซึ่ง**ใช้ไม่ได้แล้วในระดับบุคคล**เมื่ออาจารย์สวมบทบาทผู้ดูแลระบบเอง ต้องเปลี่ยนไปบังคับที่ระดับหน้าจอแทน

> **หน้าจอฝั่งผู้ดูแลระบบไม่มีเส้นทางไปถึงไฟล์งานหรือคะแนนของนักศึกษาเลย** ถ้าคนคนเดียวกันอยากดูงาน ต้องสลับไปบทบาทอาจารย์แล้วเข้าทางวิชาที่ตัวเองสอน ซึ่งเป็นสิทธิ์ที่เขามีอยู่แล้วโดยชอบ ไม่ได้มาจากการเป็นผู้ดูแลระบบ และ audit log จะบันทึกว่าเข้ามาในบทบาทใด

ประโยคนี้พูดความจริงและตรวจสอบได้ ต่างจากประโยคเดิมที่พูดถึงสิ่งที่บังคับไม่ได้

2. **ตัดอคติจากตัวตน** — โมเดลที่มองไม่เห็นชื่อ ลำเอียงตามเพศ เชื้อชาติ หรือชื่อเสียงของนักศึกษาไม่ได้ นี่เป็นข้ออ้างที่แข็งกว่ามากเวลาต้องตอบกรรมการว่าทำไมถึงเชื่อผลของระบบ และเป็นสิ่งที่การตรวจด้วยมือทำไม่ได้

**ถ้าชื่อผู้จัดทำอยู่ในพิกเซลของงานเอง — หน้าปก slide มุมล่างของ Figma frame ลายเซ็นใน persona — ระบบถอดออกไม่ได้** นโยบายจึงพูดได้แค่ว่า *"ไม่ส่งข้อมูลระบุตัวตนที่ระบบถืออยู่"* ไม่ใช่ *"โมเดลไม่มีทางรู้ว่าใครทำ"* ทั้งสองประโยคต่างกันมาก และเอกสารต้องใช้ประโยคแรก

*(ทางเลือกที่พิจารณาแล้วไม่เอา: บังคับให้นักศึกษาไม่ใส่ชื่อในไฟล์งาน — ขัดกับธรรมชาติของงาน portfolio ที่ชื่อคือส่วนหนึ่งของชิ้นงาน และบังคับจริงไม่ได้)*

### 6. งานนักศึกษาไม่ออกนอกคณะ

**ตัดสิน: ไฟล์งานของนักศึกษาในรายวิชา ไม่ถูกส่งออกนอกเครือข่ายของคณะเลย ไม่มีเงื่อนไข**

ทำได้เพราะสถาปัตยกรรมที่ตัดสินไว้แล้วรองรับอยู่ — **การตรวจจริงและการทดลองซ้ำทั้งหมดรันบนโมเดลเปิดที่เครื่อง GPU ในคณะ** ส่วน API แบบเสียเงินเป็นเพียงจุดเทียบระดับบนในบทวิจัย

**จุดเทียบทำด้วยชุดตัวอย่างแยกต่างหาก** ที่ขออนุญาตเป็นรายชิ้น — งานของเทอมก่อน ๆ ที่เจ้าของยินยอม หรืองานที่ทีมโครงงานทำขึ้นเอง

#### ทำไมถึงไม่เลือก "ขอความยินยอมรายคนแล้วส่งเฉพาะคนที่ยอม"

1. **ประโยคที่ไม่มีเงื่อนไขมีค่ามหาศาล** ในหน้าประกาศและตอนตอบกรรมการ ทันทีที่กลายเป็น "ไม่ส่ง ยกเว้นบางคน" มันจะอธิบายยากขึ้นสิบเท่าและถูกจับผิดได้ตลอด
2. **มันสร้างนักศึกษาสองชั้นในวิชาเดียวกัน** คนที่ไม่ยินยอมจะถูกตรวจด้วยโมเดลคนละตัวกับเพื่อน ซึ่งไม่ยุติธรรมในเชิงการให้คะแนน
3. **มันทำลายการเปรียบเทียบเอง** ถ้ากลุ่มตัวอย่างคือ "คนที่ยินยอม" ผลที่ได้จะมี selection bias ทันที

**ราคาที่ยอมจ่าย** — ชุดเทียบจะเล็กและอาจไม่สะท้อนงานจริงของเทอมนั้น **ต้องเขียนเป็นข้อจำกัดในบทวิจัย ห้ามปล่อยผ่าน**

**ต้องตรวจสอบและระบุในเอกสารด้วย** ว่าผู้ให้บริการ API ที่ใช้ทำจุดเทียบ นำข้อมูลที่ส่งไปฝึกโมเดลหรือไม่ (ผู้ให้บริการรายใหญ่มักไม่ฝึกจากข้อมูล API แต่ต้องอ้างนโยบายฉบับจริงพร้อมวันที่ ไม่ใช่เขียนจากความจำ) — **ข้อนี้ยังไม่ได้ทำ**

### 7. การแจ้งและความยินยอม

#### ตัดสินเชิงหลักการก่อน: ไม่ใช้ฐานความยินยอมกับการตรวจงาน

ตั๋วเดิมเขียนว่าอาจต้องมี "หน้าขอความยินยอม" — **ข้อเสนอนี้ถูกปฏิเสธ** เพราะผิดทั้งทางกฎหมายและทางจริยธรรม

**นักศึกษาปฏิเสธการถูกตรวจงานไม่ได้** ถ้าปฏิเสธแล้วไม่ได้คะแนน ความยินยอมนั้นก็ไม่ได้ให้โดยอิสระ จึงไม่ใช่ความยินยอมที่ใช้ได้ตาม PDPA ตั้งแต่ต้น การประเมินผลการเรียนเป็นภารกิจของสถาบันอุดมศึกษาอยู่แล้ว **ฐานที่ควรใช้จึงเป็นการปฏิบัติหน้าที่ของหน่วยงานรัฐ ไม่ใช่ความยินยอม**

> **ติดป้ายไว้** — ผู้เขียนไม่ใช่นักกฎหมาย การเลือกฐานตามมาตรา 24 ควรให้ผู้รับผิดชอบ PDPA ของ สจล. ยืนยันก่อนใช้จริง ข้อความข้างล่างเป็นร่างสำหรับถกกับทีม ไม่ใช่ฉบับที่ผ่านการตรวจทางกฎหมาย

#### ตัดสินเชิงช่องทาง: Orientation คือการสื่อสารจริง หน้าจอคือการเก็บหลักฐาน

อาจารย์ตั้งข้อสังเกตว่าปกติจะประกาศตอน orientation รายวิชาอยู่แล้ว และตั้งคำถามว่า **การไปขออนุญาตนักศึกษาตรง ๆ จะกระตุ้นอคติต่อ AI หรือไม่** — เป็นข้อกังวลที่มีมูล และคำตอบคือ **อคติมีจริง แต่ทางออกไม่ใช่การไม่บอก**

เหตุผลสามข้อที่การไม่บอกเป็นทางที่แพงกว่า

1. **ระบบบอกอยู่แล้วโดยการออกแบบ** — §7.4 ตัดสินไว้แล้วว่านักศึกษาเห็นป้ายว่าผ่านตาผู้สอนหรือยัง เห็นชื่อผู้ตรวจของงานชิ้นนั้น และขอดูคำอธิบายชั้น AI ได้เสมอ ถ้าไม่ประกาศแต่ระบบแสดง มันจะกลายเป็น**การค้นพบ** แทนที่จะเป็น**การแจ้ง**
2. **ความเสี่ยงไม่สมมาตร** — ประกาศแล้วราคาคือเสียงบ่นและคำถามในคาบ ซึ่งจบในคาบนั้น ไม่ประกาศแล้วมีคนรู้ทีหลัง เรื่องจะเปลี่ยนจาก "ใช้ AI ดีไหม" ซึ่งเถียงกันได้ ไปเป็น "ปิดบัง" ซึ่งเถียงไม่ขึ้น และลามไปถึงเล่มโครงงานกับ TABEE 1.7 ที่ต้องสาวได้ว่าใครตัดสินอะไร
3. **งานที่เก็บข้อมูลจากคนโดยไม่แจ้ง ติดตั้งแต่ชั้นจริยธรรมการวิจัย** ตีพิมพ์ไม่ได้

**อคติแก้ที่การวางกรอบ ไม่ใช่ที่การซ่อน** — ประโยคที่จะทำให้นักศึกษาต่อต้านคือ *"AI ให้คะแนนคุณ"* ซึ่ง**ไม่จริงตามที่ออกแบบไว้** สถาปัตยกรรมจริงคือ `AI ตรวจ → อาจารย์ยืนยัน/แก้ → นักศึกษาเห็นคะแนน` ประโยคที่ตรงกับความจริงจึงเป็น **"อาจารย์เป็นผู้ให้คะแนนทุกชิ้น โดยมีเครื่องมือช่วยอ่านงานและร่างเหตุผลให้ก่อน"** — ไม่ใช่การเลี่ยงคำ เป็นสิ่งที่ระบบทำจริง

และของที่ลดอคติได้จริงคือของที่ตัดสินไปแล้วทั้งนั้น: เห็น rubric ครบทุกเกณฑ์ทุกระดับตั้งแต่ก่อนส่ง · ทุกคะแนนมีเหตุผลและหลักฐานกำกับ · มีชื่ออาจารย์ติดอยู่กับงานชิ้นนั้น **นักศึกษาไม่ได้เกลียดเครื่องมือ เขาเกลียดกล่องดำ — และระบบนี้โปร่งใสกว่าการตรวจด้วยมือแบบเดิม** ซึ่งเป็นสิ่งที่ควรพูดตรง ๆ ใน orientation

**ข้อสรุปเชิงปฏิบัติ**

| ช่องทาง | หน้าที่ |
|---|---|
| **Orientation รายวิชา** | สื่อสารจริง อธิบายได้ ถามตอบได้ — นี่คือที่ที่นักศึกษาเข้าใจเรื่องนี้ |
| **หน้าจอตอนล็อกอินครั้งแรก** | **เก็บหลักฐาน** ว่าใครรับทราบ เมื่อไร ข้อความเวอร์ชันไหน · ใช้ข้อความชุดเดียวกับ orientation |
| ประมวลรายวิชา | ข้อความเดียวกันอีกที่หนึ่ง สำหรับคนที่ย้อนกลับมาอ่าน |

หน้าจอไม่ได้ทำหน้าที่สื่อสาร เพราะคนอ่านข้อความบนหน้าล็อกอินน้อยมาก — ยอมรับข้อนี้ตรง ๆ แล้วออกแบบให้มันทำสิ่งที่มันทำได้ดีคือเก็บหลักฐานรายคนพร้อมเวลาและเวอร์ชัน

### 8. ร่างข้อความ — ประกาศความเป็นส่วนตัว

> ยกไปใช้ได้ทั้งบนหน้าจอ ในสไลด์ orientation และในเล่มโครงงาน · ช่องในวงเล็บเหลี่ยมต้องเติมก่อนใช้จริง

---

**ประกาศเรื่องข้อมูลส่วนบุคคล — ระบบช่วยตรวจงาน [ชื่อวิชา]**

**อาจารย์เป็นผู้ให้คะแนนทุกชิ้น** วิชานี้ใช้ระบบที่มีเครื่องมือช่วยอ่านงานและร่างเหตุผลของคะแนนเสนอให้อาจารย์ก่อน อาจารย์เป็นผู้ยืนยันหรือแก้ทุกคะแนนก่อนประกาศ **คะแนนที่นักศึกษาเห็นคือคะแนนที่อาจารย์ตัดสินแล้วเสมอ**

**ข้อมูลที่เก็บ** ชื่อ-นามสกุล รหัสนักศึกษา อีเมลของสถาบัน ไฟล์งานที่ส่ง คะแนน เหตุผลของคะแนน และบันทึกการแก้คะแนน

**เก็บไปทำอะไร** ประเมินผลการเรียนตามเกณฑ์ที่ประกาศไว้ในประมวลรายวิชา และจัดทำหลักฐานประกอบการประกันคุณภาพหลักสูตร

**ประมวลผลที่ไหน** ไฟล์งานถูกประมวลผลบนเครื่องคอมพิวเตอร์ภายในคณะเท่านั้น **ไม่ถูกส่งออกไปยังผู้ให้บริการภายนอก** และก่อนส่งเข้าเครื่องมือช่วยอ่าน ระบบจะถอดชื่อ รหัสนักศึกษา อีเมล และชื่อไฟล์เดิมออกทั้งหมด เครื่องมือจะเห็นงานเป็นรหัสที่ไม่ระบุตัวตน

**ข้อจำกัดที่ต้องแจ้งให้ทราบ** หากในตัวงานมีชื่อผู้จัดทำปรากฏอยู่ เช่น บนหน้าปกหรือมุมของหน้าจอออกแบบ ระบบไม่สามารถถอดออกได้ ระบบถอดได้เฉพาะข้อมูลที่ระบบเก็บไว้เท่านั้น

**เก็บนานเท่าไร** ไฟล์งานและคะแนนเก็บไว้ **5 ปีการศึกษา** นับจากวันปิดรายวิชา หลังพ้นกำหนดระบบจะลบไฟล์งาน และเก็บไว้เฉพาะคะแนนกับผลการบรรลุผลลัพธ์การเรียนรู้ในรูปแบบที่ไม่ระบุตัวบุคคล

**สิทธิ์ของนักศึกษา**
- ขอดูข้อมูลของตนเองที่ระบบเก็บไว้ได้
- ขอแก้ข้อมูลที่ไม่ถูกต้องได้ เช่น ชื่อสะกดผิด
- **งานและคะแนนเป็นหลักฐานทางการศึกษาที่สถาบันมีหน้าที่เก็บตามกฎหมาย จึงไม่สามารถขอลบได้**
- หากไม่เห็นด้วยกับคะแนน ให้ติดต่ออาจารย์ผู้สอนโดยตรงที่ **[วัน เวลา และสถานที่จริง]** — ระบบไม่มีช่องทางทักท้วงในตัวเอง

**ผู้ควบคุมข้อมูล** [ชื่ออาจารย์ผู้สอน] · [อีเมล] · **เจ้าหน้าที่คุ้มครองข้อมูลของ สจล.** [ช่องทางติดต่อ]

### 9. ร่างข้อความ — ขอความยินยอมส่วนวิจัย

> **นี่คือความยินยอมจริง ปฏิเสธได้ ถอนได้ และต้องไม่มีผลต่อคะแนนแม้แต่น้อย** แยกหน้าจอออกจากประกาศข้างบนอย่างชัดเจน ห้ามรวมเป็น checkbox เดียวกัน

---

**ขอความยินยอมเพื่อการวิจัย — ปฏิเสธได้ ไม่มีผลต่อคะแนน**

ระบบนี้พัฒนาขึ้นเป็นโครงงานของนักศึกษา คณะ[...] สจล. นอกเหนือจากการใช้ตรวจงานในรายวิชาแล้ว ทีมผู้พัฒนาขอความยินยอมเพิ่มเติมสามข้อ **แต่ละข้อเลือกแยกกันได้**

`☐` ยินยอมให้นำงานของข้าพเจ้าไปอยู่ในชุดข้อมูลเปรียบเทียบ ซึ่ง**อาจถูกส่งไปประมวลผลกับผู้ให้บริการภายนอกประเทศ**
`☐` ยินยอมให้นำงานและคะแนนซึ่งถอดชื่อออกแล้ว ไปแสดงเป็นตัวอย่างในเล่มโครงงานที่เผยแพร่
`☐` ยินยอมให้เก็บงานของข้าพเจ้าไว้เกินกำหนด 5 ปี เพื่อใช้ทำการทดลองซ้ำ

**การไม่ยินยอมไม่มีผลต่อคะแนน การตรวจงาน หรือการเรียนการสอนใด ๆ** งานของท่านยังถูกตรวจด้วยวิธีเดียวกันกับทุกคน

**ถอนความยินยอมได้ทุกเมื่อ** ที่หน้า "ข้อมูลของฉัน" เมื่อถอนแล้วงานของท่านจะถูกนำออกจากชุดข้อมูลวิจัยภายใน 30 วัน — ยกเว้นส่วนที่ถูกตีพิมพ์ไปแล้วซึ่งเรียกคืนไม่ได้ จึงขอให้พิจารณาข้อที่สองอย่างรอบคอบ

### 10. อายุข้อมูลและสิทธิ์ขอลบ

| ก้อนข้อมูล | อายุ | พ้นกำหนดแล้ว |
|---|---|---|
| ไฟล์งานที่นักศึกษาส่ง | **5 ปีการศึกษา** นับจากวิชาปิด | **ลบ** |
| คะแนนรายเกณฑ์ + เหตุผล + หลักฐาน | 5 ปีการศึกษา | ถอดตัวตนแล้วเก็บต่อ |
| ผลการบรรลุ CLO ระดับรายวิชา | ไม่มีกำหนดลบ | เก็บต่อแบบไม่ระบุตัวบุคคลอยู่แล้ว |
| audit log | 5 ปีการศึกษา | ลบ |
| ชุดข้อมูลวิจัย (เฉพาะที่ยินยอม) | ตามที่ยินยอม | ลบเมื่อถอนความยินยอม |

**ทำไม 5 ปี** — TABEE ต้องการ Course Portfolio ที่มีชิ้นงานจริงย้อนหลังอย่างน้อย 2 ปีการศึกษา ในวงรอบรับรอง 6 ปี ตัวเลข 5 ครอบวงรอบได้โดยไม่ต้องเดาว่ารอบประเมินหน้าจะมาเมื่อไร ขณะที่ 2 ปีเสี่ยงว่ารอบประเมินมาถึงตอนที่งานถูกลบไปแล้ว

**ทำไมไฟล์กับตัวเลขมีอายุต่างกัน** — ไฟล์งานคือของหนักและเป็นข้อมูลส่วนบุคคลที่แท้จริง ส่วนตัวเลข CLO คือของที่หลักสูตรอยากได้ยาว ๆ และไม่จำเป็นต้องรู้ว่าใครทำ การลบพร้อมกันจึงทิ้งของมีค่าโดยไม่ได้ลดความเสี่ยงเพิ่ม

**เก็บเป็นค่าตั้งค่าที่ผู้ดูแลระบบแก้ได้ ไม่ใช่ค่าคงที่ในโค้ด** เพราะตัวเลขจริงตามระเบียบ สจล. ยังไม่มี

> **ติดป้าย: เลข 5 ปีเป็นค่าตั้งต้นที่ผู้เขียนเสนอ ไม่ใช่ตัวเลขที่อ้างอิงจากระเบียบของ สจล.** ห้ามเขียนในเล่มว่าเป็นไปตามระเบียบมหาวิทยาลัย

#### ทำไมไม่บันทึกการเปิดดู

1. **TABEE 1.7 ต้องการให้สาวได้ว่าใครตัดสินอะไร ไม่ใช่ใครอ่านอะไร** — การเปิดดูไม่ใช่การตัดสิน

**แถวที่สำคัญที่สุดคือการแก้คะแนน** เพราะเป็นจุดเดียวที่มีคนเถียงกันได้ในภายหลัง และเป็นหลักฐานว่าอาจารย์เป็นผู้ตัดสินจริงไม่ใช่ AI — ต่อกับ ticket 12
