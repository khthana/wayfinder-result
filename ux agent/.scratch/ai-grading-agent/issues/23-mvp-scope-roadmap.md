# 23 — ขอบเขต MVP และ roadmap สองภาคการศึกษา

Type: grilling
Status: resolved (7 ส.ค. 69)
Blocked by: 09 ✅, 14 ✅, 15 ✅, 17 ✅ — **ปลดล็อกแล้ว 7 ส.ค. 69 · เป็น frontier ถัดไป**

## Question

จากทุกอย่างที่ตัดสินไปแล้ว อะไรต้องมีในเวอร์ชันแรก อะไรรอได้ และงานทั้งหมดจัดเรียงลงบนปฏิทิน 1 ปีการศึกษาอย่างไร?

โจทย์มี 13 ข้อ แต่ทีมมี 2-3 คนและเวลา 1 ปีที่ต้องแบ่งไปทำเอกสาร สอบหัวข้อ และสอบจบด้วย ticket นี้คือการตัดสินใจที่ไม่มีใครอยากตัดสิน: ตัดอะไรออก

## สิ่งที่ต้องตัดสิน

1. **เส้นทางที่ต้องใช้งานได้ก่อนอย่างอื่น (critical path)** — เสนอไว้ให้พิจารณา: สร้างรายวิชา → นำเข้ารายชื่อ → สร้างชิ้นงาน + rubric → นักศึกษาส่งงาน → AI ตรวจ → อาจารย์ยืนยัน → นักศึกษาเห็นคะแนน — ทุกอย่างนอกเส้นทางนี้เป็นส่วนขยาย
2. **จัดลำดับฟีเจอร์ทั้ง 13 ข้อของโจทย์** เป็นสามกลุ่ม
   - **ต้องมีใน MVP** — ไม่มีแล้วระบบใช้ไม่ได้เลย
   - **ควรมีในเวอร์ชันสมบูรณ์** — เพิ่มคุณค่าชัดเจนแต่รอได้
   - **ยกไปเป็นงานในอนาคต** — เขียนไว้ในบทสุดท้ายของรายงานพอ
   โดยระบุเหตุผลของแต่ละข้อ ไม่ใช่แค่จัดกลุ่ม
3. **จุดตัดสินใจที่ต้องกำหนดวันที่จริง**
   - วันที่ต้องมี gold set พร้อมใช้ (ถ้าเลยวันนี้ calibration ทำไม่ทัน)
   - วันที่ต้องตัดสินว่า RL experiment ไปต่อหรือหยุด (จาก ticket 16)
   - วันที่ต้องหยุดเพิ่มฟีเจอร์แล้วหันไปเขียนรายงานอย่างเดียว
4. **แผนทดลองใช้จริง** — จะเอาระบบไปใช้กับนักศึกษาจริงในภาคไหน; ใช้ทั้งวิชาหรือใช้คู่ขนานกับการตรวจแบบเดิม (คำแนะนำ: คู่ขนาน เพราะได้ข้อมูลเปรียบเทียบและไม่เสี่ยงกับคะแนนจริงของนักศึกษา); ต้องเตรียมอะไรก่อนวันนั้น
5. **แผนสำรอง** — ถ้าถึงกลางเทอมสองแล้ว AI ยังตรวจได้ไม่ดีพอ จะส่งอะไรเป็นผลงาน; ถ้า Figma API ใช้ไม่ได้ตามที่หวัง (ticket 02) จะเปลี่ยนไปทางไหน; ถ้า infra คณะไม่รองรับ (ticket 06) จะไปลงที่ไหนแทน
6. **การแบ่งงานในทีม** — 2-3 คนแบ่งกันอย่างไรให้ไม่ติดกันเอง และแต่ละคนมีชิ้นงานของตัวเองที่เขียนลงรายงานได้

## สิ่งที่ต้องได้เมื่อจบ ticket

- ตารางฟีเจอร์ทั้ง 13 ข้อ จัดกลุ่มพร้อมเหตุผล
- Roadmap เป็นช่วงเวลาพร้อมวันที่จริงตลอด 1 ปีการศึกษา
- รายการจุดตัดสินใจพร้อมวันที่และเกณฑ์
- แผนสำรองของความเสี่ยงหลักสามข้อ

### 1. ภาค 1/2569 ไม่ใช่ช่วงว่างสำหรับเขียนโค้ด แต่เป็นห้องทดลองที่มีของจริงอยู่แล้ว

ภาค 1/2569 เปิดในอีกราวสองสัปดาห์ และจะมี **นักศึกษาจริง งานจริง ~20 ชิ้น × ทั้งห้อง** เกิดขึ้นระหว่าง ส.ค.–ธ.ค. 69 **ไม่ว่าโครงงานนี้จะทำอะไรหรือไม่ทำอะไรก็ตาม** อาจารย์ตรวจงานพวกนี้อยู่แล้วด้วย

และข้อมูลชุดนี้**สะอาดกว่าทุกอย่างที่จะเก็บได้ในภาค 2** เพราะยังไม่มี AI ให้เห็น → **ไม่ถูก anchor โดยธรรมชาติ** ไม่ต้องออกแบบโหมด blind ไม่ต้องสุ่ม ไม่ต้องกันอะไรเลย

**นี่คือการแก้ทางเดินของ [ticket 15](15-calibration-loop-design.md):** ทาง B (สร้าง gold set จากงานสดในภาคก่อนหน้า) **กลับมาเป็นทางหลัก** และดีกว่าทาง A สองเรื่อง — งานสดไม่มีปัญหาลิงก์ Figma ตาย และไม่ต้องขอเวลาอาจารย์เพิ่ม 20–25 ชั่วโมง

→ **ทาง A (ตรวจงานเก่า) ลดชั้นจาก "ต้องทำ" เป็น "ทำเสริมเฉพาะเมื่อความหลากหลายไม่พอ"** และ [ticket 07](07-legacy-work-archive-survey.md) ก็ลดความเร่งด่วนลงตาม — ยังควรเช็ก แต่ไม่ใช่ของที่ขวางทั้งแผนอีกต่อไป

### 2. ของที่เร่งด่วนที่สุดตอนนี้ไม่ใช่โค้ด — และเส้นตายคือวันเปิดภาค 1

| ต้องมีก่อนเปิดภาค 1 | ใคร | ต้นทุน |

ถ้าทำสองอย่างนี้ทัน ภาค 1 จะกลายเป็นภาคเก็บข้อมูลไปโดยที่ไม่มีใครต้องทำงานเพิ่ม ถ้าไม่ทัน โครงงานจะกลับไปอยู่ในสถานะเดิมคือต้องขอเวลาอาจารย์ 20–25 ชั่วโมงเพื่อตรวจงานเก่า

**เงื่อนไขที่ทำให้ข้อมูลนี้ใช้ได้จริง:** ต้องใช้ **rubric ตัวเดียวกัน** กับที่ระบบจะใช้ในภาค 2 ถ้าภาค 2 เปลี่ยน rubric ข้อมูลภาค 1 จะเทียบไม่ได้ตรง ๆ และต้องใช้ **bridge set 15–25 ชิ้น** ตามที่ [ticket 03](03-rubric-calibration-techniques.md) กำหนด → **rubric ที่ยืนยันตอนนี้ควรถือว่าล็อกไปตลอดโครงงาน**

## §1 "คู่ขนาน" แปลว่าอะไรกันแน่ — กับดักสองข้อที่ซ่อนอยู่ในคำนี้

### กับดักที่ 1: คู่ขนานไม่ได้แปลว่ามีคะแนนสองชุด

ถ้าปล่อยไว้ลอย ๆ ระบบจะมีคะแนนชุดหนึ่ง Excel มีอีกชุดหนึ่ง แล้วนักศึกษาเห็นตัวเลขไม่ตรงกัน — เป็นความเสียหายที่ตกกับนักศึกษา ไม่ใช่ความไม่สะดวกของทีม

**กฎที่ต้องล็อก: ทิศทางการคัดลอกเป็นทางเดียว — ระบบ → Excel เท่านั้น**

1. อาจารย์ตรวจและ**ยืนยันคะแนนในระบบก่อนเสมอ**
2. คัดลอกออกไป Excel
3. **ห้ามแก้คะแนนใน Excel โดยไม่ย้อนกลับมาแก้ในระบบ**

ถ้าทำกลับทางหรือแก้สองที่ ระบบจะเก็บข้อมูลที่ไม่ตรงกับสิ่งที่เกิดขึ้นจริง แล้วตัวเลข agreement ทั้งหมดของ [ticket 15](15-calibration-loop-design.md)/[16](16-rl-experiment-design.md) จะวางอยู่บนข้อมูลที่ผิด

**ผลที่ไม่คาดคิด:** กฎนี้**ดึงส่วนหนึ่งของ D8 กลับเข้า MVP** — ปุ่ม **"คัดลอกสามคอลัมน์"** ที่ [ticket 17](17-architecture-and-stack.md) D8 ตัดสินว่าเป็นช่องทางหลัก คือสะพานไป Excel จึงต้องมีตั้งแต่ MVP ส่วน**การดาวน์โหลดไฟล์ .xlsx/CSV ไม่ต้องมี** เพราะไม่มีใครส่งไฟล์นั้นให้ใครในภาคทดลอง

### กับดักที่ 2: คู่ขนานทำให้ภาระอาจารย์ "เพิ่ม" ไม่ใช่ลด — ต้องยอมรับตรง ๆ ในเล่ม

ในภาค 2/2569 อาจารย์จะตรวจงานในระบบ **บวก**ดูแล Excel **บวก**ตรวจแบบ blind อีก 20–30% ของทุกชิ้นงาน

→ **โครงงานนี้พิสูจน์ "ลดเวลาอาจารย์ทั้งเทอม" ไม่ได้ในภาคทดลองของตัวเอง** ถ้าเขียนในเล่มว่าลดได้ จะเป็นการเคลมที่ข้อมูลของตัวเองขัดอยู่

**สิ่งที่วัดได้จริงและต้องวัดแทน: เวลาต่อชิ้น** ในสองโหมด — ตรวจโดยเห็นข้อเสนอ AI พร้อมหลักฐานที่ปักไว้ เทียบกับตรวจแบบ blind ที่ไม่เห็นอะไรเลย ซึ่ง**ได้มาฟรีจากโปรโตคอลที่ตกลงกันไว้อยู่แล้ว** เพราะ blind 20–30% ทำอยู่แล้วเพื่อเหตุผลอื่น เพียงแต่ต้องจับเวลาทั้งสองโหมด

→ **ระบบต้องจับเวลาที่ใช้ตรวจต่อชิ้นตั้งแต่ MVP** และการเคลมของโครงงานเปลี่ยนจาก *"ลดภาระอาจารย์"* เป็น ***"ที่ความแม่นเท่านี้ ใช้เวลาต่อชิ้นเท่านี้"*** ซึ่งคนอ่านต่อยอดเองได้และไม่มีทางถูกจับผิด

**ของแถมจาก §0.1:** ถ้าภาค 1 บันทึกเวลาที่ใช้ตรวจด้วยมือไว้ด้วย (แค่ช่องเดียวในแบบฟอร์ม) โครงงานจะได้ **baseline เวลาต่อชิ้นแบบไม่มีระบบช่วยเลย** ซึ่งเป็นตัวเทียบที่มีค่าที่สุดและหาไม่ได้อีกหลังจากนี้

## §2 "เส้นทางตรวจ + CLO attainment" ชนกับ "Excel เป็นตัวจริง" — และวิธีคลี่

CLO attainment ของ [ticket 13](13-clo-mapping-attainment.md) คิดจาก**ทุกกิจกรรมการประเมิน รวมถึงการสอบ** ถ้าคะแนนสอบไม่เข้าระบบ ตัวเลข CLO ที่ได้คือตัวเลขของครึ่งวิชา และไม่ใช่ตัวเลขที่ลง มคอ.5 ได้จริง — ขัดกับเหตุผลที่อาจารย์เลือกข้อนี้แต่แรก

**ทางออก: เอาเฉพาะ "ช่องกรอกคะแนน" เข้ามา ไม่เอา "สมุดคะแนน" ทั้งก้อน**

| เอาเข้า MVP | ไม่เอาเข้า MVP |
|---|---|
| กิจกรรมการประเมินที่**ไม่มีไฟล์ให้ส่ง** (สอบ/นำเสนอ) สร้างได้ | สัดส่วนคะแนนรวมทั้งวิชา |
| **ตารางกรอกคะแนนด้วยมือ** หนึ่งช่องต่อคน | การเสนอจุดตัดเกรด ([ticket 26](26-computed-layer-outside-rubric.md)) |
| ผูกกิจกรรมนั้นกับ CLO ได้ | ดาวน์โหลดไฟล์ส่งทะเบียน |
| **คำนวณ CLO attainment จากทุกกิจกรรม** | หน้าสรุปเกรดของนักศึกษา |

ช่องกรอกคะแนนด้วยมือคือตารางธรรมดาหนึ่งหน้า ราคาถูกมากเทียบกับสายตรวจทั้งเส้น แต่เป็นสิ่งที่ทำให้ตัวเลข CLO เป็นตัวเลขจริง — **ตัดออกแล้ว CLO attainment ที่เหลือคือของประดับ**

**และตัวเลข CLO ต้องติดป้ายบนหน้าจอว่า "คำนวณจากกิจกรรมที่บันทึกในระบบ N จาก M กิจกรรม" ตลอดเวลา** ไม่ใช่แสดงเป็นตัวเลขเปล่า เพราะระหว่างเทอมมันจะไม่ครบเสมอ (กฎการตัดกิจกรรมที่ยังไม่ตรวจออกจากทั้งเศษและส่วนตาม [ticket 13](13-clo-mapping-attainment.md) ยังใช้เหมือนเดิม)

## §3 เส้นทางวิกฤต — ลำดับที่ห้ามสลับ

```
ตั้งค่ารายวิชา → นำเข้ารายชื่อ → สร้างกิจกรรม + rubric
      → นักศึกษาส่งงาน (แช่แข็งหลักฐานตอนกดส่ง)
      → อาจารย์กด "สั่งตรวจทั้งชุด" (= enqueue + ล็อกการส่ง)
      → AI ตรวจ → อาจารย์ยืนยัน/แก้ → นักศึกษาเห็นคะแนน
      → คะแนนไหลเข้า CLO attainment
```

ทุกอย่างที่ไม่อยู่บนเส้นนี้คือส่วนขยาย รวมถึงของที่ออกแบบละเอียดไปแล้วอย่างหน้าจัดการ TA และหน้าคัดลอกไปเทอมใหม่

**เหตุผลที่ CLO attainment ต่อท้ายได้โดยไม่ทำให้เส้นยาวขึ้นมาก:** มันไม่ใช่ฟีเจอร์ใหม่ แต่เป็นการคำนวณบนข้อมูลที่เส้นนี้ผลิตอยู่แล้ว ([ticket 13](13-clo-mapping-attainment.md) เขียนสูตรครบสามชั้นไว้แล้ว) ต้นทุนจริงอยู่ที่หน้าจอแสดงผลกับช่องกรอกคะแนนสอบ ไม่ใช่ที่ตัวเลข

## §7 แผนสำรองของความเสี่ยงหลัก

### R1 — กลางภาค 2 แล้ว AI ยังตรวจได้ไม่ดีพอ

**ไม่ใช่ความล้มเหลว ถ้าเตรียมกรอบไว้ก่อน** — [ticket 16](16-rl-experiment-design.md) วางคำถามวิจัยเป็น**เส้นโค้ง** ซึ่งเป็นผลการทดลองทั้งตอนชันและตอนแบน และ H3 ทำนายล่วงหน้าแล้วว่า CI จะคร่อมศูนย์

**แต่ต้องมีของที่ส่งได้แม้ตัวเลขไม่สวย** — และมีอยู่แล้วโดยไม่ต้องทำอะไรเพิ่ม:

> **ชั้นกฎที่คำนวณได้แบบ deterministic** ([ticket 09](09-what-ai-can-judge.md) · contrast, จำนวนขนาดฟอนต์, ความสม่ำเสมอของ spacing, การใช้ component) **ไม่พึ่งความแม่นของ LLM เลย** รวมกับสมุดคะแนน + CLO attainment + การสืบย้อนที่มา = **ระบบที่ใช้งานได้จริงและมีคุณค่าต่อรายวิชา แม้ชั้น LLM จะให้คะแนนไม่แม่น**

→ ทีมควรรู้ตั้งแต่วันนี้ว่าชั้นกฎคือ**ตัวประกันความสำเร็จของโครงงาน** ไม่ใช่ของแถมของชั้น LLM

### R2 — Figma API ไม่คืนพิกัดที่ปักหมุดได้

3. ถ้าถอยจริง **ต้องแก้ prototype ของ [ticket 21](21-grading-workspace-prototype.md)** เพราะหน้าจอนั้นวางบนสมมติฐานว่ามีหมุด

## §8 การแบ่งงานในทีม

รอยต่อคือ **สัญญา JSON ที่ชั้น analyzer คืนกลับมา** ล็อกในสัปดาห์แรกแล้วทั้งสามคนเดินขนานกันได้

| คน | รับผิดชอบ | ได้บทไหนในเล่ม |
|---|---|---|
| **A — สายเว็บ** | รายวิชา · รายชื่อ · rubric · ส่งงาน · หน้าจอตรวจแบบ A · หน้าคะแนนนักศึกษา | ออกแบบระบบและส่วนติดต่อผู้ใช้ |
| **B — สายตรวจ** | ตัวอ่าน Figma/PDF · ชั้นกฎ deterministic · ชั้น LLM + vLLM · คิวงาน · การแช่แข็งหลักฐาน | สถาปัตยกรรมการตรวจด้วย AI |
| **C — สายวัดผล** | pipeline gold set · QWK/MAE/เพดานมนุษย์ · หน้าสรุปความสอดคล้อง · การทดลองของ [ticket 16](16-rl-experiment-design.md) | **บทผลการทดลองทั้งบท** |

**ถ้าทีมมี 2 คน:** ยุบ C เข้า B แล้ว**ตัดสาย D ของ [ticket 16](16-rl-experiment-design.md) ทิ้งตั้งแต่วันนี้** ไม่ต้องรอหมุด 31 ธ.ค. — เพราะสาย D กินเวลาคนเต็มคนและเป็นสายที่ตั๋วนั้นบอกเองว่าตัดได้โดยโครงงานยังครบ

**งานของช่วง 0 (แบบฟอร์มบันทึกคะแนน) เป็นของคน C** และเป็นชิ้นแรกที่ต้องเสร็จของทั้งโครงงาน

## §9 สิ่งที่ตั๋วนี้ยังตอบไม่ได้ และต้องตามต่อ

1. **ข้อความต้นฉบับของโจทย์ข้อ 13** — ไม่มีในแฟ้ม ต้องขอจากอาจารย์ก่อนปิด [ticket 24](24-assemble-spec-pack.md)
2. **ปฏิทินการศึกษา สจล. ตัวจริง** — วันเปิด/ปิดภาคที่ใช้ในตั๋วนี้เป็นค่าประมาณ
3. **จำนวนชิ้นงานและลำดับของภาค 2/2569** — ต้องรู้ว่างาน Figma ชิ้นสำคัญตกสัปดาห์ไหน (§0.4)
4. **คำยืนยันเรื่อง blind 20–30% ตลอดภาค 2** — ยังไม่เคยได้คำตอบตรง ๆ ([ticket 04](04-rl-on-small-data.md) ชี้ว่าเป็นเงื่อนไขที่ทำให้ตัวเลขทั้งเล่มมีความหมาย) · **แต่ภาค 1 ให้ข้อมูลที่ไม่ถูก anchor มาแล้วโดยธรรมชาติ ความเสี่ยงข้อนี้จึงเบาลงมาก**
5. **อาจารย์รับการซ้อมใหญ่ปลายภาค 1 ไหม** (§0.3) — เป็นข้อเสนอ ยังไม่ได้ถาม
6. **ให้ TA ตรวจแบบ blind บางส่วนไหม** (ยกมาจาก [ticket 27](27-ta-role-and-capacity.md)) — ในภาคทดลองตัดสินว่าอาจารย์ตรวจเองทั้งหมด ข้อนี้จึงเลื่อนไปเป็นของรุ่นถัดไปโดยปริยาย
