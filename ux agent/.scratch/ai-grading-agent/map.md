## Destination

**ชุดเอกสารส่งมอบ (handoff spec pack)** ที่ทีมนักศึกษา 2-3 คน รับไปลงมือพัฒนาต่อได้ทันที ประกอบด้วย

1. **โครงสร้างของเว็บ** — domain model + ศัพท์กลาง, data model, ผังหน้าจอทั้งหมด, สถาปัตยกรรมระบบ, ขอบเขต MVP และ roadmap 2 ภาคการศึกษา
2. **Wireframe / clickable prototype** ของหน้าจอหลัก โดยเฉพาะหน้าจอตรวจงาน (grading workspace)
3. **Research report** — แนวทางจัดการ AI Agent (สถาปัตยกรรมการตรวจ, rubric calibration) และ RL พร้อมข้อเสนอการทดลองที่มี success criteria ของตัวเอง

Map นี้ **ไม่เขียนระบบจริง** — จบเมื่อทุกอย่างที่ต้องตัดสินใจถูกตัดสินแล้ว และเอกสารพร้อมส่งมอบ

**ชื่อหัวข้อโครงงาน (7 ส.ค. 69):** ยังไม่ได้เลือก — ข้อเสนอ 5 แบบ ไทย/อังกฤษ พร้อมเหตุผลและกับดักถ้อยคำ อยู่ที่ `deliverables/00-project-title-options.md` · ที่แนะนำคือแบบ A "ระบบผู้ช่วยตรวจงานออกแบบ… โดยมีอาจารย์เป็นผู้ยืนยันผลขั้นสุดท้าย" · กับดักที่บันทึกไว้: ห้ามใช้คำว่า "อัตโนมัติ" (ขัดกับ flow ที่อาจารย์ยืนยัน) และห้ามใส่ RL ในชื่อ (ภาค 2 ยังไม่รู้ว่าข้อมูลพอไหม แก้ชื่อตอนใกล้ส่งเล่มไม่ได้) · **รอจากอาจารย์: ภาควิชาและสายของกรรมการสอบ**

**ของแถมนอกขอบเขต (7 ส.ค. 69):** `sample-agent/` — ตัวอย่างแกนกลางการตรวจที่รันได้จริง เขียนเพิ่มตามคำขอของอาจารย์ เพราะนักศึกษางงว่า "เว็บไปเชื่อมกับ LLM ยังไง" ท่อครบ 4 ขั้น (ถอดตัวตน → ชั้นกฎ → ชั้น LLM → รวม+สืบย้อน) มีตัวต่อ LLM สามตัว (mock / vLLM / Anthropic) และ `demo.ts` พิมพ์ JSON ก้อนจริงที่จะยิงออกไปให้ดูกับตา · TypeScript ล้วน ไม่มี dependency ไม่ต้องมี GPU ไม่ต้องมีคีย์ · 19 เทสต์ผ่านหมด · **ยังไม่เคยยิงเข้าเครื่อง GPU จริง** — เป็นสิ่งแรกที่ควรทำเมื่อได้เครื่อง · ไม่ใช่ deliverable ที่ตกลงกันไว้ 3 ข้อข้างบน แต่ใช้แนบไปกับเอกสาร 01/04 ได้

## Notes

**Domain:** การเรียนการสอนระดับอุดมศึกษาไทย (KMITL), outcome-based assessment, AI-assisted grading
**ภาษา:** สื่อสารกับผู้ใช้เป็นภาษาไทย เอกสารส่งมอบเป็นภาษาไทย (ศัพท์เทคนิคคงภาษาอังกฤษ)
**Skills ที่ทุก session ควรใช้:** `/grilling`, `/domain-modeling` (เขียน `CONTEXT.md` ที่ราก effort), `/prototype`, `/research`

**ข้อเท็จจริงที่ปักหมุดแล้ว (จาก charting session):**

- ชิ้นงานที่ตรวจ = **Figma + PDF** เท่านั้น — ไม่มีเว็บ deploy, ไม่มีโค้ด (อาจารย์ยืนยันซ้ำ 6 ส.ค. 69)
- **Figma คือแกนกลาง และบทบาทของมันจะโตขึ้นเมื่อมีระบบ** — ที่ทุกวันนี้ Figma เป็นส่วนน้อยของเทอม เพราะ**ตรวจด้วยมือมันลำบาก** ไม่ใช่เพราะไม่สำคัญ ระบบนี้จึงไม่ใช่แค่ทำของเดิมให้เร็วขึ้น แต่**ปลดข้อจำกัดที่กำหนดหน้าตาของรายวิชาอยู่**
- **Calibration loop = ระบบจริงที่ต้อง ship** / **RL = experiment เชิงวิชาการแยกต่างหาก** ที่ล้มได้โดยโครงงานยังจบ
- ทีม **2-3 คน / 1 ปีการศึกษา**; ใช้ LLM ช่วยเขียนโค้ด → คอขวดคือคุณภาพการตรวจและความน่าเชื่อถือ ไม่ใช่จำนวนหน้าจอ CRUD
- **หลักสูตรใช้ TABEE ไม่ใช่ AUN-QA** — กรอบประกันคุณภาพที่ต้องอ้างอิงในเอกสารส่งมอบและในรายงานโครงงานคือ TABEE (กรอบรับรองหลักสูตรวิศวกรรมของไทย แนวทาง outcome-based เหมือนกัน แต่คนละกรอบ) แนวคิดหลักไม่ต่างกันมากตามที่อาจารย์ยืนยัน โครงสร้างที่ ticket 13 ตัดสินไว้ (ผูก criterion → CLO พร้อมสัดส่วน, รายงานเป็นร้อยละของผู้บรรลุ) ใช้ได้กับทั้งสองกรอบ **แต่ศัพท์และแบบฟอร์มที่ยกไปใส่เอกสารต้องเป็นของ TABEE**
- ระบบ **standalone** ทำทุกอย่างเอง ไม่ต่อกับ LMS เดิม
- ต้อง **deploy บน infra ของคณะ** — stack ยังไม่ล็อก (ดู ticket 06, 17)
- **มีงาน นศ. เทอมก่อนเก็บไว้ แต่คะแนนกระจัดกระจายและไม่มี rubric เดิม** → ต้องมีขั้นตอน re-grade เพื่อสร้าง gold set (ดู ticket 07, 15)
- **โจทย์ข้อ 14 (เพิ่ม 6 ส.ค. 69): คัดลอกรายวิชาไปเทอมใหม่** — คัดลอก CLO + rubric + ตารางสัปดาห์ ไม่คัดลอกคน/งาน/คะแนน และ rubric ที่คัดลอกต้องเป็น RubricVersion ใหม่ (ดู ticket 19)
- **CLO มีอยู่แล้วในเอกสารรายวิชา** (course description + มคอ.3) — หน้าที่ของ AI คือ**อ่านเอกสารแล้วร่างโดยชี้กลับไปที่ย่อหน้าต้นทางได้** ไม่ใช่แต่งขึ้นจากชื่อวิชา · **แต่ตารางสัปดาห์อาจารย์กรอกเอง ห้ามให้ระบบอ่านจาก มคอ.3 มากรอกให้** (อาจารย์สั่ง 6 ส.ค. 69 ดู ticket 19)
- **หน่วยหลักของโดเมนคือ "กิจกรรมการประเมิน" ไม่ใช่ "ชิ้นงาน"** — การสอบคือกิจกรรมการประเมินที่ไม่มีไฟล์ให้เก็บ โครงข้อมูลจึงเป็น กิจกรรมการประเมิน → (มี/ไม่มี) การส่งไฟล์ → ถ้ามีไฟล์จึงมี rubric และการตรวจ · กิจกรรมที่ไม่มีไฟล์ก็ยังต้องผูก CLO และยังต้องมีคะแนน (อาจารย์ยืนยัน 6 ส.ค. 69 ดู ticket 19 · กระทบ ticket 12, 13)
- **ระบบเป็นสมุดคะแนนของทั้งรายวิชา ไม่ใช่เฉพาะส่วนที่ AI ตรวจ** — คะแนนสอบกรอกมือเข้าระบบด้วย ไม่งั้น CLO สะท้อนแค่ครึ่งวิชาและโจทย์ข้อ 11 ส่งออกได้แค่ครึ่งเดียว ราคาที่จ่ายคืออาจารย์ต้องใช้ระบบนี้เป็นสมุดคะแนนหลัก (อาจารย์ตัดสิน 6 ส.ค. 69)
- **ระบบใหม่ยังมีบทบาท TA และต้องมีระบบสิทธิ์** — อาจารย์สั่งว่า **TA ต้องไม่เห็นคะแนนสอบ** ซึ่งยืนยันทั้งสองอย่างพร้อมกัน · ทำให้ทางเลือก "ไม่มี TA เลย" ของ ticket 27 ตกไป และ **"อาจารย์หลายคน + ระบบสิทธิ์" ที่ ticket 19 เคยตัดจาก MVP ต้องกลับเข้ามา** (ในรูปสองบทบาทตายตัว ไม่ใช่ระบบสิทธิ์ที่ตั้งค่าได้)
- **การนำเข้ารายชื่อเป็น add-only ห้ามถอนให้เอง** — คนที่หายไปจากไฟล์ ระบบแจ้งเฉย ๆ ไม่ทำเครื่องหมายถอน เพราะบางคนถอนแล้วแต่มีคะแนนไปแล้ว · ผลข้างเคียงคือปลายเทอมรายชื่อมากกว่าจำนวนจริง ซึ่งอาจารย์รับได้ แต่ทำให้**ตัวหารของ CLO ต้องนิยามใหม่** (อาจารย์สั่ง 6 ส.ค. 69 · กระทบ ticket 13)
- **Infra ของภาควิชาตอบครบแล้ว (6 ส.ค. 69):** ออกอินเทอร์เน็ตได้ · **GPU RTX 5090 32 GB อย่างน้อย 1 การ์ด พ่วง 2 ได้** · ส่งข้อมูลออก LLM API ต่างประเทศได้ตามระเบียบ · เข้าจากนอกเครือข่ายได้ · **VM Linux กลุ่มละ 1 เครื่อง docker + sudo ได้** (ดู ticket 06)
- **ค่า LLM API อาจารย์ต้องออกเอง — เงื่อนไข "ไม่มาก ไม่ประจำ"** จึงเป็น**ข้อจำกัดออกแบบ ไม่ใช่รายละเอียดปฏิบัติการ**: งานที่ทำซ้ำทุกสัปดาห์ (ตรวจจริง) และงานที่รันซ้ำเยอะ (ทดลอง baseline) ต้องอยู่บนโมเดลเปิดที่ 5090 · API เก็บไว้ใช้เป็น**จุดอ้างอิงระดับบนสุด**ซึ่งรันไม่บ่อย · และระบบต้องมี **ตัวนับต้นทุนต่อ call + เพดานงบที่หยุดเรียก API เองเมื่อชน** (ticket 06 §2 · เพิ่มใน ticket 17)
- **โมเดลที่ตรวจงานได้ต้องเป็น vision-language ไม่ใช่ LLM ข้อความล้วน** — งาน UX/UI ที่ต้องตัดสินเป็นภาพ · 32 GB ต่อการ์ดรัน VLM ระดับ 27–32B แบบ 4-bit ได้ (ต้อง spike ยืนยัน)
- **ความเสี่ยง: 5090 เป็น Blackwell ซึ่งใหม่** — CUDA/PyTorch/ไลบรารี serving ต้องเวอร์ชันใหม่พอ **ต้อง spike ก่อนล็อกสถาปัตยกรรม** ไม่ใช่สมมติว่ารันได้ (ticket 17 · เพิ่มในหัวข้อ risk ของ ticket 16)
- **ผลการปรับจูน AI · ตัวอย่างงานที่ปักไว้ · คลังประโยค feedback คัดลอกข้ามเทอมไปด้วย** — ระบบสะสมความรู้ข้ามเทอมได้จริง แต่บังคับว่า **baseline ของเทอมที่ 2 คือ "ตัวที่ยกมา" ไม่ใช่ระบบเปล่า** และชุดทดสอบเทอมใหม่ต้องเป็นงานที่ระบบไม่เคยเห็น (อาจารย์เลือก 6 ส.ค. 69 · กระทบ ticket 15, 16)

**คะแนนของงานเก่าใช้เป็นเฉลยไม่ได้** (7 ส.ค. 69) — คลังงานเก่ามีจริงและครอบคลุมทั้งช่วงคุณภาพ แต่การตรวจเดิมเป็นแบบ **มี/ไม่มี** ไม่ใช่การตัดสินเชิงคุณภาพ ต่อให้แยกตามเกณฑ์ย่อยไว้ก็ตอบคนละคำถามกับที่ระบบใหม่ตอบ → คลังงานเปลี่ยนบทบาทจาก "ข้อมูลที่มี label แล้ว" เป็น **"corpus ที่ต้องตรวจใหม่"** · ผลพลอยได้: การตรวจงานเก่าเป็น blind grading โดยธรรมชาติ (แก้ปัญหาของ ticket 04 ให้ฟรี) และให้ข้อความปัญหาของโครงงานที่มีหลักฐานรองรับ · ห้ามให้อาจารย์เห็นคะแนนเดิมตอนตรวจใหม่ แต่ใช้คะแนนเดิมช่วยสุ่มให้กระจายได้ · **จริยธรรมการวิจัยในมนุษย์: ไม่ต้องผ่าน** ดู [ticket 07](issues/07-legacy-work-archive-survey.md)

**ของจริงที่รออาจารย์เอามาให้ (map เดินต่อได้แต่จะตื้นกว่าที่ควร ถ้าไม่มี):**

- **rubric ที่ใช้จริงในวิชา UX/UI อย่างน้อย 2 ชิ้นงาน พร้อมน้ำหนักคะแนน** — ต้องมีก่อนทำ ticket 10 ให้ลึกได้ และเป็นตัวตอบว่าสัดส่วนคะแนนที่ AI ช่วยไม่ได้มีเท่าไร (ticket 09 ข้อ 2)
- **course description + syllabus (มคอ.3) ตัวจริงของวิชา UX/UI** — อาจารย์เสนอจะอัปโหลดให้เมื่อ 6 ส.ค. 69 · ขอบเขตแคบลงหลังรอบที่ 3: ใช้เป็นวัตถุดิบของ **CLO เท่านั้น** ไม่เอาไปกรอกตารางสัปดาห์ · ยังทำให้ ticket 13 (CLO×PLO) ลึกขึ้นจากของจริง และยังเปิด pipeline ที่สามใน ticket 17 (ชั้นอ่านเอกสารรายวิชา คนละเรื่องกับชั้นอ่านงานนักศึกษา)
- **นับจำนวนชิ้นงานเก่าที่ยังใช้ได้จริง (นับคร่าว ๆ พอ)** — ย้ายออกจาก ticket 07 มาเป็นรายการใน checklist ของเอกสาร 04 · ไม่กระทบแผนหลักแล้วเพราะ gold set สร้างจากงานสดของภาค 1/2569 ได้ แต่เป็นตัวบอกว่า**แผนสำรอง**ของด่าน "ภาค 1 เป็นภาคเก็บข้อมูลได้ไหม" มีอยู่จริงหรือเป็นแค่ชื่อ — ต่ำกว่า ~80 ชิ้น = ทางถอยนั้นไม่มีอยู่
- **อาจารย์ตรวจงานเก่าใหม่ ~80–100 ชิ้น เพื่อสร้าง gold set** — ~20 ชั่วโมง เป็น input ที่มีมูลค่าสูงที่สุดที่อาจารย์ให้โครงงานได้ ดู ticket 07 §3 · ต้องเป็นอาจารย์ตรวจเอง TA แทนไม่ได้
- **คำยืนยันว่าอาจารย์ยอมตรวจแบบไม่เห็นคะแนน AI (blind mode) สุ่ม 20–30% ของทุกชิ้นงาน ตลอดสองเทอม** — ticket 04 ชี้ว่านี่ไม่ใช่ฟีเจอร์เสริม แต่เป็น**เงื่อนไขที่ทำให้ตัวเลขผลการทดลองทั้งโครงงานมีความหมาย** ถ้าอาจารย์ไม่ยอม ต้องรู้ตั้งแต่วันนี้เพื่อเปลี่ยนวิธีเล่าผลในเล่ม ไม่ใช่ไปรู้ตอนวิเคราะห์ข้อมูล
- **ระเบียบของ สจล. 2 ฉบับ** ที่ระบบต้องใส่ตัวเลขจริงแทนค่าสมมติ (ticket 18 ปิดแล้วโดยใส่ค่าตั้งต้นไว้ ต้องได้ตัวเลขจริงจากอาจารย์):
  - **ระยะเวลาเก็บข้อมูลงานและคะแนนนักศึกษา** — ticket 18 ตัดสินใช้ **5 ปีการศึกษา** ไว้ก่อน (พื้นล่างจาก TABEE คือ 2 ปีการศึกษา) ยังไม่มีระเบียบ สจล. รองรับ · ticket 12 ใช้ "ตามระเบียบมหาวิทยาลัย" ไว้ก่อน
  - **ช่องทางติดต่อผู้รับผิดชอบคุ้มครองข้อมูลของ สจล.** — ร่างประกาศความเป็นส่วนตัวใน §4.4.3 ของเอกสาร 01 เว้นช่องนี้ไว้และใช้จริงไม่ได้จนกว่าจะเติม + ผ่านตานักกฎหมาย
  - **เกณฑ์การบรรลุ CLO ที่มหาวิทยาลัยกำหนด** — ticket 13 ใช้ค่าตั้งต้น 60%/70% ไว้ก่อน ถ้า สจล. มีประกาศต้องใช้ตัวเลขนั้นแทน

- **การรวม CLO ขึ้นไปเป็น PLO ระดับหลักสูตร** — ticket 13 วางโครง CLO×PLO ไว้แล้วแต่ยังไม่ตัดสินว่าระบบจะคำนวณ PLO attainment ให้ด้วยหรือปล่อยเป็นงานระดับหลักสูตรนอกขอบเขต รอดูว่าเวลาของโครงงานเหลือแค่ไหนหลัง ticket 15/16
- **การให้ feedback เชิงข้อความกลับนักศึกษา** — ticket 14 ตัดสินแล้วว่านักศึกษาเห็น "เหตุผลของอาจารย์ + หลักฐาน" ตอนประกาศคะแนน แต่ยังไม่ได้ตัดสินว่า AI ควรเขียน feedback เชิงพัฒนา (ไม่ผูกคะแนน) ให้ด้วยหรือไม่ และถ้าให้ ใครเป็นคนอนุมัติก่อนถึงมือนักศึกษา

## Out of scope

งานที่ตัดออกจาก effort นี้อย่างตั้งใจ จะกลับมาได้ก็ต่อเมื่อมีการวาดปลายทางใหม่

- **ตรวจงานที่เป็นเว็บ deploy จริงหรือซอร์สโค้ด** — ตัดจากคำถาม charting ข้อ 2; ต้องใช้ headless browser + DOM/accessibility analysis ซึ่งเป็นระบบคนละก้อน
- **Integrate กับ LMS ของคณะ (Google Classroom / Moodle / MS Teams)** — เลือกทำ standalone
- **Fine-tune โมเดลเป็นฟีเจอร์ production** — RL/fine-tuning อยู่ในฐานะ experiment เท่านั้น (ticket 16)
- **รองรับวิชาอื่นนอกจาก UX/UI ใน MVP** — data model ต้องออกแบบเผื่อการขยาย แต่จะไม่สร้างหรือทดสอบวิชาอื่นใน effort นี้
- **การเขียนระบบจริง** — map นี้จบที่เอกสาร; การพัฒนาเป็นงานของทีมนักศึกษาหลังรับ spec
